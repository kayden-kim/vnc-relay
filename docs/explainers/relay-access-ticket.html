VNC Relay 해설 · WebSocket 중계 접속

철회한 ticket 확인을
vnc-relay에 넣으면

ticket은 어드민 서비스가 연결 직전에 발급하는 짧은 수명의 접속 허가값이다. 사용처는 전용 중계가 ticket을 확인하는 설계를 채택했다가 철회했다. 내재화 안은 같은 확인을 vnc-relay 안에서 한다. 업그레이드 때 서명·만료·사용 기록을 보고, 초기 교환 뒤에 중계 ID를 대조하고, 원격 지원 세션이 끝나는 시각에 연결을 끊는다. 이 해설은 이 확인이 기본으로 꺼져 있고, 운영자가 WS·WSS의 역할마다 설정으로 켠다는 전제로 설명한다. 켜지 않은 vnc-relay는 지금과 같게 동작한다. 그래도 이 기능을 두는 것은 지금 기준과 맞지 않는다. 채택하려면 PRD 확정 기준과 ADR-0002를 다시 결정해야 한다. 06절은 같은 확인을 기기 쪽 Server 역할에 켜는 변형을 다룬다. droidVNC-NG 기기는 리피터에 TCP로만 연결하므로, 이 변형에는 기기 쪽 변경도 필요하다.

이 해설이 다루는 세 상태

현재 기준
vnc-relay는 중계 접속에 토큰을 쓰지 않는다. 접근 통제는 진입점별 출발지 IP 허용 목록이다(ADR-0002). PRD 확정 기준 "WS·WSS 중계 접근"도 중계 접근을 "관리자 로그인·접속 토큰과 분리"한다. 사용처의 현재 계약도 ticket 없이 연결한다.
철회한 설계
사용처의 어드민 서비스가 2026-10-12에 채택하고 2026-11-08에 철회했다. 전용 중계가 서명한 일회용 ticket을 직접 확인하고 UltraVNC Repeater로 넘기는 설계였다.
내재화 안
철회한 설계의 확인 규칙을 vnc-relay 안으로 옮기는 안이다. 이 해설에서 설명하려고 정리했다. 검토 전제는 기본으로 꺼져 있고 역할마다 설정으로 켠다는 것이다(사용자 지시 2026-11-11). 아무도 채택하지 않았고 구현하지 않았다. 기기 쪽 Server 역할에 켜는 변형(06절)도 같다.

이 해설은 요구사항이나 설계를 정하지 않는다. 내재화 안과 Server 역할 변형의 단계 순서·응답 코드·설정 이름·close 코드는 설명을 위한 예시다.

01 / 문제 상황

중계 ID만으로는 누가 연결하는지 알 수 없다

브라우저의 noVNC는 vnc-relay의 /relay/viewer 경로로 WebSocket 업그레이드 요청을 보낸다. 101 응답 뒤에는 초기 교환으로 중계 ID를 보낸다. 같은 중계 ID로 기다리던 기기의 대기 연결이 있으면 둘은 Mode II로 짝을 이룬다.

vnc-relay가 업그레이드 전에 보는 접근 조건은 클라이언트 주소와 Origin이다(계약 1.1절). 출발지 IP 허용 목록에 전체 허용 항목(0.0.0.0/0)을 쓰면 주소 검사는 아무도 거르지 않는다. Origin은 다른 사이트의 브라우저 페이지만 막는다. 요청을 직접 만드는 프로그램은 Origin 헤더를 빼고 보낼 수 있다. 이때 vnc-relay는 Origin 검사만 건너뛰고 주소 검사는 그대로 한다(계약 1.3절).

중계 ID는 짝을 찾는 값이며 비밀값이 아니다(용어집). 그래서 허용된 출발지에서 Origin 검사를 통과한 클라이언트는 중계 ID만 알면 자격 증명 없이 짝을 이룰 수 있다. 그 뒤에 남는 보호는 기기가 확인하는 VNC 비밀번호다. ticket은 여기에 "어드민 서비스에서 방금 연결을 요청한 브라우저인가"라는 조건을 더하려는 방법이다.

03 / 정상 흐름

04 / 철회한 설계

전용 중계가 서명과 사용 기록을 본다

사용처는 처음에 브라우저 앞에 전용 WebSocket 중계를 두려고 했다. 이 중계가 ticket을 확인한 뒤 기존 UltraVNC Repeater의 Viewer 포트로 TCP 연결을 열 예정이었다. 2026-11-08 결정(ADM-TBD-238)이 ticket 인증을 철회하고 중계를 vnc-relay로 바꾸었다. vnc-relay에는 ticket을 확인하는 기능이 없다.

ticket은 JWS 압축 형식이다. 어드민 API가 KMS(키 관리 서비스)의 P-256 서명 키로 서명하고, 전용 중계는 공개 키만 가진다. KMS는 ECDSA 서명을 DER 형식으로 돌려준다(AWS KMS Sign). 그래서 API가 JWS가 요구하는 R‖S 64바이트로 바꾼다. 서명 키는 환경(stage)마다 하나이며 키 교체 절차는 정하지 않았다.

API는 세션 만료 시각 sx가 발급 시각 iat보다 늦지 않으면 발급하지 않고 409로 답한다. ticket 원문은 DB·감사 기록·로그에 남기지 않는다.

  2. Origin이 허용 값과 다르면 403이다.
  3. 서브프로토콜 값 목록의 형식이 틀리면 400이다. 목록은 앱 고유 이름 하나와 접두어를 붙인 ticket 하나로 이루어진다.
  4. 서명·iss·aud·exp·iat를 5초의 시계 오차 안에서 확인한다. 틀리면 401이다.
  5. jti를 사용 기록에 원자적으로 쓴다. 이미 있으면 401이다. 기록은 exp 뒤 5초까지 두고, 재시작해도 유지한다. 저장에 실패하면 503이다. 기록을 잃었으면 시계를 다시 맞춘 뒤 70초 동안 모든 요청을 503으로 거절한다. 그래서 환경마다 전용 중계 인스턴스는 하나다.
  6. rh가 허용한 중계 호스트가 아니면 403이다.
  7. 101은 앱 고유 이름만 고른다. ticket 값은 응답에 되돌리지 않는다.

70초는 다음 계산과 맞는다. 기록을 잃기 전에 받아들인 ticket의 iat는 그 시각보다 최대 5초 늦을 수 있다. 여기에 수명 60초와 exp 쪽 시계 오차 5초를 더하면 70초다. 그래서 70초가 지나면 그 ticket은 모두 만료로 거절된다(추정: 원문에서 이 계산을 확인하지 않았다).

101 뒤의 동작

  • 5초 안에 Repeater의 Viewer 포트로 TCP 연결을 열지 못하면 close 4502로 끊는다.
  • 브라우저의 첫 250바이트가 ID:와 rid를 이은 값(남는 자리는 NUL로 채움)과 다르면 4403으로 끊는다. ticket을 중계 ID 하나에 묶는 장치다.
  • 120초 동안 Repeater에서 바이트가 오지 않으면 4408로 끊는다.
  • sx가 되면 4410으로 끊는다.
  • 로그에는 시각·sub·jti·결과·전송량만 남긴다.

이 close 코드들은 vnc-relay의 close 코드에 없다. vnc-relay는 4000번대 코드를 다른 뜻으로 쓴다. 05절은 이 규칙들이 vnc-relay 안에서 어디로 가는지 설명한다.

05 / 내재화 안

철회한 규칙을 vnc-relay의 검사 순서에 넣는다

내재화 안은 철회한 설계의 ticket 형식과 확인 규칙을 그대로 쓴다. 바뀌는 것은 확인하는 곳이다. 어드민 API는 지금처럼 로그인·권한·원격 지원 세션을 확인하고 ticket에 서명한다. vnc-relay는 공개 키만 가진다. 서명 키와 발급 판단은 어드민 서비스에 남는다.

vnc-relay 안에 두면 두 가지가 가능해진다. 첫째, 업그레이드 요청을 받는 프로그램이 곧 ticket을 확인하는 프로그램이다. 둘째, 짝짓기를 하는 같은 프로세스가 ticket의 rid와 sx를 안다. 그래서 철회한 설계의 101 뒤 규칙 가운데 중계 ID 대조와 세션 만료 종료를 옮길 수 있다.

오른쪽 그림은 지금 검사 순서에 새 단계를 끼운 모습이다. 순서를 정하는 원칙은 하나다. 사용 기록은 실패할 수 있는 검사를 모두 마친 뒤에 쓴다. 기록을 먼저 쓰면 뒤의 검사에서 거절된 요청도 ticket을 소비한다.

서브프로토콜에 싣는 값

브라우저는 noVNC의 wsProtocols 옵션으로 값 두 개를 보낸다(noVNC API). 예를 들면 binary와 ticket. 뒤에 JWS를 붙인 값이다. JWS 압축 형식은 base64url 문자와 점만 쓰므로 서브프로토콜 값의 문자 규칙에 맞는다. 길이는 수백 바이트이고, 요청 머리 상한 16 KiB(계약 1.1절)보다 훨씬 작다.

noVNC 1.7.0은 이 옵션이 없으면 Sec-WebSocket-Protocol 헤더를 보내지 않는다(계약 1.2절의 관찰 기록). 그래서 이 안은 vnc-relay만 바꾸어서는 동작하지 않는다. 사용처 페이지가 noVNC에 ticket을 넘기도록 함께 바뀌어야 한다.

브라우저는 제시한 값 가운데 하나를 서버가 고르지 않으면 연결을 실패로 처리한다(WHATWG WebSockets 2.2절). vnc-relay는 지금처럼 binary를 고른다. ticket 값은 응답에 되돌리지 않는다.

지금 계약은 값이 없거나 binary만 있어도 수락한다(계약 1.2절). ticket을 켠 역할에서는 이 두 경우가 거절로 바뀐다. ticket을 켜지 않은 역할의 판정은 그대로다. 계약 3절은 서브프로토콜 규칙 변경을 호환성을 깨는 변경으로 명시한다(계약 3절). 같은 절의 호환 변경 목록에는 명시적으로 설정해야 켜지는 처리가 한 항목 있다. 3절은 그 항목의 근거로 기본값에서 기존 Viewer 클라이언트의 판정이 바뀌지 않았다는 점을 적는다. ticket 확인도 기본으로 꺼 두면 같은 근거를 댈 수 있다. 하지만 ticket 확인은 그 목록에 없으므로 선례만으로는 호환 변경이 되지 않는다. 계약을 고칠 때 "명시적으로 켠 역할의 ticket 확인"을 3절의 호환 변경 목록에 함께 적으면 2.x.0이고, 적지 않으면 3.0.0이다.

서명과 클레임 확인

확인은 표 4의 순서로 한다. 서명을 먼저 검증한다. 서명이 맞지 않는 값의 클레임은 믿을 근거가 없기 때문이다. 시각 비교에는 vnc-relay 호스트의 시스템 시각을 쓴다. 그래서 발급 쪽과 vnc-relay 양쪽의 시계가 맞아야 한다.

aud는 역할마다 고정한 값 하나다. Viewer는 vnc-relay/viewer, Server는 vnc-relay/server다(사용자 결정 2026-11-10). vnc-relay는 기대값을 ticket이나 요청 헤더에서 가져오지 않는다. 경로로 고른 역할에서 정한다. 그래서 Server 역할도 ticket을 요구하면(06절) Viewer ticket을 /relay/server에 내도 401이다.

비교는 변환 없이 대소문자를 구분하는 문자열 비교다. 두 값에는 :가 없으므로 URI가 아니어도 된다(RFC 7519 2절의 StringOrURI). 표준은 aud를 배열로도 허용한다(RFC 7519 4.1.3절). 이 안은 문자열 하나만 받는다. 배열을 받으면 두 역할 값을 함께 담은 ticket이 두 경로에서 모두 통과하기 때문이다.

역할마다 aud를 나누는 것은 역할을 구분하는 여러 방법 가운데 하나다. RFC 8725 3.12절은 같은 발급자가 여러 종류의 JWT를 내면 확인 규칙이 서로 겹치지 않아야 한다고 정한다. 그 방법으로 typ, 필수 클레임, 서명 키, 발급자, aud를 나누는 방식을 예로 든다(RFC 8725 3.12절). 서명 키를 역할마다 나눌지는 정하지 않았다(표 9).

rh는 요청의 Host가 아니라 설정값과 대조한다. Host는 클라이언트가 정하는 값이고, 계약도 이 값을 라우팅에 쓰지 않는다(계약 1.1절). 설정한 이름과 대조해야 다른 중계용으로 발급한 ticket을 거른다.

sx는 exp와 따로 비교한다. exp는 sx를 넘지 않지만, exp 확인에는 5초 오차를 허용한다. 그 오차만 적용하면 sx 뒤 5초 안에 온 요청도 통과한다. 이 연결은 원격 지원 세션이 끝난 뒤에 열리고 101 직후 바로 끊긴다. 그래서 이 안은 업그레이드 때 sx를 오차 없이 비교한다(예). vnc-relay 호스트의 시계가 발급 쪽보다 빠르면 그 차이만큼 세션이 일찍 끝난다.

서명 검증에 쓸 라이브러리는 이미 있다. aws-lc-rs는 작업공간 의존성이며, 그 ECDSA_P256_SHA256_FIXED는 R‖S 고정 길이 서명을 검증한다(aws-lc-rs 문서). JWS의 ES256 서명 형식과 같다.

사용 기록을 메모리에 두는 근거와 한계

vnc-relay는 프로세스 하나로 운영하고, 대기 등록과 활성 세션을 그 프로세스의 메모리에만 둔다(ADR-0003, PRD 확정 기준 "인스턴스"). 같은 중계 ID의 Viewer와 기기는 같은 프로세스에 닿아야 짝을 이룬다. ticket의 rh는 vnc-relay 하나를 가리킨다. 그래서 사용 기록도 그 프로세스의 메모리에 두면 같은 ticket이 두 번 통과하지 못한다.

기록에는 서명 확인을 통과한 ticket만 들어간다. 위조 값으로 메모리를 채울 수 없다. 기록은 exp 뒤 5초에 지운다. ticket은 iat보다 최대 5초 이른 시각에 통과할 수 있고, exp는 iat 뒤 60초 이내다. 그래서 기록 하나는 길어야 70초 남고, 기록 수는 최근 70초 동안 통과한 업그레이드 수를 넘지 않는다.

한계는 재시작이다. 프로세스가 끝나면 기록이 사라진다. 재시작 전에 쓴 ticket이 아직 만료 전이면 다시 통과할 수 있다. 다루는 방법은 표 6의 첫 행에 비교했다.

101 뒤: 중계 ID 대조와 세션 만료

101을 보낸 뒤 vnc-relay는 초기 교환을 제한 시간 H 안에 읽는다. ticket을 싣고 온 Viewer 역할 연결에서 해석 결과가 Mode II 요청이면 그 중계 ID를 ticket의 rid와 비교한다. 중계 ID는 바이트열이 정확히 같을 때만 같은 ID다(PRD 확정 기준 "Repeater 초기 교환"). 다르면 대기 등록 전에 새 close 코드로 끊는다. 기기의 대기 연결은 영향을 받지 않는다.

Viewer 역할에 켠 ticket의 rid 대조와 sx 시각은 그 Viewer 역할 연결에만 붙는다. Server 역할에 ticket을 켜지 않으면, 같은 중계 ID로 기다리는 기기 쪽 연결은 ticket 없이 지금처럼 대기한다. Server 역할에도 켜는 경우는 06절의 Server 역할 변형이다. 이 변형도 채택하지 않았다.

ticket은 중계 ID에 묶이므로 Mode I 요청에는 대조할 값이 없다. ticket을 요구하는 역할에서 Mode I 요청을 거절할지는 정해야 한다(표 6).

sx가 되면 활성 세션을 끝낸다. vnc-relay에는 관리자 종료가 세션을 끝내는 경로가 이미 있다(07절). 관리자 종료는 같은 종료 동작을 브라우저 쪽과 기기 쪽 연결에 모두 보낸다. WS 연결은 close 4005를 받고, TCP 연결은 소켓이 닫힌다. sx 종료는 이 경로에 새 종료 원인과 close 코드를 더하는 방식이 가능하다(추정). 그러면 기기 쪽 연결도 함께 닫힌다. 짝을 이루기 전 대기 중에 sx가 지나는 경우도 같은 시각에 끊어야 규칙이 맞는다.

철회한 설계의 4502(Repeater 연결 실패)와 4408(Repeater 무응답)에 해당하는 규칙은 필요 없다. vnc-relay는 같은 프로세스에서 짝을 짓는다. 상대가 오지 않으면 기존 4001(대기 시간 초과)이, 상대 연결이 끊기면 기존 4006·4007이 쓰인다(계약 1.5절).

설정과 재로드

ticket 확인은 기본으로 꺼져 있고, 운영자가 역할마다 설정으로 켠다(사용자 지시 2026-11-11). ticket 설정이 없거나 꺼진 역할은 지금과 같게 동작한다. ticket을 실은 요청도 지금처럼 판정한다(07절). Viewer 역할과 Server 역할은 따로 켠다. 그래서 Viewer 역할에 먼저 켜고, 기기 쪽 변경이 끝난 뒤 Server 역할에 켤 수 있다(06절).

켜는 키는 설정 계약의 역할 표처럼 enabled로 두고 기본값을 false로 할 수 있다. 켜면 ticket이 필수다. ticket이 있을 때만 확인하는 방식은 ticket을 빼고 보낸 요청을 통과시키므로 보호 효과가 없다(표 6).

설정을 두는 단위는 두 가지가 가능하다. 지금 설정 계약은 WS 리스너와 WSS 리스너에 역할 표를 따로 둔다(설정 계약 1.2절). 이 구조를 따라 리스너·역할마다 켜면, 같은 역할을 두 리스너에서 받을 때 한쪽에만 켠 구성이 생길 수 있다. 그러면 다른 리스너의 같은 경로가 ticket 없는 길로 남는다. 역할마다 한 번 켜고 WS·WSS에 함께 적용하면 이 길은 생기지 않는다. 어느 쪽이든 같은 역할의 TCP 진입점은 ticket을 받지 못한다(표 6).

평문 WS 리스너에서 ticket을 켜면 ticket 원문이 암호화되지 않은 채 그 구간을 지난다. 그 구간을 관찰할 수 있는 쪽은 정상 클라이언트보다 먼저 같은 ticket을 쓸 수 있다. 사용 기록은 두 번째 사용만 막으므로, 먼저 쓴 쪽이 통과하고 정상 클라이언트는 거절된다.

지금 설정 계약은 알 수 없는 키를 config_unknown_key로 거절한다. 생략하면 지금과 같게 동작하는 새 선택 키는 호환 변경이다. 다만 새 키를 쓴 파일은 그 키를 모르는 이전 서버가 거절한다(설정 계약 3절).

공개 키 파일은 인증서처럼 경로와 내용을 재로드 대상으로 둘 수 있다(설정 계약 1.8절의 인증서 방식과 같게 둔다면, 추정). 그러면 재시작 없이 키를 바꿀 수 있다. 새 키를 더하고, 발급 쪽을 새 키로 바꾸고, 옛 키로 서명한 ticket의 수명이 지난 뒤 옛 키를 뺀다. 여러 키 가운데 하나를 고르려면 JWS 헤더에 kid가 필요하다. 철회한 설계의 헤더에는 kid가 없었다. 켜고 끄는 키를 재시작이 필요한 키로 둘지, 재로드 대상으로 둘지도 정해야 한다. 한번 정한 재로드 구분을 나중에 바꾸면 설정 계약의 호환성을 깨는 변경이 된다(설정 계약 3절).

06 / Server 역할로 넓히기

기기 쪽 연결에도 ticket을 요구하려면

05절은 브라우저 쪽 Viewer 역할에 ticket을 켠 경우를 설명했다. 기기 쪽 연결은 Server 역할이다. Server 역할에 ticket을 켜지 않으면 이 연결은 지금처럼 출발지 IP 허용 목록과 중계 ID만 거친다. 중계 ID는 접속 권한의 증거로 쓰면 안 된다(중계와 매칭 스펙 5절).

Mode II에서 같은 중계 ID·같은 역할의 연결이 둘이면 먼저 온 연결이 남고 나중 연결은 거절된다(중계와 매칭 스펙 3.3절 4항). 그래서 기기보다 먼저 같은 중계 ID로 Server 역할에 등록한 연결이 있으면, 실제 기기는 거절되고 브라우저는 그 연결과 짝을 이룬다. Viewer ticket은 이 경우를 막지 못한다. ticket을 확인하는 쪽이 Viewer 역할뿐이기 때문이다.

VNC 비밀번호도 이 경우를 막지 못한다. VNC 인증에서는 Server가 무작위 값(challenge)을 보내고, Viewer가 비밀번호로 그 값을 암호화해 돌려준다(RFC 6143 7.2.2절). 이 방식으로 기기는 Viewer가 비밀번호를 아는지 확인한다. 하지만 Viewer는 상대가 실제 기기인지 확인하지 못한다. 또 RFB 프로토콜은 데이터의 관찰과 변조를 막지 않는다(RFC 6143 9절). 지금 기기 쪽 TCP 구간은 암호화되지 않는다.

Server 역할 변형은 Server 역할에도 ticket을 켜서 기기 쪽 연결에 ticket을 요구한다. 그러면 ticket을 켠 리스너에서는 사용처가 발급한 ticket이 없는 연결이 기기 자리에 등록하지 못한다. 이것이 ticket이 더하는 효과다. 기기 쪽 구간의 암호화는 이와 별개다. ticket을 실으려면 기기가 WebSocket으로 연결해야 하고, 그때 WSS를 쓰면 TLS가 그 구간의 관찰과 변조를 막는다. 이 변형도 아무도 채택하지 않았고 구현하지 않았다.

vnc-relay 쪽: 같은 검사를 역할별로 쓴다

vnc-relay는 WS·WSS의 Server 역할을 이미 받는다. 경로 /relay/server가 Server 역할을 고른다(계약 1.7절). 지금은 이 역할에서도 ticket을 확인하지 않는다. Server 역할의 ticket도 기본으로 꺼져 있고 Viewer 역할과 따로 켠다. 그래서 기기 쪽 변경이 끝날 때까지 Server 역할만 꺼 둘 수 있다. 켜면 그림 5의 검사 순서를 그대로 쓰고, 고른 역할의 ticket 설정으로 확인할 수 있다(추정). 코드에서 이 자리는 07절에 있다.

기기 쪽: droidVNC-NG에는 ticket을 실을 자리가 없다

droidVNC-NG는 Android용 오픈소스 VNC Server 앱이다. 다른 앱은 Intent로 이 앱을 제어할 수 있다. Intent는 Android 앱 사이에서 동작을 요청하는 메시지이고, extra라는 이름과 값의 쌍을 담는다. 리피터 연결 요청 ACTION_CONNECT_REPEATER의 extra는 접근 키·주소·포트·중계 ID·요청 ID·재연결 횟수다(droidVNC-NG Intent 인터페이스). URL·TLS·ticket을 받는 extra는 없다.

연결 경로도 TCP뿐이다. MainService.java는 이 요청을 받으면 작업 스레드에서 네이티브 함수 vncConnectRepeater에 주소·포트·중계 ID를 넘긴다(693~719행). 네이티브 함수는 JNI로 부르는 C 함수다. JNI는 Java 코드가 C 함수를 부르는 방식이다. 이 함수는 LibVNCServer의 rfbUltraVNCRepeaterMode2Connection을 부른다(droidvnc-ng.c 527~549행). LibVNCServer는 droidVNC-NG가 쓰는 VNC 서버 C 라이브러리다.

LibVNCServer의 이 함수는 TCP 소켓을 열고, ID:와 중계 ID를 이은 250바이트를 보낸 뒤, 그 소켓으로 VNC 클라이언트를 만든다(rfbserver.c 283~335행). 소켓은 rfbConnectToTcpAddr가 여는 TCP 소켓이다(sockets.c 1267행 이하). 이 경로에는 TLS나 WebSocket 처리가 없다.

TCP 초기 교환에도 ticket을 넣을 수 없다. 초기 요청은 250바이트 고정 형식이고 인증 필드가 없다(Repeater 초기 교환 계약 1.2절). 그래서 Server ticket을 쓰려면 기기 쪽에 WSS 클라이언트가 있어야 한다. 방법은 둘이다. A는 기기 앱에 로컬 터널을 두고, B는 droidVNC-NG를 고친다(그림 7).

사용처의 기기 앱은 원격 지원 세션 정보를 받으면 droidVNC-NG에 이 Intent를 보낸다. 주소·포트·중계 ID는 넘기지만 요청 ID와 재연결 횟수는 넘기지 않는다(비공개 기기 앱 코드). 그래서 지금은 droidVNC-NG의 자동 재연결을 쓰지 않는다.

A. 기기 앱의 로컬 터널

A는 droidVNC-NG를 바꾸지 않는다. 기기 앱이 droidVNC-NG의 TCP 연결을 받아 WSS 연결로 옮긴다. 루프백 주소(127.0.0.1)는 같은 기기 안에서만 닿는 주소다. 흐름은 다음과 같다(예).

  1. 기기 앱이 루프백 주소의 빈 포트에 수신 소켓을 연다.
  2. droidVNC-NG에 ACTION_CONNECT_REPEATER를 보낸다. 주소와 포트는 그 수신 소켓을 가리킨다. 중계 ID는 지금과 같다.
  3. 수신 소켓은 첫 연결 하나만 받고 바로 닫는다. 첫 250바이트가 ID:와 중계 ID를 이은 값인지 확인한다.
  4. 기기용 API에서 Server ticket을 받는다.
  5. /relay/server로 WSS 업그레이드 요청을 보낸다. 서브프로토콜 값은 binary와 ticket이다.
  6. 101을 받으면 3단계의 250바이트를 먼저 보낸다. 그 뒤에는 두 연결의 바이트를 그대로 넘긴다.
  7. 한쪽이 닫히면 다른 쪽도 닫는다. 원격 지원 세션을 멈추거나 교체할 때도 터널을 닫는다.

ticket은 기기 앱 밖으로 나가지 않는다. 터널은 연결 시도마다 새 ticket을 받으므로 일회용 규칙과 맞는다. Android 앱은 OkHttp 같은 라이브러리로 WebSocket 클라이언트를 만들 수 있다. OkHttp 5.3.0은 호출자가 넣은 요청 헤더를 유지한 채 업그레이드 요청을 만든다(RealWebSocket.kt 159~167행). 그래서 Sec-WebSocket-Protocol에 ticket을 실을 수 있다.

A에 남는 점은 다음과 같다.

  • 루프백 포트에는 같은 기기의 다른 앱도 접속할 수 있다. 첫 연결 하나만 받고 첫 250바이트를 확인하면 범위가 줄어든다. 다른 앱이 droidVNC-NG보다 먼저 접속하는 경우는 남는다.
  • droidVNC-NG가 알리는 연결 성공은 루프백 연결의 성공이다. droidVNC-NG는 TCP 연결과 ID 전송이 끝나면 성공으로 본다(droidvnc-ng.c 543~546행, MainService.java 707~710행). vnc-relay까지의 연결 결과는 터널이 판단해야 한다.
  • 터널은 기기 앱 프로세스 안에 있다. 앱이 끝나면 원격 지원 연결도 끊긴다.
  • 흐름 제어가 필요하다. OkHttp는 보낼 대기열이 16 MiB를 넘으면 연결을 close 1001로 닫는다(RealWebSocket.kt 446~449·684행). 터널은 대기열이 클 때 droidVNC-NG 쪽 읽기를 멈춰야 한다.

B. droidVNC-NG 수정

B는 droidVNC-NG가 직접 WSS로 연결하게 고친다. 원 저장소의 코드를 고친 수정본(포크)을 만들어 기기에 설치하는 방식이다. 기기 앱은 Server ticket을 받아 Intent로 넘긴다. droidVNC-NG 3e5f27e(2.22.2) 기준으로 바꿀 곳은 다음과 같다.

  • 연결 요청 처리(MainService.java 693~719행)가 WSS 주소와 ticket을 담은 새 extra를 받는다.
  • WebSocket 클라이언트를 더한다. 지금 의존성에는 네트워크 라이브러리가 없다(app/build.gradle 143~154행).
  • 네이티브 쪽에 연결된 소켓을 넘기는 JNI 함수를 새로 둔다. LibVNCServer의 공개 함수 rfbNewClient는 이미 연결된 소켓으로 VNC 클라이언트를 만든다(rfb.h 843행). Java 쪽에서 WSS를 열고, 소켓 쌍의 한쪽을 이 함수에 넘기는 방식이 가능하다(추정). 소켓 쌍은 서로 연결된 소켓 두 개이며, 한쪽에 쓴 바이트를 다른 쪽에서 읽는다. 이 방식이면 droidVNC-NG 안에 A의 터널과 같은 부분이 생긴다.
  • 재연결용 Intent를 거르는 허용 목록(MainService.java 880~891행)에 새 extra를 더한다. 더하지 않으면 재연결 Intent에서 그 값이 빠진다.

B에서 주의할 점은 다음과 같다.

  • 재연결: 지금 기기 앱은 요청 ID와 재연결 횟수를 넘기지 않으므로 droidVNC-NG의 자동 재연결이 꺼져 있다. 기기 앱이 이 값을 넘겨 재연결을 켜면, droidVNC-NG는 연결이 끊겼을 때 처음 받은 Intent를 다시 보낸다(837~876행). 네트워크가 돌아올 때도 같다(163~193행). 그 Intent의 ticket은 이미 쓰였으므로 거절된다. 그래서 재연결을 켜려면 재연결 때 기기 앱에서 새 ticket을 받는 경로를 더해야 한다. 재연결을 끈 채로 두면 이 문제는 생기지 않는다. 이때는 기기 앱이 새 ticket으로 Intent를 다시 보낸다(예).
  • 배포: Android는 새 버전과 설치된 버전의 인증서가 같을 때 업데이트를 허용한다(Android 앱 서명). 수정본은 원래 배포본과 다른 키로 서명한다. 그래서 같은 패키지 이름이면 기존 앱을 지우고 다시 설치해야 한다. 이때 접근 키 같은 앱 데이터가 지워진다. 새 패키지 이름을 쓰면 기기 앱이 부르는 패키지 이름도 바꿔야 한다.
  • 버전: 포크의 기준 버전과 기기에 설치된 버전이 다르면 그 사이의 변경도 검증해야 한다.
  • 라이선스: droidVNC-NG는 GPL-2.0이다(COPYING). 수정본을 배포하면 GPL-2.0 3절의 소스 제공 조건을 따라야 한다. 기기 앱은 Intent로만 연결하므로 별개 프로그램으로 볼 수 있다(추정, 법률 검토 아님).
  • 원 저장소 제안: 이 기능을 droidVNC-NG 원 저장소에 제안할 수 있다. 받아들여지면 포크를 유지하지 않아도 된다. 받아들일지는 알 수 없다.

두 방법에 공통인 조건

vnc-relay에는 두 방법이 같은 WSS 연결로 보인다. 그래서 vnc-relay와 기기용 API의 변경은 같고, 기기마다 다른 방법을 써도 된다. 다음 조건도 두 방법에 같다.

  • 역할 묶음: Server ticket은 Server 역할에서만 통과해야 한다. Viewer ticket을 기기 쪽에 다시 쓰지 않는다.
  • 받는 시점: 기기는 연결 직전에 ticket을 받아야 한다. 사용처 기록에 따르면 정상 기기도 세션을 만든 뒤 약 70초까지 중계에 접속하지 않을 수 있다(사용처 결정 ADM-TBD-242의 근거). 세션을 만들 때 발급한 60초 수명의 ticket은 그 사이에 만료될 수 있다.
  • 일회용: 연결 시도마다 새 ticket을 쓴다. 재시도에도 새 ticket이 필요하다.
  • TCP Server 진입점: 켜 두면 ticket 없이 같은 중계 ID에 Server로 등록하는 경로가 남는다. 그래서 끄거나 같은 수준으로 좁혀야 효과가 생긴다. TCP로 접속하는 기기가 남아 있는 동안에는 끌 수 없다.
  • 중계 ID: 중계 ID를 길게 하거나 무작위로 만드는 것은 별도의 완화책이다. ticket 확인을 대신하지 않는다(중계와 매칭 스펙 5절).
  • 바뀌는 기준: 표 5의 기준이 Server 역할에도 같은 방식으로 바뀐다. 사용처 쪽에서는 API 계약 6.4.1·6.4.2절(비공개)이 바뀐다. 6.4.2절은 지금 "기기의 접속 방식과 §6.4.1의 기기 전달 형식은 바꾸지 않는다"고 정한다.

07 / 코드에서 따라가기

지금 코드에서 내재화 안이 손댈 자리

검사 순서의 기준은 WebSocket 진입점 모듈 설계의 검사 순서다. 아래는 지금 코드의 사실과, 내재화 안이 그 위치에서 할 일을 나눠 적었다. "내재화 안"과 "Server 역할 변형"으로 시작하는 문장은 모두 추정이다.

  1. crates/adapters/src/websocket.rs의 upgrade(344~392행)가 요청 머리를 읽고 check_upgrade(308~339행)를 부른다. check_upgrade는 현재 설정으로 check를 실행한 뒤 클라이언트 주소를 선택한 역할의 허용 목록과 다시 대조한다. 내재화 안: ticket 확인(그림 5의 6)은 설정·공개 키·현재 시각만 있으면 되는 계산이다. 그래서 check 쪽에 둘 수 있다. upgrade.rs는 검사와 응답 문장에 소켓이 없어 단위 테스트로 바로 확인하는 모듈이다.
  2. upgrade.rs의 check(151~256행)는 끝에서 서브프로토콜 값을 모은다(코드 1). 내재화 안: 접두어로 ticket 값을 골라 확인하고, rid·sx·jti·sub를 ValidUpgrade에 담아 넘긴다.
  3. upgrade는 응답 바이트를 먼저 만든다. 그다음 업그레이드 제한 시간 U가 지났는지 마지막으로 보고(367행) 응답을 쓴다(375행). 내재화 안: 사용 기록 쓰기(그림 5의 8)는 이 마지막 확인 뒤, 응답 쓰기 앞이 가장 늦은 자리다. 여기서 jti가 이미 있으면 101 대신 거절 응답을 써야 하므로 응답을 고르는 순서가 바뀐다.
  4. upgrade.rs의 switching_protocols(260~271행)는 binary를 제시한 요청에만 Sec-WebSocket-Protocol: binary를 넣는다. ticket을 되돌리지 않으므로 바뀔 필요가 없다.
  5. 101 뒤 websocket.rs의 connection(197~280행)은 handle_connection으로 초기 교환을 H 안에 읽고, dispatch로 짝짓기와 중계를 넘긴다(코드 2). 그 사이의 값이 PreparedConnection이다. 이 형은 해석한 요청을 request()로 보여 주고, 다음 단계를 호출자에게 맡긴다. 내재화 안: rid 대조는 이 두 호출 사이에 들어갈 수 있다.
  6. 관리자 종료는 RelayRuntime의 request_terminate(crates/app/src/relay.rs 689~730행)가 세션 제어에 종료 명령을 넣는 방식이다. 세션 쪽의 close_once(crates/app/src/relay/session.rs 592~611행)는 같은 RelayCloseAction을 두 연결에 보낸다. WS 쪽 close 코드는 crates/adapters/src/websocket_stream.rs(885~920행)가 그 값에서 고른다. TCP 쪽은 소켓을 닫는다(crates/adapters/tests/tcp_target.rs). 내재화 안: sx 종료와 rid 불일치에는 새 종료 동작과 새 코드가 필요하다.
  7. websocket.rs의 refuse(409~429행)는 거절 사유와 주소를 운영 로그에 남긴다. 헤더 값은 Origin 거절일 때의 Origin 원문만 남긴다. 내재화 안: ticket 거절 사유를 더하되 원문은 남기지 않는다. 남길 수 있는 값은 철회한 설계처럼 jti와 sub다.
  8. upgrade.rs의 check는 경로로 역할과 그 역할의 설정을 고른다(188~192행). websocket.rs의 connection은 역할과 관계없이 101 뒤의 연결을 handle_connection과 dispatch에 넘긴다(258~265행). 그래서 Server가 101 뒤 먼저 보내는 ID:도 Viewer의 초기 교환과 같은 경로를 지난다. 중복 ID 거절은 dispatch의 짝짓기 단계에서 정한다(crates/app/src/relay/matching.rs 245~249행). Server 역할 변형: ticket 설정은 check에서 역할별로 고를 수 있다. rid 대조는 Viewer와 같은 자리에 둘 수 있다. 사용 기록을 업그레이드 때 쓰면 중복으로 거절된 연결도 ticket을 소비한다.

지금은 Cookie와 Authorization도 접근 판정에 쓰지 않는다(계약 1.1절 표의 "그 밖의 헤더" 행). 따라서 vnc-relay에는 ticket이나 로그인 쿠키를 확인할 자리가 없다. 내재화 안은 이 자리를 서브프로토콜 값으로 새로 만든다.

09 / 오해와 선택

자주 하는 오해와 선택의 대가

"서명한 ticket이면 일회용이다."
서명은 위조만 막는다. 같은 값을 두 번 내면 두 번 모두 서명 검증을 통과한다. JWT 표준도 jti를 재사용 방지에 쓸 수 있는 식별자로만 정한다(RFC 7519 4.1.7절). 일회용은 확인 지점의 사용 기록에서 나온다.
"Origin 검사나 중계 ID가 인증 역할을 한다."
둘 다 인증 수단이 아니다(계약 1.3절, 용어집).
"지금 vnc-relay에 ticket을 실으면 거른다."
지금 vnc-relay는 binary 외의 값을 판정에 쓰지 않는다(07절). 내재화 안이 구현돼도 ticket을 켜지 않은 역할은 같다. 그 역할은 ticket을 실은 요청도 지금처럼 101로 수락한다.
"기본으로 꺼 두는 기능이면 기준 문서를 바꾸지 않아도 된다."
바꿔야 한다. PRD 확정 기준은 중계 접근을 "관리자 로그인·접속 토큰과 분리"한다고 정하고, ADR-0002는 WS 전용 토큰을 대안에서 제외했다(표 5). 기본값이 바꾸는 것은 기존 배포의 동작과 계약 호환성 판단이다. 기준 문서와 맞지 않는 점은 그대로 남는다.
"vnc-relay가 ticket을 확인하면 모든 접속 경로가 보호된다."
ticket을 실을 자리는 WebSocket 업그레이드 요청뿐이다. TCP Viewer 진입점의 초기 교환은 250바이트 고정 형식이고 인증 필드가 없다(Repeater 초기 교환 계약, ADR-0002 1절). TCP Viewer 진입점이 열려 있으면 허용 목록 안의 주소에서 같은 중계 ID에 ticket 없이 닿는다.
"vnc-relay가 401로 거절하면 페이지가 원인을 안다."
모른다. WebSocket API는 101 전의 실패를 close 1006 하나로만 알린다(WHATWG WebSockets 4절). 페이지는 새 ticket을 받아 다시 시도하는 것 외에 원인별로 처리할 수 없다.
"ticket이 있으면 권한 회수가 바로 반영된다."
확인은 업그레이드 때 한 번이다. 내재화 안은 sx에 끊지만, 그 전의 권한 회수는 반영하지 않는다.
"사용 기록을 메모리에 두면 일회용이 깨진다."
평소에는 깨지지 않는다. 상태를 가진 프로세스가 하나이기 때문이다(ADR-0003). 깨질 수 있는 때는 재시작이다. 그래서 재시작 규칙이 따로 필요하다(표 6).
"ticket은 수명이 짧으니 원문이 로그에 남아도 괜찮다."
ticket은 가진 사람이면 누구나 쓸 수 있는 값이다. 수명 안에 다른 사람이 먼저 쓰면 그 사람이 통과하고, 정상 사용자는 거절된다. 그래서 철회한 설계와 내재화 안 모두 원문을 로그에 남기지 않는다.
"WS·WSS Server 역할이 있으니 droidVNC-NG 기기도 바로 ticket을 쓸 수 있다."
droidVNC-NG의 리피터 연결은 TCP뿐이고 ticket을 실을 자리가 없다(06절). 기기 쪽에 WSS 클라이언트가 먼저 있어야 한다. 06절의 A나 B가 그 방법이다.
"Viewer ticket과 VNC 비밀번호가 있으면 기기 쪽 연결도 확인된다."
둘 다 기기 쪽 연결을 확인하지 않는다. Viewer ticket은 Viewer 역할만 보고, VNC 인증은 기기가 Viewer를 확인하는 방식이다(RFC 6143 7.2.2절). 기기 쪽 연결을 확인하려면 Server ticket이 따로 있어야 한다.
표 13. 선택에 따른 이점과 제약. 어느 선택도 이 저장소의 기준을 바꾸지 않았다.
선택이점제약
ticket 없이 출발지 IP 허용 목록(현재 기준)구성 요소가 늘지 않는다. 기존 UltraVNC와 호환된다.허용한 IP 안의 사용자를 구분하지 못한다. 전체 허용 항목이면 주소 검사가 아무도 거르지 않는다.
전용 중계가 확인(철회한 설계)중계 ID·중계 호스트와 묶고, 세션 만료 때 끊을 수 있다.중계 프로그램을 하나 더 운영한다. 사용 기록을 재시작 뒤에도 유지해야 했다. 중계를 vnc-relay로 바꾸면서 철회했다.
vnc-relay가 확인(내재화 안)프로그램이 늘지 않는다. 중계 ID와 묶고 세션 만료 때 끊을 수 있다. 짝짓기 상태와 같은 메모리에 사용 기록을 둔다. 켜지 않은 배포는 지금과 같다.PRD 확정 기준과 ADR-0002를 다시 정해야 한다. WebSocket 계약은 3절 문구대로면 호환성을 깨는 변경이고, 3절을 고쳐야 호환 변경이 된다. 재시작 규칙과 키 교체를 새로 운영한다. 같은 역할의 TCP 진입점과 ticket을 켜지 않은 리스너는 보호하지 못한다. 평문 WS 구간에서는 ticket이 노출된다.
vnc-relay가 두 역할을 확인(Server 역할 변형)ticket 없는 WS·WSS 연결이 기기 자리에 등록하지 못한다. 기기 쪽 구간을 WSS로 옮기면 TLS로 암호화된다. 이 암호화는 ticket과 별개의 효과다.droidVNC-NG 기기에는 기기 쪽 변경(A 또는 B)이 필요하다. 기기용 API가 기기를 인증해 ticket을 발급해야 한다. TCP Server 진입점을 끄거나 좁히기 전에는 효과가 없다.

내재화 안에는 정하지 않은 질문이 남아 있다. 기본으로 꺼 두고 설정으로 켠다는 것은 검토 전제다(사용자 지시 2026-11-11). PRD 확정 기준의 "접속 토큰과 분리"를 바꿀 것인가. WebSocket 계약 3절을 고쳐 호환 변경으로 낼 것인가. 표 6의 선택 10개를 어떻게 정할 것인가. 공개 키 파일의 형식과 교체 절차는 무엇인가. 운영 로그와 관리 API에 무엇을 더할 것인가. Server 역할에 켜려면 표 9의 다섯 선택을 어떻게 정할 것인가. 이 저장소에서는 PRD 확정 기준과 새 ADR이 이 질문을 다룬다. 사용처 쪽에서는 보호 강화 검토(ADM-TBD-239)가 열려 있다.

11 / 확인 질문

이해했는지 확인하기

서명만 확인하고 사용 기록이 없는 vnc-relay가 같은 ticket을 두 번 받으면?

두 번 모두 101로 수락한다. 사용 기록이 없으므로 두 번째 요청을 구분할 근거가 없다.

사용 기록 쓰기를 IP 재검사보다 먼저 하면 무엇이 달라지는가?

IP 재검사의 403으로 거절된 요청도 ticket을 소비한다. 맨 뒤에 쓰면 기록 뒤에 남는 실패는 101 쓰기 실패 같은 연결 문제뿐이다.

ticket의 rid와 다른 중계 ID를 초기 교환에 보내면?

101 뒤 초기 교환에서 새 close 코드로 끊긴다. ticket은 이미 사용됐고, 기기의 대기 연결은 그대로다.

vnc-relay가 재시작된 직후, 재시작 전에 쓴 ticket을 다시 내면?

재시작 규칙에 따라 다르다. 표 6 (가)라면 iat가 기동 시각 + 5초 이하이므로 거절된다. 아무 규칙이 없으면 만료 전까지 다시 통과한다.

Viewer 역할만 확인하는 내재화 안이 막지 못하는 것 세 가지는?

TCP Viewer 진입점으로 같은 중계 ID에 들어오는 연결, 기기보다 먼저 같은 중계 ID로 Server 역할에 등록하는 연결, 그리고 sx 전의 권한 회수다. 둘째는 06절의 Server 역할 변형이 다룬다.

Server ticket을 켰는데 TCP Server 진입점이 열려 있으면?

ticket 없는 TCP 연결이 같은 중계 ID에 Server로 등록할 수 있다. 그래서 TCP Server 진입점을 끄거나 좁히기 전에는 Server ticket의 보호 효과가 없다.

WSS Viewer에만 ticket을 켜고 WS 리스너의 Viewer 역할은 ticket 없이 열어 두면?

WS 리스너의 /relay/viewer로 ticket 없이 같은 중계 ID에 닿는다. 그래서 WSS의 ticket은 보호 효과가 없다. 설정을 역할 단위로 두거나 이런 구성을 경고하는 선택은 표 6에 있다.

B에서 droidVNC-NG의 자동 재연결을 켜면?

재연결은 처음 받은 Intent를 다시 보낸다. 그 Intent의 ticket은 이미 쓰였으므로 거절된다. 그래서 새 ticket을 받는 경로가 필요하다. 지금 기기 앱처럼 재연결을 끄면 이 문제는 생기지 않는다.
