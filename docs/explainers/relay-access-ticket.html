VNC Relay 해설 · WebSocket 중계 접속

접속 ticket은
무엇을 확인하는가

vnc-relay는 설정으로 켠 WS·WSS 역할에서 접속 ticket을 확인한다. 발급 쪽이 서명한 ticket 하나를 한 역할과 한 중계 ID에 묶고, 같은 ticket의 두 번째 사용을 막는다. 101 뒤에는 중계 ID를 대조한다. 세션 만료 시각 sx가 있으면 그 시각에 연결을 끝낸다. 기본은 꺼짐이다. TCP 진입점과 VNC 자체 인증은 이 기능으로 바뀌지 않는다.

01 / 중계 ID는 접속 권한의 증거가 아니다

중계 ID는 접속 권한의 증거가 아니다

브라우저 noVNC는 /relay/viewer로 업그레이드를 요청한다. 101 뒤 초기 교환에서 중계 ID를 보낸다. 같은 ID의 Server 연결이 기다리면 두 연결이 Mode II 활성 세션이 된다.

중계 ID는 짝을 찾는 값이지 비밀값이 아니다. 출발지 IP 허용 목록은 주소를 제한하지만 같은 허용 IP 뒤의 개별 사용자를 구분하지 못한다. Origin은 브라우저 페이지의 출처를 검사한다. Origin 헤더가 없으면 그 검사만 생략한다. IP 검사와 켠 역할의 ticket 확인은 유지한다(계약 1.3절).

ticket은 발급 쪽이 허락한 역할·중계 ID의 접속인지 확인하는 추가 수단이다. 발급 쪽의 권한 정책은 외부 책임이다. vnc-relay는 서명과 계약의 값을 검사할 뿐, 사용자의 로그인이나 VNC 비밀번호를 대신 확인하지 않는다.

03 / 발급부터 짝짓기까지

발급부터 짝짓기까지

발급 쪽은 자신의 정책에 따라 ticket을 발급한다. 브라우저는 그 값을 noVNC에 넘긴다. vnc-relay는 ticket을 확인하고 사용 기록을 쓴 뒤 101로 수락한다. 초기 교환의 중계 ID까지 맞으면 대기 등록·매칭으로 이어진다.

그림 3은 Viewer 확인을 켠 예다. 기기 쪽 연결은 이미 대기한다고 가정한다. 그림의 속도는 설명용이며 실제 지연이나 처리량이 아니다.

직접 재생하거나 이전·다음으로 한 단계씩 볼 수 있다.

04 / 업그레이드 확인과 연결 수명

업그레이드 확인과 연결 수명

ticket 확인은 기존 업그레이드 검사를 대신하지 않는다. 요청·경로·Origin·서브프로토콜 검사를 먼저 통과해야 한다. ticket 확인 뒤에도 업그레이드 직전 IP 검사가 남는다. 그 검사까지 통과한 뒤 사용 기록을 쓴다.

사용 기록은 ticket 확인과 다르다. 서명 확인은 허가값이 바뀌지 않았는지 본다. 사용 기록은 같은 허가값을 다시 내는지 본다. 기록이 생긴 뒤의 101 전송이나 초기 교환 실패는 기록을 되돌리지 않는다.

그림 4는 수락과 TLS도 포함한 요약이다. 정확한 업그레이드 판정 순서는 계약 1.1절을 따른다. 연결 상한과 TLS·업그레이드 제한 시간 U도 그대로 적용한다.

클라이언트가 보내는 값

클라이언트는 binary와 ticket.<JWS>를 함께 제시한다. 접두어 ticket.는 소문자다. JWS는 패딩 없는 base64url 세 부분이다. 요청 머리 전체 상한 16 KiB가 적용된다(계약 1.9.1절).

브라우저 noVNC는 wsProtocols로 두 값을 넘긴다. 페이지도 이 값을 준비해야 한다. vnc-relay는 응답에서 binary만 고른다. ticket 원문은 응답·운영 로그·진단·관리 API에 쓰지 않는다.

Sec-WebSocket-Protocol: binary, ticket.<JWS>

위 줄은 형식 설명이다. <JWS>는 발급 쪽이 서명한 실제 값으로 바꾼다.

사용 기록과 재시작

사용 기록은 WS·WSS가 함께 쓰는 프로세스 메모리에 있다. 같은 (역할, jti)의 확인과 쓰기는 한 잠금 안에서 이뤄진다. 동시에 두 요청이 와도 하나만 기록한다. 이는 단일 인스턴스·메모리 상태 결정을 따른다.

기록은 exp + 5에 만료한다. 실제 메모리 정리는 다음 기록 쓰기 때 만료 항목을 지우는 방식이다. 따라서 더는 요청이 없으면 만료 항목이 메모리에 남을 수 있다. 개수 상한은 없다. 서명을 통과한 ticket만 기록하며, 아직 재사용 가능한 기록의 시간 범위는 최대 수명 + 10초다(계약 1.9.4절).

재시작하면 기록이 사라진다. 대신 iat ≤ 기동 시각 + 5인 ticket을 거절한다(사용자 결정 2026-11-11(Q201)). 미사용 ticket도 이 조건에 걸리면 거절한다. 발급 쪽과 vnc-relay의 시계를 5초 안으로 맞추고, 기동 기준을 넘는 새 ticket을 받아야 한다. 재로드·켜고 끄기·키 교체는 기록을 지우지 않는다.

101 뒤: 중계 ID와 종료 시각

초기 교환 문법·모드 검사를 모두 통과한 뒤 rid를 대조한다. 실패하면 Close 4012로 닫고 대기 등록이나 대상 연결을 하지 않는다. 같은 ID로 기다리던 상대는 그대로 남는다. ticket은 이미 소비됐다.

ticket을 켠 Viewer에서는 Mode I를 거절한다(사용자 결정 2026-11-11(Q203)). mode1.enabled = false이면 기존 Close 1008 mode_disabled가 먼저다. true이면 문법 검사 뒤 Close 4012다. 어느 경우든 대상에 연결하지 않는다.

exp는 접속 시점의 수명이다. 이미 열린 연결을 끊는 시각은 선택 클레임 sx다. 101 직후 남은 시간을 단조 시각의 기한으로 바꾼다. 이후 벽시계 변경이나 재로드는 그 기한을 바꾸지 않는다. 초기 교환·대기 중 기한이 먼저 오면 Close 4013으로 끝낸다. 기존 H·W 기한과 같으면 기존 시간 초과가 우선한다.

활성 세션의 만료는 새 데이터 수락을 멈추고 WS·WSS에 Close 4013을 보낸다. 상대가 TCP이면 소켓을 닫는다. Close 응답을 E까지 기다린 뒤 정리한다. 남은 데이터 전달은 보장하지 않는다. 종료 원인은 session_expired이며 활성 세션만 최근 종료 목록에 오른다. 양쪽에 sx가 있으면 이른 기한을 쓴다. 없으면 ticket은 종료 시각을 정하지 않는다(계약 1.9.5절).

설정·재로드·경고

[relay.ticket.viewer]와 [relay.ticket.server]는 각 5개 키를 가진다. enabled의 기본값은 false다. 켜면 issuer·relay_host·public_keys_file이 필수다. 최대 수명 max_lifetime_secs는 기본 60초, 범위 10~600초다(사용자 결정 2026-11-11(Q212)). 시계 오차 5초는 설정 키가 아니다.

같은 역할의 WS·WSS에는 하나의 ticket 설정이 적용된다. TCP가 함께 켜져 있으면 ticket_tcp_bypass, 평문 WS에 그 역할이 켜져 있으면 ticket_plaintext_ws를 경고한다. 경고는 시작·재로드를 거절하지 않는다. 재로드 경고는 그 역할의 ticket enabled가 바뀔 때 다시 쓴다. 평문 WS는 믿을 수 있는 망 안에서만 쓴다. 원문을 본 사람이 먼저 쓰는 공격은 일회용 기록으로 막지 못한다.

공개 키 파일은 64 KiB 이하 JWKS이며 P-256 공개 키 1~16개를 담는다. kid는 고유해야 한다. 개인키 멤버 d는 받지 않는다. 두 역할을 함께 켜고 같은 공개 키를 넣으면 ticket_keys_invalid다. 시작에서는 바인드 전에 종료 코드 3으로 끝낸다. 재로드에서는 후보 전체를 거절하고 기존 설정·키를 유지한다.

ticket 10개 키는 모두 재로드 대상이다. 관리 API는 공개 키 파일 경로 2개를 뺀 8개를 편집한다. 전체 재로드 대상은 43개, 편집 대상은 37개다. 새 업그레이드부터 적용하고 기존 연결의 ID·만료 기한·사용 기록은 유지한다(설정 계약 1.8절).

설정 표 예시 보기
# 해당 역할의 WS·WSS에 함께 적용한다.
[relay.ticket.viewer]
enabled = true
issuer = "issuer.example/prod"

public_keys_file = "keys/viewer-ticket.jwks"

역할·리스너·공개 키를 따로 준비해야 하는 설정 조각이다. 전체 설정 파일은 아니다. 상대 경로는 설정 파일의 디렉터리를 기준으로 푼다.

키 교체는 새 공개 키 추가 → 발급 쪽의 서명 키 전환 → 최대 수명 + 10초 뒤 옛 공개 키 제거 순서다(설정 계약 1.11절). 운영 절차는 운영 안내 3.10절에 있다.

05 / Server 역할도 따로 확인한다

Server 역할도 따로 확인한다

Mode II는 같은 ID의 같은 역할이 먼저 등록하면 그 연결을 유지한다. 뒤에 온 같은 역할은 Close 4004 duplicate_id로 거절한다. 기존 연결은 교체하지 않는다(중계 스펙 3.3절). 그러므로 허용 주소의 다른 연결이 기기보다 먼저 Server로 등록하면 실제 기기가 거절될 수 있다. Viewer ticket만으로는 Server 등록 권한을 확인하지 못한다.

Server 확인을 켜면 기기 쪽 WS·WSS 클라이언트가 /relay/server에 binary와 Server ticket을 보낸다. vnc-relay는 Server 설정·공개 키와 aud = vnc-relay/server를 써서 같은 업그레이드 검사를 한다. Viewer ticket을 대신 내면 401이다. 101 뒤 Server는 시작 바이트를 기다리지 않고 ID: 초기 요청을 먼저 보낸다. vnc-relay는 그 ID를 rid와 대조한 뒤 등록·매칭한다.

표 6. 두 역할의 ticket 차이.

TCP 초기 교환에는 ticket 자리가 없다

초기 요청은 정확히 250바이트다. Mode II 값은 ID:<중계 ID>이며 남는 곳은 NUL로 채운다. 인증 필드는 없다(초기 교환 계약 1.2절). 채움 바이트에 ticket을 넣어도 vnc-relay는 읽지 않는다.

따라서 TCP만 쓰는 VNC Server를 ticket으로 보호하려면 기기 쪽에 WS·WSS를 쓸 수 있는 클라이언트나 로컬 터널이 필요하다. 이 구성요소가 연결 시도마다 새 Server ticket을 받아 업그레이드에 싣고 초기 교환·스트림·종료를 전달해야 한다. 발급 쪽과 클라이언트의 의무는 계약 1.9.7절을 따른다.

같은 역할의 TCP 진입점을 계속 열면 그 경로에는 ticket 확인이 없다. Server 확인을 켜는 것만으로 모든 Server 연결을 보호했다고 판단하면 안 된다. 또 ticket은 허가된 연결의 역할·ID를 확인할 뿐, 기기의 전체 소프트웨어나 VNC 끝점의 신원을 증명하지 않는다(중계 스펙의 비보장 범위).

06 / 현재 코드에서 입력을 따라가기

현재 코드에서 입력을 따라가기

먼저 모듈 설계의 처리 순서를 읽고 아래 순서로 코드를 따라간다. 행 번호는 이 해설의 대상 커밋에서 확인했다. 코드 발췌는 실제 구현이며 생략한 주변 흐름은 목록에서 설명한다.

  1. upgrade.rs 278~299행은 서브프로토콜 목록에서 ticket. 값을 센다. binary 누락 검사가 먼저다.
  2. websocket.rs check_upgrade(324~425행)는 실행 중 설정의 해당 역할을 읽는다. 꺼졌으면 ticket 확인을 건너뛴다. 켜졌으면 개수·JWS 확인을 한 뒤 IP를 재검사하고 사용 기록을 쓴다.
  3. ticket/jws.rs verify(35~73행)는 키 선택·서명·클레임 형식을 처리한다. domain/src/ticket.rs TicketPolicy::check(131~153행)는 클레임 대조·수명·기동 기준을 검사한다.
  4. 같은 domain 파일의 TicketUseTable::try_record(367~384행)는 만료 기록 정리와 중복 확인·쓰기를 한다. 호출 쪽 websocket.rs 397~408행이 잠금을 잡는다.
  5. websocket.rs upgrade(430~512행)는 ticket_accepted를 기록하고 U를 다시 확인한 뒤 101을 보낸다. 488~496행은 TicketBinding을 만든다. session_deadline(526~531행)은 sx를 단조 시각의 기한으로 바꾼다.
  6. 그 뒤 app/src/relay.rs는 초기 요청과 결속 값을 대조한다. relay/handshake.rs, matching.rs, session.rs는 초기 교환·대기·활성 세션의 만료를 각각 처리한다. JWS 검증은 이 중계 계층에 넘기지 않는다.

서명 확인: 서명 키가 아니라 공개 키를 쓴다

기동 기준: 일회용 기록이 사라지는 경계를 막는다

초기화와 시험용 발급

기동 시각·사용 기록은 프로세스 시작 때 한 번 만든다. 공개 키는 시작과 재로드 후보 검증 때 읽어 설정 스냅샷에 담는다. 업그레이드마다 파일을 다시 읽지는 않는다. 설정과 키는 한 세대로 확인한다(상태와 초기화).

운영 ticket은 외부 발급 쪽이 서명한다. 개발 전용 cargo xtask ticket은 시험 키와 ticket을 만드는 도구다(사용자 결정 2026-11-13(Q233)). 배포 실행파일에는 발급 기능이 없다. 명령과 확인 절차는 운영 안내 3.10.1절을 따른다. 이 해설을 정리하면서 그 명령이나 중계 시험을 실행하지는 않았다.

07 / 실패 뒤 남는 상태와 재시도

08 / 오해와 보호 범위

오해와 보호 범위

“서명했으니 한 번만 쓸 수 있다.”
서명은 값의 위조·변조를 확인한다. 일회용은 vnc-relay의 사용 기록에서 나온다. 처음 사용하기 전에 원문을 빼앗기면 공격자가 먼저 쓸 수 있다.
“Viewer ticket이면 기기도 확인했다.”
Viewer 역할만 확인한 것이다. Server 등록은 별도 설정이다. 같은 역할의 TCP 경로도 함께 살펴야 한다.
“exp가 되면 화면 연결도 끊긴다.”
exp는 접속 시점의 유효 기간이다. 이미 열린 연결의 종료 시각은 선택 클레임 sx다. sx가 없으면 ticket은 종료 시각을 정하지 않는다.
“키를 빼거나 ticket을 끄면 기존 연결도 끝난다.”
재로드는 새 업그레이드부터 바뀐다. 기존 연결의 ID·sx 기한과 사용 기록은 유지한다. 활성 세션 종료는 별도의 관리 기능이다.
“ticket이면 IP·Origin·VNC 비밀번호는 필요 없다.”
ticket은 추가 확인이다. 기존 접근 검사와 VNC 끝점의 인증을 대신하지 않는다. 중계 스트림 자체를 암호화하는 기능도 아니다. WS·WSS는 연결 구간의 보호이며, VNC 데이터의 끝점 간 보호는 따로 판단한다.
“관리 로그인으로 중계 권한을 얻는다.”
관리 세션과 접속 ticket은 분리한다. 발급 쪽은 자신의 권한 정책으로 서명 여부를 정하고 vnc-relay는 그 결과만 계약대로 확인한다.
표 9. 선택의 이점과 제약.
선택이점제약
역할별 선택형 확인클라이언트를 준비한 역할부터 켤 수 있다.꺼진 역할과 TCP 경로는 ticket으로 보호하지 않는다.
공개 키 검증vnc-relay가 발급 쪽 서명 키를 갖지 않는다.키 파일 무결성과 발급 쪽 권한 정책을 신뢰한다.
메모리 일회용 기록같은 프로세스의 동시 재사용을 거절한다.단일 인스턴스 경계이며 개수 상한이 없다. 재시작은 새 발급 기준을 적용한다.
101 전 거절대기·매칭 전에 막는다.브라우저 페이지의 오류 정보는 제한된다.
선택 sx 기한초기 교환·대기·활성 연결을 같은 허가 기간으로 제한한다.끝점 상태를 복구하거나 자동 재연결하지 않는다. 정리 중 남은 바이트 전달은 보장하지 않는다.

10 / 이해했는지 확인하기

이해했는지 확인하기

ticket 값을 보냈는데 binary를 제시하지 않았다면?

기존 서브프로토콜 검사가 먼저 HTTP 400으로 거절한다. ticket 확인 단계에 가지 않는다.

사용 기록을 쓴 뒤 101 전송이 실패하면 같은 ticket으로 재시도할 수 있는가?

없다. 사용 기록은 유지한다. 새 ticket으로 새 연결을 시도한다.

재시작 직전 만든 미사용 ticket은 반드시 통과하는가?

아니다. iat가 새 기동 시각 + 5초 이하이면 ticket_issued_before_start로 거절한다.

Viewer 확인만 켜면 다른 연결의 Server 선점도 막는가?

아니다. Server 확인은 별도다. Server를 켜도 같은 역할의 TCP 진입점을 열어 두면 그 경로는 ticket 없이 남는다.

TCP 초기 요청의 NUL 채움 자리에 ticket을 넣으면?

인증 필드가 아니므로 확인하지 않는다. 기기 쪽 WS·WSS 클라이언트나 로컬 터널이 업그레이드 요청에 실어야 한다.

ticket을 끄는 재로드 뒤 기존 연결의 sx는 사라지는가?

사라지지 않는다. 기존 연결의 ID와 만료 기한, 사용 기록은 유지한다.

ticket을 켠 Viewer가 Mode I을 요청하면?

Mode I이 꺼졌으면 기존 Close 1008이 먼저다. 켜졌으면 문법 검사 뒤 Close 4012다. 대상 연결은 하지 않는다.
