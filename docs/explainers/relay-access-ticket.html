VNC Relay 해설 · WebSocket 중계 접속

ticket은 누가 확인해야
효과가 생기는가

ticket은 어드민 서비스가 연결 직전에 발급하는 짧은 수명의 접속 허가값이다. 업그레이드 요청을 받는 쪽이 ticket의 진위·만료·사용 여부를 확인해야 효과가 생긴다. vnc-relay는 ticket을 읽지 않는다. 그래서 vnc-relay를 바꾸지 않고 ticket을 쓰려면 확인 지점을 vnc-relay 앞의 프록시에 두어야 한다.

이 해설이 다루는 세 상태

현재 기준
vnc-relay는 중계 접속에 토큰을 쓰지 않는다. 접근 통제는 진입점별 출발지 IP 허용 목록이다(ADR-0002). 프록시의 인증 종료와 중계 접속 토큰은 ADR-0007의 범위 밖이다. 사용처의 현재 계약도 ticket 없이 연결한다.
철회한 설계
사용처의 어드민 서비스가 2026-10-12에 채택하고 2026-11-08에 철회했다. 전용 중계가 서명한 일회용 ticket을 직접 확인하는 설계였다.
미승인 대안
vnc-relay 앞의 프록시가 ticket을 확인하는 방식이다. 아무도 채택하지 않았고 실행하지도 않았다.

이 해설은 요구사항이나 설계를 정하지 않는다. 경로·헤더 이름·설정은 설명을 위한 예시다.

읽기 안내

기준 독자vnc-relay 앞에 어드민 웹이나 역방향 프록시를 붙이려는 개발자와 운영자
먼저 읽을 문서WebSocket 진입점 모듈 설계, WebSocket 중계 계약 1.1절
관련 기준 문서ADR-0002, ADR-0007, WebSocket 중계 계약 v1, 설정 계약 v4
대상 버전·확인일vnc-relay v2026.11.2 이후 main c13e82e의 코드와 문서. 사용처 계약은 비공개 저장소의 철회 직전 커밋 96b0258과 현재 커밋 a012d9d(결정 ADM-TBD-059·238·239). 외부 문서를 포함해 2026-11-10에 확인했다.

  • vnc-relay를 바꾸지 않고 ticket을 확인하려면 어디에 무엇을 두는가?

01 / 문제 상황

중계 ID만으로는 누가 연결하는지 알 수 없다

브라우저의 noVNC는 vnc-relay의 /relay 경로로 WebSocket 업그레이드 요청을 보낸다. 101 응답 뒤에는 초기 교환으로 중계 ID를 보낸다. 같은 중계 ID로 기다리던 기기의 대기 연결이 있으면 둘은 Mode II로 짝을 이룬다.

vnc-relay가 업그레이드 전에 보는 접근 조건은 클라이언트 주소와 Origin이다(계약 1.1절). 출발지 IP 허용 목록에 전체 허용 항목(0.0.0.0/0)을 쓰면 주소 검사는 아무도 거르지 않는다. Origin은 다른 사이트의 브라우저 페이지만 막는다. 요청을 직접 만드는 프로그램은 Origin 헤더를 빼고 보낼 수 있다. 이때 vnc-relay는 Origin 검사만 건너뛰고 주소 검사는 그대로 한다(계약 1.3절).

중계 ID는 짝을 찾는 값이며 비밀값이 아니다(용어집). 그래서 허용된 출발지에서 Origin 검사를 통과한 클라이언트는 중계 ID만 알면 자격 증명 없이 짝을 이룰 수 있다. 그 뒤에 남는 보호는 기기가 확인하는 VNC 비밀번호다. ticket은 여기에 "어드민 서비스에서 방금 연결을 요청한 브라우저인가"라는 조건을 더하려는 방법이다.

03 / 정상 흐름

확인 위치만 다르고 순서는 같다

두 ticket 설계는 같은 순서를 따른다. 브라우저가 접속정보를 요청하면 어드민 API가 ticket을 발급한다. 브라우저는 업그레이드 요청에 ticket을 싣는다. 확인 지점은 ticket을 확인하고 사용 기록을 남긴 뒤에만 요청을 통과시킨다.

아래 모형은 확인 지점을 상자 하나로 묶었다. 시나리오를 바꾸면 같은 요청이 어디에서 갈라지는지 볼 수 있다.

직접 재생하거나 이전·다음으로 한 단계씩 볼 수 있다.

04 / 철회한 설계

전용 중계가 서명과 사용 기록을 본다

사용처는 처음에 브라우저 앞에 전용 WebSocket 중계를 두려고 했다. 이 중계가 ticket을 확인한 뒤 기존 UltraVNC Repeater의 Viewer 포트로 TCP 연결을 열 예정이었다. 2026-11-08 결정(ADM-TBD-238)이 ticket 인증을 철회하고 중계를 vnc-relay로 바꾸었다. vnc-relay에는 ticket을 확인하는 기능이 없다.

ticket은 JWS 압축 형식이다. 어드민 API가 KMS(키 관리 서비스)의 P-256 서명 키로 서명하고, 전용 중계는 공개 키만 가진다. KMS는 ECDSA 서명을 DER 형식으로 돌려준다(AWS KMS Sign). 그래서 API가 JWS가 요구하는 R‖S 64바이트로 바꾼다. 서명 키는 환경(stage)마다 하나이며 키 교체 절차는 정하지 않았다.

API는 세션 만료 시각 sx가 발급 시각 iat보다 늦지 않으면 발급하지 않고 409로 답한다. ticket 원문은 DB·감사 기록·로그에 남기지 않는다.

표 3. 철회한 설계의 클레임 9개. 발급자와 수신자 이름은 일반화해 적었다.

101 전에 전용 중계가 확인하는 순서

  1. TLS 연결이 성립해야 한다.
  2. Origin이 허용 값과 다르면 403이다.
  3. 서브프로토콜 값 목록의 형식이 틀리면 400이다. 목록은 앱 고유 이름 하나와 접두어를 붙인 ticket 하나로 이루어진다.
  4. 서명·iss·aud·exp·iat를 5초의 시계 오차 안에서 확인한다. 틀리면 401이다.
  5. jti를 사용 기록에 원자적으로 쓴다. 이미 있으면 401이다. 기록은 exp 뒤 5초까지 두고, 재시작해도 유지한다. 저장에 실패하면 503이다. 기록을 잃었으면 시계를 다시 맞춘 뒤 70초 동안 모든 요청을 503으로 거절한다. 그래서 환경마다 전용 중계 인스턴스는 하나다.
  6. rh가 허용한 중계 호스트가 아니면 403이다.
  7. 101은 앱 고유 이름만 고른다. ticket 값은 응답에 되돌리지 않는다.

70초는 ticket 수명 60초와 시계 오차 5초를 더한 값보다 길다. 그래서 기록을 잃기 전에 발급된 ticket은 이 기간 안에 모두 만료된다(추정: 원문에서 이 이유를 확인하지 않았다).

101 뒤의 동작

  • 5초 안에 Repeater의 Viewer 포트로 TCP 연결을 열지 못하면 close 4502로 끊는다.
  • 브라우저의 첫 250바이트가 ID:와 rid를 이은 값(남는 자리는 NUL로 채움)과 다르면 4403으로 끊는다. ticket을 중계 ID 하나에 묶는 장치다.
  • 120초 동안 Repeater에서 바이트가 오지 않으면 4408로 끊는다.
  • sx가 되면 4410으로 끊는다.
  • 로그에는 시각·sub·jti·결과·전송량만 남긴다.

이 close 코드들은 vnc-relay의 close 코드에 없다. vnc-relay는 4000번대 코드를 다른 뜻으로 쓴다.

05 / 미승인 대안

프록시가 업그레이드 전에 묻는다

vnc-relay를 바꾸지 않으려면 확인 지점을 vnc-relay 앞으로 옮긴다. 역방향 프록시가 WSS를 받아 TLS를 끝낸다. 프록시는 업그레이드를 넘기기 전에 확인 서버에 ticket을 보낸다. 확인 서버가 2xx로 답할 때만 요청을 vnc-relay의 루프백 WS 리스너로 넘긴다.

vnc-relay 쪽은 설정만 바뀐다. [relay.ws]를 루프백 주소에서 열고, 그 리스너의 trusted_proxies에 프록시 주소를 넣는다. 그러면 vnc-relay는 프록시가 붙인 X-Forwarded-For로 클라이언트 주소를 구한다(계약 1.8절, ADR-0007). 역할별 출발지 IP 허용 목록과 Origin 검사는 그대로 동작한다. trusted_proxies는 재로드 대상이지만, 리스너를 새로 열거나 역할을 켜고 끄는 변경은 재시작이 필요하다(설정 계약 1.8절).

프록시를 거치지 않는 Viewer 진입점이 열려 있으면 ticket을 건너뛸 수 있다. 그래서 이 대안은 공개 WSS Viewer 역할을 끄고, 프록시 뒤의 WS만 남기는 배치를 전제로 한다.

ticket과 웹 쪽 형태

확인 서버가 발급 기록을 직접 읽을 수 있으면 서명이 필요 없다. 예를 들어 32바이트 난수를 base64url로 바꾼 값을 ticket으로 준다. 서버에는 그 값의 해시와 만료 시각만 저장한다. 해시 앞에는 용도·버전·환경 이름을 붙여 다른 용도의 해시와 섞이지 않게 한다. 확인 때는 "미사용이면 사용됨으로 바꾼다"는 조건부 쓰기를 한 번 한다. 이 쓰기가 성공한 요청만 통과한다.

웹은 noVNC의 wsProtocols 옵션에 ['binary', ticket]을 넣는다(noVNC API). binary를 함께 넣는 이유는 응답 때문이다. 서버는 클라이언트가 제시한 값만 고를 수 있다. vnc-relay는 binary를 골라 101에 되돌린다(계약 1.2절).

지금의 vnc-relay도 binary가 들어 있는 목록은 받아들이고, 나머지 값은 판정에 쓰지 않는다. 그래서 웹이 프록시보다 먼저 ticket을 실어도 연결은 깨지지 않는다. 그때 ticket은 아무 효과가 없다.

헤더를 다룰 때 생기는 문제

확인 요청에 업그레이드 헤더가 남으면 확인 서버는 WebSocket 업그레이드 요청을 받는다. 그래서 이 헤더를 지운다. 그런데 Sec-WebSocket-*를 지우면 ticket도 함께 지워진다. 지우기 전에 다른 헤더로 옮겨야 한다. 2026-11-10 Caddy 2.11.9 루프백 임시 시험에서 두 가지를 관찰했다. forward_auth는 업그레이드 헤더를 확인 요청에 그대로 넘겼다. 헤더를 지우자 ticket이 사라져 확인 서버가 401로 답했다. 이 시험은 저장소에 기록하지 않았다. 옮긴 뒤 지우는 설정은 실행하지 않았다.

Caddy 접근 로그는 요청 헤더를 남긴다. 기본으로 가리는 헤더는 Cookie·Set-Cookie·Authorization·Proxy-Authorization뿐이다(Caddy log_credentials). 그래서 ticket이 든 Sec-WebSocket-Protocol은 로그 필터로 따로 지워야 한다. 같은 임시 시험에서 이 값이 평문으로 남은 것을 관찰했다.

Caddy는 설정을 다시 적용할 때 열린 WebSocket을 바로 닫는다. stream_close_delay를 주면 그 시간 동안 유지한다(Caddy reverse_proxy).

확인 요청이 GET일 때의 문제

Caddy의 forward_auth는 확인 요청을 항상 GET으로 보낸다(Caddy forward_auth). GET은 멱등 메서드이며, 응답을 읽기 전에 통신이 실패하면 자동으로 다시 보낼 수 있다(RFC 9110 9.2.2절). 일회용 확인은 상태를 바꾸므로 이 가정과 맞지 않는다. 첫 확인이 사용 기록을 쓴 뒤 응답이 사라져 다시 보내면, 두 번째 확인은 "이미 사용됨"으로 거절한다. 선택지는 세 가지다.

  1. GET에서 소비하는 것을 받아들인다. 드물게 정상 사용자가 401을 받으면 접속정보를 다시 요청해 새 ticket으로 연결한다.
  2. forward_auth 대신 같은 동작의 확장형 reverse_proxy를 쓰고 메서드를 POST로 바꾼다. forward_auth는 method GET이 들어간 reverse_proxy의 축약이다. 이 구성은 실행하지 않았다.
  3. 확인 때 소비하지 않는다. 만료 전까지 같은 ticket을 다시 쓸 수 있으므로 일회용이 아니다.
표 4. 프록시별 확인 요청 처리. 각 프록시 공식 문서 기준이며 nginx는 실행하지 않았다.
프록시2xx401·403그 밖의 응답
Caddy forward_auth원래 요청을 계속 처리한다.확인 서버의 응답을 클라이언트에 그대로 복사한다.같다. 그래서 확인 서버의 503이 브라우저에 503으로 보인다.
nginx auth_request허용한다.같은 코드로 거절한다.오류로 처리한다(500). 확인 서버의 503은 브라우저에 500으로 보인다.
표 5. 확인 서버를 두는 위치. 두 위치 모두 미승인 대안의 세부 선택지다.
위치이점비용
어드민 API발급 기록과 사용 기록이 한 저장소에 있다. 서명 키가 필요 없다.연결마다 프록시가 인터넷 너머의 API를 부른다. API 장애는 곧 연결 불가다. 확인 경로가 인터넷에 열리므로 호출자 인증과 요청 수 제한을 정해야 한다.
프록시 옆 로컬 확인 서버네트워크 왕복이 없다.서명한 ticket과 공개 키가 필요하다. 일회용이려면 사용 기록을 디스크에 남기거나, 기록을 잃은 뒤 수명보다 긴 시간 동안 모두 거절해야 한다. 서버를 하나 더 운영한다.
설정 예시 보기(개념 예시, 실행하지 않음)

채택한 설정이 아니다. 이름과 주소는 문서용 값이다. 헤더 복사와 삭제의 적용 순서는 확인하지 않았다.

relay.example {
	@relay path /relay
	handle @relay {
		forward_auth https://admin.example {
			uri /relay-tickets/verify
			header_up X-Relay-Subprotocols {http.request.header.Sec-WebSocket-Protocol}
			header_up -Connection
			header_up -Upgrade
			header_up -Sec-WebSocket-*
		}
		reverse_proxy 127.0.0.1:8080 {
			header_up Sec-WebSocket-Protocol binary
			stream_close_delay 30m
		}
	}
	handle {
		respond 404
	}
	log {
		format filter {
			request>headers>Sec-Websocket-Protocol delete
		}
	}
}

06 / 코드에서 따라가기

vnc-relay 코드에서 ticket이 지나가는 곳

검사 순서의 기준은 WebSocket 진입점 모듈 설계의 검사 순서다. 여기서는 ticket과 관련된 지점만 따라간다.

  1. crates/adapters/src/websocket.rs의 upgrade가 요청 머리를 읽고 check_upgrade를 부른다. check_upgrade는 현재 설정으로 check를 실행한다. 그다음 클라이언트 주소(forwarded_ip.unwrap_or(peer_ip))를 선택한 역할의 허용 목록과 다시 대조한다.
  2. crates/adapters/src/upgrade.rs의 check가 요청 머리를 순서대로 검사한다. 소켓 상대가 trusted_proxies에 있으면 vnc_relay_domain::forwarded_for::client_ip가 X-Forwarded-For를 오른쪽부터 읽어 처음 만나는 비신뢰 주소를 고른다.
  3. 같은 함수가 Origin을 본다. 헤더가 없으면 이 검사를 건너뛴다.
  4. 마지막으로 서브프로토콜 값을 모은다. 아래가 그 부분이다.

ticket은 tokens에 들어가지만 어떤 판정에도 쓰이지 않는다. binary가 함께 있으면 통과하고, 값이 있는데 binary가 없으면 400(SubprotocolNotSupported)이다. 그래서 철회한 설계의 값 목록(앱 고유 이름과 ticket)을 vnc-relay에 그대로 보내면 400이 된다.

같은 파일의 switching_protocols가 101 응답을 만든다. binary를 제시한 요청에만 Sec-WebSocket-Protocol: binary를 넣는다. ticket은 응답에 나타나지 않는다.

Cookie와 Authorization도 접근 판정에 쓰지 않는다(계약 1.1절 표의 "그 밖의 헤더" 행). 따라서 vnc-relay에는 ticket이나 로그인 쿠키를 확인할 자리가 없다. ADR-0002가 토큰 대신 출발지 IP 허용 목록을 고른 결과다. 그 ADR은 WS 전용 토큰과 관리자 로그인 재사용을 대안에서 제외했다. TCP 경로에 적용할 수 없고, 관리 권한과 중계 권한이 섞이기 때문이다.

07 / 실패 흐름

실패하면 무엇이 남고, 다시 할 수 있는가

ticket 방식의 실패는 대부분 "새 ticket으로 다시 시작"으로 복구한다. ticket은 한 번 쓰면 끝난다. 또 확인과 업그레이드는 하나의 원자적 작업이 아니다. 확인 지점이 사용 기록을 쓴 뒤에 업그레이드가 실패해도 기록은 되돌아가지 않는다.

표 6. 실패 지점별 결과. 철회한 설계와 대안이 다르면 함께 적었다.
실패 지점남는 상태재시도복구 원리
접속정보 요청 거절(로그인·권한·세션 만료)ticket 없음원인을 해소한 뒤 다시 요청한다.발급 전에 끝나므로 정리할 상태가 없다.
ticket 만료(받은 뒤 60초 경과 또는 세션 만료)쓰지 않은 ticket. 대안에서는 해시 기록이 보존 기간 뒤 지워진다.같은 ticket은 쓸 수 없다. 접속정보를 다시 요청한다.확인 지점이 만료 시각으로 거절한다(401).
이미 쓴 ticket 제출사용 기록이 그대로 남는다.새 ticket이 필요하다.조건부 쓰기는 한 번만 성공한다(401).
확인은 통과했으나 업그레이드 실패(중계 중지, Origin·IP 403, 프록시에서 중계로의 연결 실패)ticket은 사용됨. 중계에는 대기 연결이나 활성 세션이 없다.같은 ticket은 쓸 수 없다. 새 ticket이 필요하다.사용 기록은 업그레이드 결과를 모른다.
확인 응답이 사라진 뒤 자동 재전송첫 확인이 쓴 사용 기록두 번째 확인은 401이다. 새 ticket이 필요하다.GET으로 소비하는 대가다(05절의 선택지).
사용 기록 저장소 장애판단할 수 없다. ticket은 아직 쓰지 않은 상태일 수 있다.저장소가 복구된 뒤 새로 시도한다.판단할 수 없으면 통과시키지 않는다. 철회한 설계는 503이며, 기록을 잃었으면 70초 동안 모두 503이다.
확인 서버 무응답(대안)요청이 닿기 전이나 기록 전에 실패했으면 바뀐 상태가 없다. 기록한 뒤 응답만 사라졌으면 ticket은 이미 사용됐을 수 있다.확인 서버가 복구된 뒤 같은 ticket으로 다시 시도할 수 있다. 이미 사용됐으면 401이므로 새 ticket이 필요하다.프록시가 요청을 넘기지 않는다. 브라우저가 받는 코드는 프록시마다 다르다(표 4). 프록시는 확인 서버가 기록을 남겼는지 알 수 없다.
연결 뒤 권한 회수나 세션 만료중계의 활성 세션이 유지된다.해당 없음확인은 업그레이드 때 한 번뿐이다. 대안과 현재 기준에서는 vnc-relay의 관리자 종료로 끝낼 수 있다. 철회한 설계는 sx에 4410으로 끊었다.

08 / 오해와 선택

자주 하는 오해와 선택의 대가

"서명한 ticket이면 일회용이다."
서명은 위조만 막는다. 같은 값을 두 번 내면 두 번 모두 서명 검증을 통과한다. JWT 표준도 jti를 재사용 방지에 쓸 수 있는 식별자로만 정한다(RFC 7519 4.1.7절). 일회용은 확인 지점의 사용 기록에서 나온다.
"Origin 검사나 중계 ID가 인증 역할을 한다."
둘 다 인증 수단이 아니다(계약 1.3절, 용어집).
"ticket을 실으면 vnc-relay가 거른다."
vnc-relay는 binary 외의 값을 판정에 쓰지 않는다(06절).
"ticket이 있으면 권한 회수가 바로 반영된다."
확인은 업그레이드 때 한 번이다. 그 뒤 연결은 계속된다.
"프록시를 두면 모든 접속 경로가 보호된다."
TCP 진입점은 HTTP가 아니어서 프록시의 확인을 거치지 않는다. TCP Viewer 진입점이 열려 있으면 ticket 없이 같은 중계 ID로 연결할 수 있다.
"대안에서 ticket을 통과하면 그 중계 ID에만 연결된다."
대안의 확인 지점은 WebSocket 프레임 안의 초기 교환을 보지 않는다. ticket을 받은 사용자는 다른 중계 ID를 보낼 수 있다. 철회한 설계는 rid로 이것을 막았다.
"ticket은 수명이 짧으니 원문이 로그에 남아도 괜찮다."
ticket은 가진 사람이면 누구나 쓸 수 있는 값이다. 수명 안에 다른 사람이 먼저 쓰면 그 사람이 통과하고, 정상 사용자는 401을 받는다. 그래서 두 설계 모두 원문을 로그에 남기지 않는다.
표 8. 선택에 따른 이점과 제약. 어느 선택도 이 저장소의 기준을 바꾸지 않는다.
선택이점제약
ticket 없이 출발지 IP 허용 목록(현재 기준)구성 요소가 늘지 않는다. 기존 UltraVNC와 호환된다.허용한 IP 안의 사용자를 구분하지 못한다. 전체 허용 항목이면 주소 검사가 아무도 거르지 않는다.
중계가 직접 확인(철회한 설계)중계 ID·중계 호스트와 묶고, 세션 만료 때 끊을 수 있다.중계에 ticket 기능이 있어야 한다. vnc-relay에는 없다.
프록시와 어드민 API 확인vnc-relay 코드가 바뀌지 않는다. 발급과 사용 기록이 한곳에 있다.연결마다 API를 왕복한다. API 장애가 연결 불가로 이어진다. 중계 ID와 묶지 않는다.
프록시와 로컬 확인 서버왕복이 없다.서명 키와 확인 서버를 운영한다. 일회용이려면 기록을 영속화하거나 거절 기간을 둔다.
프록시가 어드민 로그인 쿠키 확인발급 단계가 없다.쿠키가 중계 주소로 가야 하므로 쿠키 범위와 SameSite 조건에 묶인다. 로그인 권한 전체가 중계 접속 권한이 된다. 일회용이 아니다.

대안에는 아직 정하지 않은 질문이 남아 있다. 확인 서버를 어디에 둘 것인가. 확인 경로의 호출자를 어떻게 인증할 것인가. 확인 때 원격 지원 세션을 다시 볼 것인가. TCP Viewer 진입점을 어떻게 할 것인가. GET으로 소비하는 문제를 어떻게 다룰 것인가. 이 질문은 사용처의 보호 강화 검토(ADM-TBD-239)에 속한다. 프록시의 인증은 ADR-0007의 범위 밖이다. 그래서 이 저장소가 아니라 배치하는 쪽이 정한다.

10 / 확인 질문

이해했는지 확인하기

서명만 검증하는 확인 서버가 같은 ticket을 두 번 받으면 어떻게 되는가?

두 번 모두 통과한다. 사용 기록이 없으므로 두 번째 요청을 구분할 근거가 없다.

브라우저가 ['binary', ticket]을 보냈는데 프록시 없이 vnc-relay에 바로 닿으면?

vnc-relay는 binary를 골라 101로 수락한다. ticket은 무시된다.

확인은 성공했는데 vnc-relay가 Origin 불일치로 403을 돌려주면 그 ticket은 어떻게 되는가?

이미 사용됨 상태다. 같은 ticket으로는 다시 연결할 수 없고, 새 ticket이 필요하다.

프록시 앞단 확인을 두어도 막지 못하는 것 두 가지는?

프록시를 거치지 않는 TCP 진입점으로 들어오는 연결, 그리고 연결이 성립한 뒤의 권한 회수나 세션 만료다. 대안에서는 다른 중계 ID로 바꿔 보내는 것도 막지 못한다.
