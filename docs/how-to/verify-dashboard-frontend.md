# 대시보드 프런트엔드를 검증하는 방법

대시보드 프런트엔드(`web/dashboard/`)가 [프런트엔드 컨벤션](../conventions/frontend.md)과 [디자인 기준](../design/DESIGN.md)을 지키는지 확인한다. 자동 검사 결과는 실행할 때 생성한다. 수동·외부 도구 검토의 최신 증거는 4절에 둔다. 미실행 범위를 통과로 표시하지 않는다.

이 문서는 Draft다.

| 검증 환경·버전 | 고정 Rust 툴체인과 지원 OS는 2·3절을 따른다. 검토에 사용한 브라우저·도구의 실제 버전은 4절에 적는다 |
| 최신 수동 검토일 | 2026-11-17. 범위별 날짜와 미실행 항목은 4절을 따른다 |

## 1. 대상과 영향

- 대상: `web/dashboard/` 정적 파일, `docs/design/DESIGN.md`의 YAML 토큰, `docs/design/mockups/dashboard.html`·`help-site.html`의 토큰 블록, `tests/dashboard_assets.rs`·`tests/dashboard_browser.rs`·`tests/dashboard_live/main.rs`와 그 공통·화면별 본문.
- 예상 사용자 영향: 운영 중인 VNC Relay를 멈추지 않는다. 실제 VNC Relay 시험은 OS 임시 폴더에 계정·설정·브라우저 프로필을 만들고, 임의 루프백 포트에 시험용 VNC Relay·전달 프록시·TCP 중계를 연다. 자신이 시작한 프로세스와 소켓만 종료한다. 기존 토큰·정적 검사는 파일을 읽고 `target/` 아래에 결과를 쓴다.
- 작업 허용 시간: 자동 검사는 VNC Relay 중단이 필요 없다. 수동 검토(3.4~3.7절)는 검토자의 시간이 필요하다.

## 2. 전제 조건

- [ ] 검증할 커밋을 정했고, `git status --short` 결과를 검증 기록에 적었다.
- [ ] 고정 Rust 툴체인 1.99.1을 쓴다(`rust-toolchain.toml`).
- [ ] Chromium(Chrome 또는 Edge)은 두 OS 모두 필수다. 실행 파일 경로를 환경 변수 `DASHBOARD_BROWSER`에 넣을 수 있다. 넣지 않으면 표준 설치 경로와 PATH에서 Chrome, 다음 Edge를 찾는다. 찾지 못하면 브라우저 시험은 실패한다. 환경 변수 이름은 이 문서의 기본값이다.
- [ ] Firefox 수동 검토에 쓸 버전을 정했다. 실제 버전은 검증 기록에 적는다.
- [ ] Safari 대체 확인에 쓸 Playwright와 WebKit을 저장소 밖에 준비했다. 두 버전은 검증 기록에 적는다.
- [ ] (선택) Node.js와 고정 버전의 `@google/design.md`를 준비했다. 고정 버전은 검증 기록에 적는다.
- [ ] 수동 검토자와 스크린 리더 환경을 정했다.


## 3. 절차

- 실행 환경: Ubuntu 24.04 LTS x64는 bash, Windows 11 x64는 PowerShell을 쓴다. 지원 환경은 [개발 환경·검증 how-to 2절](set-up-and-verify.md#2-전제-조건)을 따른다.
- 실행 위치: 저장소 루트
- 바꿔 넣을 값: `DASHBOARD_BROWSER`에는 Chromium 실행 파일 경로를 넣는다. 확인하려면 경로를 직접 실행해 `--version`이 버전을 출력하는지 본다. 경로에 공백이 있으면 큰따옴표로 감싼다.
- 최대 대기 시간: 일반 자동 명령은 10분을 기본값으로 쓴다. 실제 VNC Relay 브라우저 시험 묶음과 전체 게이트는 `Si=300s` 실제 만료를 포함하므로 20분 이상 허용한다. 수동 검토에는 시간 한도가 없다.

### 3.1 토큰과 문서 확인

1. 저장된 토큰 CSS를 DESIGN.md YAML에서 다시 만든 결과와 대조한다. 로그인 화면의 생성 복사본(`web/dashboard/login/components/`, `web/dashboard/login/styles/`)도 원본 `web/dashboard/app/`과 같은지 대조한다.

   영향: 없음. 파일을 쓰지 않는다.

   ```shell
   cargo xtask tokens --check
   ```

   기대 결과: 종료 코드 0. 차이가 있으면 파일 이름과 줄이 출력되고 종료 코드가 0이 아니다.

2. (선택) DESIGN.md 린트를 실행한다.

   영향: 없음. `npx`가 패키지를 내려받는다. 고정 버전은 아직 정하지 않았다. 처음 실행할 때 정하고 검증 기록에 적는다.

   ```shell
   npx -y -p @google/design.md@<고정 버전> designmd lint docs/design/DESIGN.md
   ```

   기대 결과: 오류 0건. 경고 수와 정보 수를 검증 기록에 적는다([디자인 기준 검증 절](../design/DESIGN.md#검증)).

### 3.2 제공 파일과 실행 파일 내장 대조

1. 제공 표와 `web/dashboard/`의 실제 파일을 비교한다. 빠진 파일이나 표에 없는 파일이 있는지 확인한다.

   영향: 없음. 테스트 빌드 결과는 `target/` 아래에 쓴다.

   ```shell
   cargo test --test dashboard_assets
   ```

   기대 결과: `test result: ok.` 줄이 나온다. 실패한 테스트 이름이 있으면 실패다.

### 3.3 브라우저 테스트와 보고서

1. 헤드리스 Chromium으로 브라우저 테스트를 실행한다.

   영향: 임시 브라우저 프로필을 만든다. 실행이 끝나면 지운다(이 문서의 기본값).

   ```shell
   cargo test --test dashboard_browser
   ```

   기대 결과: `test result: ok.` 줄이 나온다. 각 테스트 페이지의 `data-result` 값이 `pass`다. `DASHBOARD_BROWSER`가 없거나 실행되지 않으면 테스트가 실패해야 한다.

   실제 VNC Relay·CDP 수용 시험도 실행한다.

   ```shell
   cargo test --test dashboard_live
   ```

   일반 API 데이터는 실제 `serve`에서 얻는다. 시험 TCP 프록시의 지연·유실·계약 모양 500은 전달·주입 카운터로 구분한다. 주입한 500을 VNC Relay 자체 실패 증거라고 적지 않는다. DASH-008은 운영 현황과 상세에서 `Si=300s`를 실제로 기다린다. 이 명령을 60초에 끊지 않는다. Chrome·Edge 경로 탐색은 기존 `DASHBOARD_BROWSER` 규칙과 같다. 브라우저·VNC Relay·프록시는 시험 종료 시 정리한다. DASH-015·023의 수동 확인은 이 명령으로 대체하지 않는다.


2. 시나리오 보고서를 갱신한다.

   영향: `.work/reports/scenario-report.md`를 덮어쓴다.

   ```shell
   cargo xtask scenarios
   ```

   기대 결과: 자동으로 연결된 DASH 항목의 상태가 `통과`다. `부분` 표식이 붙으면 검증 기록에 이유를 적는다. `tests/dashboard_live/main.rs`의 비부분 행은 각 기대 결과 전체를 연결한다. 실행하지 않은 시험은 통과가 아니다. DASH-015·023의 수동 범위는 별도다([테스트 컨벤션 7절](../conventions/testing.md#7-테스트와-스펙-시나리오-연결)).

### 3.4 폭별 스크린샷과 시안 대조 (수동)

1. 미리보기 서버를 실행한다.

   영향: 루프백 주소의 포트 하나를 연다. Ctrl+C로 멈춘다.

   ```shell
   cargo xtask dashboard-serve
   ```

   기대 결과: 로컬 주소 한 줄이 출력되고 프로세스가 계속 실행된다.

2. 같은 화면 상태를 폭 1440·1280·1024·1023·768·390·320px에서 연다. 시안 `docs/design/mockups/dashboard.html`에서 같은 상태의 프레임도 같은 폭에서 연다.

   영향: 없음. 스크린샷은 `target/dashboard-shots/<폭>/<화면 상태>.png`에 저장하고 커밋하지 않는다.

   기대 결과: 페이지에 가로 스크롤이 없다. 화면 상태는 [화면 스펙 4절](../specs/dashboard.md#4-화면-상태와-갱신)의 SCR-001·SCR-002·SCR-003이다.

3. 구현 스크린샷과 시안 스크린샷을 나란히 두고 차이를 적는다. 자동 픽셀 비교는 하지 않는다.

   영향: 없음.

   기대 결과: 차이가 없거나, 차이가 화면 스펙과 디자인 기준에 맞는다. 시안과 스펙 문장이 다르면 스펙을 따른다.

4. 사람의 비교에는 비교 페이지를 쓴다. 저장소 밖 도구로 시안 프레임 26개와 같은 상태의 구현 화면을 2단계의 7개 폭(1440·1280·1024·1023·768·390·320px)으로 찍어 `target/` 아래 비교 페이지에 나란히 놓는다. 사용자가 이 페이지를 보고 차이를 판정한다. 설정·최근 로그·접속 ticket·도움말 링크·목록의 검토에는 해당 시안 프레임도 포함한다.

   시안 페이지는 프레임마다 18px 여백이 있다. 그래서 도구는 시안 뷰포트를 18px 넓혀 시안 내용 폭을 구현 뷰포트와 맞춘다. 1023px만 예외다. 시안 뷰포트를 1041px로 넓히면 중단점 `max-width:1023.98px`을 넘어 데스크톱 배치가 된다. 그래서 1023px에서는 두 뷰포트를 모두 1023px로 두어 모바일 배치를 유지하고, 시안 내용 폭은 1005px이 된다. 비교 페이지는 이 26쌍에 그 사실을 표시한다.

   영향: `cargo xtask dashboard-serve`의 루프백 포트 하나를 쓴다. 관리 API 응답은 도구가 시안과 같은 값으로 준다.

   기대 결과: 26개 프레임 × 7폭의 짝 182쌍이 모두 있고, 구현 쪽 가로 넘침·페이지 오류·응답 없는 API 요청이 0건이다. 차이의 판정은 사용자가 한다.

### 3.5 키보드 확인 (수동)

1. 로그인 화면에서 Tab으로 모든 조작 요소를 차례로 지나간다.

   기대 결과: 포커스 순서가 화면 순서와 같다. 포커스가 사라지지 않는다.

2. 포커스 표시를 확인한다.

   기대 결과: 링 두께 2px(`spacing.focus-ring-width`), 간격 2px(`spacing.focus-ring-offset`), 색 `colors.ring`이다. 상단 막대 안에서는 `colors.navbar-ring`이다.

3. 조작 요소를 Enter 또는 Space로 실행한다.

   기대 결과: 마우스로 실행한 것과 같은 행동이 일어난다.

4. 대화상자를 열고 닫는다.

   기대 결과: [화면 스펙](../specs/dashboard.md) 6절의 대화상자 포커스 규칙을 따른다.

검토자, 날짜, 브라우저 이름과 버전, 각 결과를 검증 기록에 적는다.

### 3.6 스크린 리더 확인 (수동)

스크린 리더 확인은 프런트엔드 기본 완료 조건에 포함하지 않는다. 실행하지 않으면 4절에 미실행으로 남긴다.

1. 스크린 리더를 켜고 로그인 화면과 SCR-001 화면을 연다. 스크린 리더 이름과 버전을 기록한다.

   기대 결과: 아래 2단계의 항목을 모두 확인했다.

2. 다음 항목을 확인한다.

   - 상단 막대의 이름이 "주 메뉴"이고, 본문이 랜드마크로 읽힌다([디자인 기준 접근성 절](../design/DESIGN.md#접근성-기준)).
   - 폭 390px에서 활성 세션 카드 목록이 `table`·`row`·`columnheader`·`cell` 역할로 읽힌다.
   - 사용량 고리가 이름과 현재·최소·최대 값을 읽는다(`progressbar`).
   - 언어 선택의 이름이 "언어 (Language)" 또는 "Language (언어)"로 읽힌다.
   - 장식용 SVG는 읽히지 않는다.

### 3.7 다른 브라우저와 실기기 확인 (수동)

1. Firefox에서 3.4의 2단계와 3.5 전체를 실행한다. 브라우저 이름과 버전을 적는다.

   영향: 없음.

   기대 결과: 결과가 Chromium과 같다. 차이가 있으면 검증 기록에 적는다.

2. Safari 대신 Playwright WebKit으로 자동 확인한다. Playwright는 저장소 밖 Python 가상 환경에 설치한다. 프로젝트 의존성에 넣지 않는다. 다음 두 가지를 실행한다.
   - `cargo xtask dashboard-serve`의 시험 페이지에서 `tests/dashboard_browser.rs`와 같은 사례를 7폭과 `lang=ko`·`lang=en`으로 연다. `data-result`, `data-failures`, CSP 위반 상세, 가로 넘침을 모은다.
   - 루프백의 실제 `vnc-relay serve`와 실제 TCP 중계 세션으로 SCR-003 로그인 → SCR-001 → SCR-002 → 종료 취소·확인 → 로그아웃을 1280·390·320px, ko·en으로 실행한다. 필수 요소가 화면 안에 있고 가려지지 않는지 `elementFromPoint`로 확인한다.

   영향: 시험 계정·설정·운영 로그를 저장소 밖 임시 폴더에 만든다. 끝나면 실행 파일 복사본과 계정 파일을 지운다.

   기대 결과: 결과가 Chromium과 같다. 결과는 "WebKit 대체 확인"으로 적고 Safari 통과로 적지 않는다. 엔진 차이와 도구가 만든 현상(예: 스크린샷이 넣는 `<style>`)은 나누어 적는다.

3. 실제 모바일 기기에서 390px 폭 화면을 확인한다. 릴리스 전 한 번 실행한다([프런트엔드 컨벤션 6절](../conventions/frontend.md#6-검증-명령과-통과-기준)). 이 확인은 프런트엔드 기본 완료 조건과 구분한다. 모바일 폭의 데스크톱 브라우저 실행으로 대신하지 않는다.

   영향: 없음.

   기대 결과: 카드 목록에서 정보와 행동이 가려지지 않는다.

## 4. 검증

[검증 기록](../AGENTS.md#검증-기록)에 따라 실제 결과와 성공 조건을 대조한다. 자동 검사 결과는 3.1~3.3의 명령과 `cargo xtask scenarios`가 생성하는 `.work/reports/scenario-report.md`, CI에서 확인한다. 과거 테스트 통과 수를 현재 결과로 쓰지 않는다.

아래에는 화면별 최신 시각 대조와 저장소의 Chromium 시험만으로 다시 얻을 수 없는 검토 증거를 둔다. 에이전트의 이미지 대조, 외부 도구 실행, 사람의 검토를 구분한다. 통과는 각 기록의 대상과 범위에만 적용한다. 실제 Safari·모바일 기기·스크린 리더 확인은 미실행이다. 실제 기기가 없고, 스크린 리더는 사람의 읽기 순서·발음 확인이 필요하다.

#### 허용하는 시안 차이

위 대조에서 허용한 차이는 다음과 같다. 동작·문구의 기준은 [화면 스펙](../specs/dashboard.md), 시각 기준은 [DESIGN.md](../design/DESIGN.md)다.

- 공통 셸은 내용에 맞는 높이와 실제 조작 요소를 쓴다. 세 항목 모바일 상단 막대는 시안의 100px 대신 108px다. 공통 배지 세로 안쪽 여백은 2px 대신 `spacing.xs`(4px)다.
- 인증 만료는 보호 데이터를 제거하고 로그인으로 이동한다. 시안의 보호 화면 안 작은 로그인 견본과 구분한다.
- SCR-001·002의 조회 중 안내는 전체 폭 배너 대신 카드 머리와 값 자리의 공통 정보 배지다. CPY에 없는 설명은 넣지 않는다. SCR-001 조회 실패는 요청별 카드에서 실패와 이전 데이터를 구분한다.
- SCR-002의 대상 없음·잘못된 식별자·종료 결과는 스펙이 정한 행동·톤·복구 안내를 쓴다. 정보의 키·값은 공통 `fact` 행 구분선·안쪽 여백·모바일 한 열을 쓴다.
- 설정 파일 상태는 상태 제목·본문·키·번역한 진단을 안내 안에 둔다. `invalid`·`unreadable`은 위험 톤이다. VNC Relay 진단에는 알려진 코드의 번역한 줄 오류를 쓰며 원문 키를 따로 덧붙이지 않는다.
- 설정 확인의 이전 값·새 값·목록 추가·삭제는 세로로 쌓는다. 계약과 입력 순서를 따르고 정수는 `typography.body-numeric`을 쓴다. 실제 대화상자는 뷰포트 가운데에 놓고 내부에서 스크롤한다. 초기 초점은 취소다.
- 설정 카드·표·구역은 모두 펼친다. 모바일 페이지 행동은 전체 폭으로 세로로 쌓는다. 취소·설정 보기 행동과 CPY-189 안내는 스펙 상태에 맞게 유지한다. 변경 없음 안내 CPY-106은 확인 대화상자 안에 있고 적용 시 PATCH 없이 설정 보기로 돌아간다.
- 최근 로그의 첫 성공 전 시각은 CPY-035 “확인 불가”·“Unavailable”이다. 다운로드 수집 중에는 시작 필터를 고정하고 입력·필터·수동 조회를 잠시 비활성화한다. 언어·이동·상세 조작은 유지한다.
- 표의 바이트 머리글과 주소 레이블은 시안의 짧은 문구 대신 스펙 CPY 문구를 쓴다. 긴 값은 자르지 않고 줄바꿈한다. 샘플 ID·주소·경로·revision·로그 수·시각·진단·검색 입력과 그 길이에 따른 높이 차이는 데이터 차이다.
- SCR-008의 제목 단계는 시안의 h4~h6 대신 h1·h2·h3이다. 주소별·ASN별 개수 배지의 `{shown}`은 `items` 수다. 그래서 가짜 API가 7행을 주면 "상위 7개"이고, 시안은 100행 응답을 가정해 "상위 100개"로 그렸다. 숫자·이름·주소는 데이터 차이다.
- SCR-007의 제목 단계는 시안의 h5·h6 대신 h2·h3이다. 조회 중에는 프로세스 카드의 핸들·fd 행을 생략한다. 시험 페이지 가짜 API의 적은 추이 점, 긴 원인 값의 줄바꿈 위치는 데이터와 열 폭에 따른 차이다.
- 모바일 빈 표 행의 높이는 시안 77px, 구현 53px다. 시안은 행 여백 12px 안에 칸 여백 16px을 두고, 구현은 행 여백 16px만 둔다. 같은 차이가 SCR-001 빈 목록에도 있다(2026-11-19 390px 측정). 글씨는 둘 다 가운데다.
- 추이 기간 선택의 꺾쇠 오른쪽 여백은 시안 8px(`spacing.sm`), 구현 12px(`spacing.md`)다. 선택 상자의 오른쪽 안쪽 여백은 시안 26px, 구현 24px(`spacing.xl`)다. 그래서 데스크톱 선택 상자가 시안보다 2px 좁다. DESIGN은 이 선택을 SCR-006 사건 선택과 같은 변형으로 정했고, 구현은 사건 선택의 규칙을 그대로 쓴다. 같은 차이가 SCR-006 사건 선택에도 있다(2026-11-19 1280px 측정).
- 차단 표시: 결과 알림의 중립 톤(CPY-097)은 시안의 느낌표 원 아이콘 대신 공통 알림 컴포넌트의 중립 아이콘을 쓴다. 같은 차이가 다른 중립 알림에도 있다. 설정 변경 확인의 차단 목록은 시안처럼 한 줄 화살표 대신 이전 값·새 값·추가한 항목·뺀 항목을 세로로 쌓는다(위 설정 확인 항목과 같은 이유). VNC Relay 진단 키(`relay.deny.sources[1]`)는 위 설정 파일 상태 항목처럼 덧붙이지 않고 오류가 난 줄을 선택한다. 결과 알림은 `scrollIntoView({ block: 'nearest' })`로 보이게 하고, 포커스는 호출한 버튼으로 돌아가며 버튼이 사라지면 알림 영역으로 간다(DESIGN.md 결정 8의 구현).

최신 로그·공통 셸 확인의 상세 결과는 다음과 같다.

- 실제 응답의 제품 JS·CSS는 실행마다 현재 소스와 바이트가 같았다. VNC Relay·전체 소스 해시는 `provenance.json`에 있다.
- 상세에는 `TCP → WS`, 대상 WS와 전달 주소 `192.0.2.20`이 보였다. 로그의 세션 필터는 해당 ID와 같고 해제하면 칩·URL에서 사라졌다.
- warn·`connection_rejected`·`forwarded_for_invalid` 검색은 검색어가 든 실제 GET과 200행을 확인했다. 더 보기는 200→400행, 상세 펼침은 `aria-expanded` true→false, 자동 갱신은 `aria-checked` false→true였다.
- 다운로드 파일은 실제 API 5페이지의 모든 entry와 같았다. Chrome·Edge·WebKit은 4977줄, Firefox는 4975줄이다. UTF-8·LF·마지막 LF도 맞았다. 각 실행의 VNC Relay 응답·필터 결과와 대조했으며 서로 다른 실행의 파일 내용 일치를 요구하지 않았다.
- 취소 뒤 실제 상세 GET은 200이고 초점은 종료 버튼으로 돌아왔다. 종료 확인 완료 안내 뒤 GET은 404였다. 로그아웃은 `/login/`으로 이동하고 보호 화면·로그 행·설정 입력을 제거했다.
- Chrome·Edge는 CSP 0건, 콘솔은 종료 확인 GET의 예상된 404 한 건이다. Firefox는 CSP·콘솔 오류 0건이다.
- WebKit은 실행마다 select 생성의 `style-src-attr` 64건과 캡처의 `style-src-elem` 15건을 보고했다. 콘솔은 이 거부 79건과 예상된 404 한 건이다. `select-probe.json`의 분리 재현에서 스타일 속성 없는 select만 보고를 만들고 div는 만들지 않았다. 캡처 직전·직후 차이로 캡처 보고를 구분했다. 제품 CSP는 완화하지 않았다. 제품 style 요소·속성은 0개이고 필수 행동은 모두 동작했다.
- 증거 목록 `target/logs-engines/SHA256SUMS`는 351개 파일·98,271,828바이트이며 SHA-256은 `23e767997a7911d8a11b2bc50005e12067ffe15027efda6dc941741efe0a670e`다. 초기 시도 파일도 포함하므로 최종 16회 수와 구분한다. 시험용 VNC Relay·실행파일 복사본·계정 파일·임시 비밀번호·Firefox 프로필은 제거했다.

### 4.3 WebKit 인증·CSRF 관찰 기록

- 날짜·대상: 2026-11-07, `e71dcee` 위 대화상자 포커스 복귀 변경 작업 트리의 관리 API 인증 경로. 인증·CSRF 관찰은 대화상자 코드를 쓰지 않는다.
- 환경: Windows 10.0.26200 x64, Python 3.14.6, Playwright 1.64.1, WebKit 27.2(빌드 v2370), argon2-cffi 25.1.0. 루프백에서 실행한 debug VNC Relay와 로컬 공격·대조 페이지를 썼다.
- 방법: 저장소 밖 `D:/vr-tools/webkit-q135/check_auth.py`로 `Session`·`Basic` 401 탐색, 다른 사이트의 JSON·`no-cors`·폼 로그인, 정상 로그인 뒤 다른 사이트 조회·종료 요청을 관찰했다.
- 결과: JSON 로그인은 OPTIONS 401·CORS 헤더 없음 뒤 `TypeError`로 막혔다. `no-cors`의 `text/plain`과 폼 POST는 415였고 `Set-Cookie`가 없었다. 공격 뒤 쿠키는 0개였다. 정상 로그인 뒤 VNC Relay가 `SameSite=Strict`를 보냈지만 이 빌드는 `sameSite=None`으로 저장해 다른 사이트 GET 두 건에 쿠키를 실었고 200을 받았다. 공격 페이지는 불투명 응답만 받았다. 쿠키가 실린 종료 요청도 `X-CSRF-Token`이 없어 403이며 세션은 유지됐다. `text/plain` POST는 415였다.
- 판정 한계: `Session`·`Basic` 401 모두 JSON 본문을 보여 기본 인증 창 대조가 성립하지 않았다. 실제 Safari의 인증 창·SameSite 동작은 판정하지 못했다. Windows용 WebKit의 쿠키 처리 한계라는 해석은 추정이다.
- 증거: `target/webkit-q135/results-auth.json`, `relay-auth-run.jsonl`, 저장소 밖 `D:/vr-tools/webkit-q135/check_auth.py`와 `repro/`.

## 5. 중단 조건

- `cargo xtask tokens --check`의 종료 코드가 0이 아니면 3.2 이후 단계를 실행하지 않는다.
- `DASHBOARD_BROWSER`가 없거나 `--version`이 실행되지 않으면 3.3을 실행하지 않는다.
- `data-result`가 `pass`가 아닌 테스트 페이지가 하나라도 있으면 실패로 기록하고 3.4 이후를 실행하지 않는다.
- 브라우저 네트워크 목록에 대시보드 출처 밖 요청이 있으면 중단한다. 외부 자원 금지는 [프런트엔드 컨벤션 1.3절](../conventions/frontend.md)을 따른다.
- 스크린샷에 가로 스크롤이 생기면 그 폭을 실패로 기록하고, 나머지 폭은 계속 확인한다.
