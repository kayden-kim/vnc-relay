# 아키텍처 문서 작성 규칙

[상위 규칙](../AGENTS.md)을 따르며 다음을 추가한다.

## 시작 템플릿

| 템플릿 | 사용할 질문 |
| --- | --- |
| [코드 지도](../templates/code-map.template.md) | 코드 위치·진입점·구성요소와 대표 요청의 흐름 |
| [도메인 모델](../templates/domain-model.template.md) | 용어집의 업무 용어가 코드의 어떤 타입·파일·관계로 표현되는가 |
| [모듈 설계](../templates/module-design.template.md) | 한 모듈의 내부 구조·데이터·처리 순서·초기화 |
| [관점별 아키텍처 문서](../templates/architecture-view.template.md) | 배포·보안·전환 계획 등 특정 구조 질문 |

코드 지도, 도메인 모델, 모듈 설계는 전체 구조에서 파일·함수까지 따라갈 수 있게 작성한다.

## 작성 규칙

- 한 문서는 하나의 구조 질문에 답한다. 외부 동작과 교환 형식은 관련 스펙·계약을 연결한다.
- 프로젝트마다 코드 지도 하나를 둔다. 코드가 있으면 실제 구조를 `Current`로 기록한다. 코드가 없으면 계획 경로를 `Target`으로 기록한다. 구현 후 경로·심볼·흐름을 대조하고 `Current`로 바꾼다.
- 모듈 설계는 내부 구조·데이터·처리 순서·초기화를 정한다. 구현 전에는 `Target`으로 작성하고 채택된 범위를 `Active`로 표시한다.
- 채택된 단계적 전환은 `Transitional`로 표시한다. 현재 코드와의 차이·전환 계획을 기록한다. 구현이 설계와 일치하면 `Current`로 바꾼다.
- 설계 선택의 별도 기록은 [ADR 작성 조건](../decisions/AGENTS.md)을 따른다. 기준과 코드의 충돌은 [상위 규칙](../AGENTS.md#기준-문서-적용과-충돌-처리)을 따른다.
- 코드 위치는 저장소 기준 파일 경로와 심볼(클래스·함수 이름)로 적는다. 자주 바뀌는 줄 번호는 적지 않는다.
- 코드의 구조나 흐름이 바뀌면 코드 지도와 관련 모듈 설계를 같은 변경에서 갱신한다.
- 현재 구조(`Current`)와 목표 구조(`Target`)를 한 다이어그램에 섞지 않는다. 도메인 모델만 예외다. 아직 코드에 없는 요소에 템플릿의 계획 표시를 붙이면 한 그림에 함께 그릴 수 있다.
- 다이어그램의 모든 화살표 의미(호출, 데이터 전달, 처리 순서, 의존 관계)를 밝히고 의존 방향과 경계를 함께 설명한다.
- 코드 구조는 클린 아키텍처를 따라야 한다. 클린 아키텍처는 업무 규칙을 중심에 두고, UI·DB·외부 서비스 같은 바깥 레이어가 안쪽 레이어에 의존하게 하는 구조다. 안쪽 레이어는 바깥 레이어를 알지 못한다.
- 의존은 단방향이어야 하고, 레이어 사이의 경계는 명확해야 한다.
- 레이어 목록, 레이어별 허용 의존, 경계, 의존 위반 확인 방법(도구 또는 리뷰)은 코드 지도의 레이어 표에 기록해야 한다.
- 이 구조에서 벗어나려면 [ADR](../decisions/AGENTS.md)을 작성해야 한다.
- 구현 대조 상태와 증거는 [검증 기록](../AGENTS.md#검증-기록)을 따른다.

## 도메인 모델

도메인 모델은 용어집·스펙과 코드를 잇는 문서다. 용어집의 업무 용어마다 그 용어를 표현하는 코드 타입, 파일, 다른 모델과의 연결, 코드가 지키는 조건의 위치를 적는다. 개발자는 이 문서로 업무 용어에서 코드로, 코드에서 업무 용어로 오갈 수 있다.

업무 결정과 코드 대응은 아래 순서로 정한다.

1. 용어집에서 용어의 이름과 뜻을 정한다.
2. 스펙에서 개념 사이의 관계(소속·개수), 상태와 전이, 항상 지켜야 할 조건을 정한다.
3. 스펙이 채택되면 구현 전에 도메인 모델을 `Target`으로 쓴다. 정한 개념과 관계를 어떤 코드 타입·필드로 만들지 계획한다.
4. 구현한 뒤 실제 코드 심볼과 대조해 `Current`로 바꾼다. 코드가 이미 있으면 처음부터 `Current`로 쓴다.

- 맥락(용어집)마다 도메인 모델을 하나 둔다. 맥락이 하나면 `domain-model.md`, 여럿이면 `<맥락 이름>-domain-model.md`로 이 디렉터리에 둔다. 해당 용어집의 "코드와의 대응" 줄에 이 문서를 연결한다.
- 용어집 용어를 표현하는 타입만 넣는다. 같은 개념의 저장 형식·API 스키마 같은 다른 레이어의 표현은 그 타입의 행에 함께 연결한다. 업무 의미가 없는 유틸리티·설정 타입은 넣지 않는다.
- 용어의 뜻은 용어집을, 관계와 조건의 업무 의미는 PRD·스펙을 링크한다. 이 문서에서 다시 정의하지 않는다.
- 모듈 설계의 데이터 모델 표에는 모듈 안에서만 쓰는 데이터를 적는다. 도메인 모델에 있는 타입은 링크한다.
- 업무 개념을 표현하는 코드 타입을 추가·이름 변경·삭제하거나 필드·관계·조건을 바꾸면 같은 변경에서 도메인 모델을 고친다. 새 용어가 필요하면 용어집을, 업무 관계·조건이 바뀌면 스펙을 먼저 고친다.
- 용어집의 영어 이름과 코드 심볼이 다르거나, 용어집에 없는 모델이 코드에 있거나, 코드의 관계·개수가 스펙과 다르면 "용어집·스펙과 코드의 차이"에 적는다. 차이를 숨기지 않아야 기준 문서와 코드가 멀어지는 것을 알아챌 수 있다.
- 변경 보고는 루트 지침의 [도메인 모델과 용어](../../AGENTS.md#도메인-모델과-용어)를 따른다.

종류 열에는 아래 DDD(도메인 주도 설계) 이름을 쓴다. 코드나 채택된 설계에서 확인한 종류만 적는다. 확인할 수 없으면 `구분 없음`으로 적는다. 종류를 추정해 붙이면 독자가 코드에 없는 구조를 찾게 된다.

| 종류 | 뜻 |
| --- | --- |
| 애그리거트 루트(aggregate root) | 함께 바뀌고 함께 저장되는 모델 묶음의 대표다. 묶음 밖에서는 루트를 거쳐서만 묶음 안의 모델을 바꾼다. |
| 엔티티(entity) | 식별자로 구분하는 모델이다. 속성이 바뀌어도 같은 대상이다. |
| 값 객체(value object) | 식별자 없이 값으로 같은지 판단하는 모델이다. 예: 금액, 주소. |
| 도메인 이벤트(domain event) | 업무상 의미 있는 일이 일어났다는 기록이다. 예: 주문 완료됨. |
| 상태 값 | 업무 상태를 나타내는 열거형 값이다. 상태 전이 규칙은 스펙이 정한다. |
