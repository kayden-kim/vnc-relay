## 1. 결정

중계 접근 통제는 TCP Viewer, TCP Server, WS Viewer, WSS Viewer 진입점마다 둔 출발지 IP 허용 목록 하나로 한다. 판정에는 소켓의 실제 상대 주소만 쓴다. UltraVNC Repeater의 초기 교환에 인증 필드를 추가하지 않는다. 중계 ID는 인증 수단이 아니다.

항목 형식과 목록 오류 처리는 [PRD](../requirements/PRD.md#확정-기준)와 [설정 계약](../contracts/config-v1.md)이 정한다. 이 ADR은 그 형식을 다시 쓰지 않는다.

## 2. 배경

Repeater 중계는 Viewer와 Server가 같은 ID를 대면 연결된다. ID를 아는 쪽이 누구인지 확인하는 단계는 없다. VNC Relay가 인터넷에 열리면 ID를 추측하거나 엿들은 쪽이 세션을 가로챌 수 있다. 접근 통제를 어디에 둘지 정해야 한다.

- 맥락 없이 보면 의외인 점: 중계 접속에 사용자 이름·비밀번호·토큰이 없다. 관리자 로그인이 있는데도 중계 접속은 관리자 로그인과 무관하다. 코드를 읽는 사람은 "인증 없이 열어 두는가"라고 물을 수 있다.
- 되돌리기 어려운 이유: 인증 필드를 초기 교환에 넣으면 기존 UltraVNC Viewer·Server와 맞지 않을 수 있다. 이미 배포한 클라이언트가 생기면 교환 형식을 바꿀 수 없다. 또 이 선택은 진입점별 목록, 수락 직후 판정, 재로드 대상, 로그 경고의 기준이 된다.
- 제약: 초기 교환의 실제 바이트 형식은 아직 관찰하지 않았다([RLY-TBD-002](../specs/relay.md#8-미결정-사항)). 추가 필드가 실제 제품과 호환되는지는 확인되지 않았다.

## 3. 결정 요인

1. 기존 UltraVNC Viewer·Server를 수정하지 않고 쓸 수 있는가.
2. 비인가 접속을 막는 시점. 데이터를 읽기 전에 거절할수록 자원 소모가 작다.
3. 우회 가능성. 클라이언트가 보낸 값으로 판정을 바꿀 수 없어야 한다.
4. TCP·WS·WSS 세 경로에 같은 모델을 적용할 수 있는가.
5. 운영 부담. 목록 변경이 재시작 없이 가능해야 한다.
6. 개별 사용자 구분 능력.

## 4. 선택 근거

1. 호환. 허용 목록은 접속 수락 시점의 소켓 정보만 쓴다. Repeater 교환 바이트를 바꾸지 않는다. 필드 추가의 호환성은 관찰 전이어서 지금 전제할 수 없다.
2. 판정 시점. TCP는 수락 직후 데이터를 읽기 전에, WS·WSS는 수락 직후(TLS·HTTP 처리 전)와 업그레이드 직전에 검사한다([WS-R10](../specs/websocket.md#3-정상-흐름과-규칙)). 비허용 출발지는 초기 교환·대기 등록·대상 연결에 도달하지 못한다([RLY-023](../specs/relay.md#7-수용-테스트)).
3. 우회 가능성. 관리자 쿠키, 중계 ID, 전달 헤더는 판정에 쓰지 않는다([WS-014](../specs/websocket.md#7-수용-테스트), [MGT-015](../specs/management.md#7-수용-테스트)). 이 조건은 서버가 TLS와 소켓을 직접 소유할 때만 지켜진다([ADR-0001](ADR-0001-built-in-tls.md)).
4. 공통 모델. 네 진입점이 같은 규칙으로 목록을 평가한다. 진입점마다 목록이 따로여서 한 진입점의 허용이 다른 진입점으로 번지지 않는다([OPS-037](../specs/operations.md#7-수용-테스트)).
5. 운영 부담. 허용 목록은 재시작 없이 바꾸는 재로드 대상이다([운영 스펙 3.3절](../specs/operations.md#33-파일-변경-자동-감지와-부분-재로드)). 이미 허용한 연결은 유지한다.
6. 개별 사용자 구분. 이 선택은 구분 능력이 없다. 같은 공인 IP를 쓰는 사용자는 구분되지 않는다([PRD 7절](../requirements/PRD.md#7-보안-및-신뢰-경계)). 이 한계를 알고 수용한다.

브라우저의 Origin 검사는 WS·WSS에만 추가한다. Origin은 사용자 인증 수단이 아니다([WS-027](../specs/websocket.md#7-수용-테스트)). Origin 헤더가 없는 비브라우저 클라이언트는 IP 검사만 받는다([WS-021](../specs/websocket.md#7-수용-테스트)).

## 6. 결과

### 긍정적 결과

- 기존 UltraVNC Viewer·Server와 같은 초기 교환을 유지할 수 있다.
- 비허용 출발지는 데이터를 읽기 전, WSS는 TLS 협상 전에 끊는다.
- 세 전송 경로가 같은 검사 규칙과 같은 설정 형식을 쓴다.

### 부정적 결과와 비용

- 허용 IP 안의 개별 사용자를 구분하지 못한다. 같은 공인 IP를 공유하는 사용자 한 명이 ID를 알면 같은 권한을 가진다.
- 접속 IP가 자주 바뀌는 사용자는 운영자가 목록을 갱신해야 한다.
- 목록을 잘못 쓰면 공개 허용이 된다. `0.0.0.0/0`·`::/0`은 허용하되 경고를 남기는 것으로 완화한다.
- 허용 목록은 VNC Relay의 앞단에서 NAT나 프록시가 출발지 주소를 바꾸는 환경에서는 쓸 수 없다. 그 환경은 지원 대상이 아니다.

### 후속 작업

- 설정 계약: `allow` 키와 항목 형식 오류 처리를 확정한다.
- 운영 정보 계약: 전체 허용 경고와 거절 사건의 로그 이름을 정한다.
- 설정 계약: Origin 값 문법과 정규화(WS-TBD-003)를 정한다([설정 계약 1.4절](../contracts/config-v1.md#14-origin-값-문법과-비교)). WebSocket 중계 계약은 그 규칙을 인용한다.
- 호환 관찰 후 초기 교환에 확장 여지가 있는지 기록한다(RLY-TBD-002). 형식은 [Repeater 초기 교환 계약](../contracts/repeater-handshake-v1.md)이 관찰 뒤에 정한다.

## 8. 재검토 조건

- 허용 IP 안의 사용자 때문에 무단 접속이나 세션 탈취가 발생했다는 사고 기록이 생긴다.
- 호환 관찰(RLY-TBD-002)에서 대상 UltraVNC 버전의 Viewer·Server가 초기 교환에 추가 인증 정보를 안전하게 실을 수 있다는 근거가 기록된다.
- 운영자의 허용 목록 변경 요청이 재로드 운영 한계를 넘어 반복해서 접수된다.
- VNC Relay 앞단에 출발지 주소를 바꾸는 장치를 둔 배치가 PRD 범위에 들어온다.
