## 1. 결정

VNC Relay는 프로세스 하나로 운영한다. 다음 상태를 그 프로세스의 메모리에만 둔다.

- Mode II 대기 등록
- 활성 세션
- 전송량과 연결 수 카운터
- 관리 세션
- 최근 종료 목록

프로세스가 끝나면 이 상태는 모두 사라진다. 관리자는 재시작 뒤 다시 로그인해야 한다. 외부 저장소, 다중 노드 공유, 서명 토큰 방식의 관리 세션은 쓰지 않는다. 장기 기록은 운영 로그(JSON Lines)가 맡는다.

## 2. 배경

운영 서버는 보통 재시작해도 로그인과 이력을 유지하고, 필요하면 노드를 늘릴 수 있게 설계한다. 이 프로젝트는 그 방향을 택하지 않았다.

- 맥락 없이 보면 의외인 점: 서버를 재시작하면 관리자가 쫓겨나고 최근 종료 목록이 비며 대기 연결이 사라진다. 코드를 읽는 사람은 "세션 저장소나 서명 토큰을 쓰면 되는데 왜 메모리인가"라고 물을 수 있다. 같은 주소로 두 번째 프로세스를 띄우면 시작 실패인 점도 의외다.
- 되돌리기 어려운 이유: 매칭의 원자성, 활성 수 집계, 세션 종료 요청의 대상 확인, 관리 세션 검증이 모두 "상태 소유자는 이 프로세스 하나"라는 가정 위에 있다. 다중 노드로 바꾸려면 이 네 가지를 다시 설계하고 세션이 어느 노드에 있는지 찾는 방법도 새로 정해야 한다.
- 제약: 규모 목표는 단일 서버의 활성 100세션이다([PRD 확정 기준 "초기 규모"](../requirements/PRD.md#확정-기준)). 배포는 실행파일 하나이며 외부 데이터베이스나 컨테이너 오케스트레이션은 범위 밖이다. 다중 노드 매칭과 클러스터링은 제외 범위다([4.2](../requirements/PRD.md#42-제외)).

## 3. 결정 요인

1. 매칭의 원자성과 활성 수의 정확성. 한 연결은 한 세션에만 속해야 한다.
2. 중계 TCP 연결의 수명과 상태의 수명 일치. 소켓은 프로세스가 소유한다.
3. 관리 세션의 즉시 폐기 가능성(로그아웃, 만료, 재시작).
4. 구현·운영 구성 요소 수.
5. 규모 목표 적합성(활성 100세션).
6. 재시작 때 잃는 정보의 크기와 대체 수단.

## 4. 선택 근거

1. 원자적 매칭. 대기 등록과 활성 세션이 한 프로세스 안에 있으면 매칭 전이를 한 곳에서 결정할 수 있다([RLY-013](../specs/relay.md#7-수용-테스트), [RLY-014](../specs/relay.md#7-수용-테스트)). 외부 저장소를 쓰면 같은 결정을 저장소 수준의 원자적 연산으로 다시 만들어야 한다.
2. 수명 일치. 중계 중인 TCP 연결은 프로세스가 끝나면 함께 끊긴다. 상태만 살려도 이어 갈 연결이 없다. 그래서 재시작 뒤 세션 복구와 자동 재매칭은 보장하지 않는다([FR-07](../requirements/PRD.md#fr-07-설정과-프로세스-수명)). 대기·활성·카운터를 영속화할 이유가 약하다.
3. 관리 세션. 서버 메모리의 불투명 식별자 쿠키는 로그아웃·만료·재시작에서 서버가 바로 무효화할 수 있다([MGT-020](../specs/management.md#7-수용-테스트), [MGT-027](../specs/management.md#7-수용-테스트)). 서명 토큰은 서버가 상태를 안 갖는 대신, 만료 전에 토큰을 폐기하려면 서버가 폐기 목록을 따로 가져야 한다. 이 점은 일반적인 설계 판단이며 이 프로젝트에서 테스트로 확인하지 않았다.
4. 구성 요소 수. 외부 저장소는 설치·접근 통제·장애 대응 대상을 하나 더 만든다. 배포 범위(실행파일·설정 예시·수동 운영 안내)에 들어 있지 않다.
5. 규모. 목표는 단일 서버의 활성 100세션이다. 이 규모에서 공유 상태가 필요한 근거는 지금 없다. 단일 프로세스가 이 목표를 채우는지는 측정 전이다([OPS-018](../specs/operations.md#7-수용-테스트)).
6. 손실과 대체. 잃는 정보는 최근 종료 목록, 카운터, 관리 세션이다. 장기 추적은 로그가 맡는다. 최근 종료 목록은 장기 이력 검색이 아니다([MGT-024](../specs/management.md#7-수용-테스트)).

단일 인스턴스는 규칙으로 강제한다. 이미 사용 중인 리스너 주소로 두 번째 프로세스를 시작하면 시작에 실패한다([OPS-R23](../specs/operations.md#41-판정-가능한-규칙)). 이 규칙이 검출하는 조건은 리스너 주소 충돌이다. 다른 주소로 띄운 두 번째 프로세스를 이 규칙이 막는지는 스펙에 쓰여 있지 않다.

## 6. 결과

### 긍정적 결과

- 매칭과 카운터가 한 프로세스 안에서 결정되어 경쟁 상태를 한 곳에서 다룬다.
- 실행파일 하나와 설정 파일로 운영할 수 있다. 외부 저장소가 필요 없다.
- 관리 세션이 서버 안에서 즉시 무효화된다.

### 부정적 결과와 비용

- 재시작하면 대기·활성 세션이 끊기고 카운터와 최근 종료 목록이 초기화된다.
- 관리자는 재시작 뒤 다시 로그인해야 한다.
- 고가용성이 없다. 프로세스 장애는 모든 세션의 종료로 이어진다.
- 수평 확장을 지원하지 않는다. 100세션을 넘는 부하는 이 구조로 보장하지 않는다.
- 종료 이력은 운영 로그에만 남는다. 로그 보관은 운영자 책임이다.

### 후속 작업

- 운영 정보 계약: 세션 종료와 관리자 종료 사건을 로그로 남기는 형식을 정한다.
- 관리 API 계약: 재시작 뒤 이전 쿠키 거절 응답을 정한다.
- 성능 측정 계획: 활성 100세션 목표를 측정한다(OPS-TBD-004).

## 8. 재검토 조건

- OPS-018 측정에서 단일 프로세스가 활성 100세션 목표나 채택한 성능 지표를 두 대상 OS 중 한 곳에서 충족하지 못한다.
- 운영자가 무중단 재시작 또는 다중 노드 운영을 요구하는 이슈가 접수되고 PRD 제외 범위가 바뀐다.
- 재시작 뒤 재로그인이나 목록 소실 때문에 운영 조치가 지연되었다는 사고 기록이 반복해서 생긴다.
- 장기 세션 이력 검색이 PRD 요구사항으로 채택된다.
