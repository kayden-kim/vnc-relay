# ADR-0005: WebSocket 데이터 프레임 처리는 자체 스트리밍 상태 머신을 쓴다

## 1. 결정

- WebSocket 데이터 프레임 처리는 자체 스트리밍 상태 머신을 쓴다.
- tungstenite 0.30.0에서는 공개 함수·구조체인 `FrameHeader::parse`/`format`과 `handshake::derive_accept_key`만 재사용한다.
- 나머지 페이로드 청킹, 인플레이스 언마스킹(청크 간 마스크 오프셋 modulo 4), 프레임 분할(fragmentation), 제어 프레임 인터리빙, Close 상태 머신은 RFC 6455만으로 자체 구현한다.
- UltraVNC, websockify, noVNC 소스를 읽거나 복사·번역·포팅하지 않는다.
- 새 crate 의존성을 추가하지 않는다.
- 버퍼 상한 B와 논리 메시지 상한 M 사이에는 크기 제약이 없다(사용자 결정 2026-11-01(Q78)). 프레임 안에서 스트리밍하며, 방향당 미전달 보관 바이트는 B 이하다. 분할 프레임을 합친 논리 메시지 크기가 M을 넘으면 1009로 닫고 추가 전달을 멈춘다. B보다 큰 유효 프레임도 수락해 스트리밍하며 전체를 저장하지 않는다.

## 2. 배경

[ADR-0004](ADR-0004-tokio-rustls.md)와 [PRD 구현 기술](../requirements/PRD.md#확정-기준)에 따라 비동기 런타임은 tokio, WebSocket 라이브러리는 tokio-tungstenite 0.30.0(하위 tungstenite 0.30.0)을 채택했다.

- 맥락 없이 보면 의외인 점: tungstenite 0.30.0은 완전한 WebSocket 프로토콜 라이브러리다. 그럼에도 이 프로젝트는 tungstenite의 고수준 스트림·메시지 수신 API(`WebSocketStream`, `Message`)를 쓰지 않고, 프레임 헤더 파서와 accept_key 도우미만 빌려 쓰며 스트리밍 프레임 코덱을 직접 작성한다. 코드를 읽는 사람은 "완전한 WebSocket 라이브러리가 있는데 왜 프레임 코덱을 직접 작성했는가"라고 물을 수 있다.
- 되돌리기 어려운 이유: WebSocket 프레임 처리 방식은 중계 버퍼 상한(B) 준수, 논리 메시지 크기(M) 계산, 비동기 I/O 루프 구조, 스트림 어댑터(`RelayStream`) 구현에 깊이 맞물린다. 나중에 구조를 바꾸면 스트리밍 중계와 프레임 분할 테스트 전체가 영향을 받는다.
- 문제와 제약: tungstenite 0.30.0의 고수준 API는 메시지 또는 프레임 전체를 메모리에 모아서 전달한다. 그러나 [설정 계약](../contracts/config-v4.md)의 연결당 버퍼 상한 B는 16 KiB~4 MiB이고, 논리 메시지 상한 M은 64 KiB~16 MiB다. 유효한 설정에서 M > B가 가능하고, B보다 큰 단일 프레임이 올 수 있다. 프레임 전체를 모은 뒤 전달하면 연결당 버퍼 상한 B를 넘겨 메모리를 점유하므로 계약을 위반한다.

## 3. 결정 요인

1. B보다 큰 유효 단일 프레임을 프레임 크기 전체 버퍼링 없이 청크 단위로 스트리밍해 방향당 미전달 바이트 상한 B를 지킬 수 있는가.
2. 프레임 분할을 합친 논리 메시지 크기 M을 정확히 계산하고 초과(M+1) 시 종료 코드 1009로 즉시 중단할 수 있는가.
3. 새 crate 의존성을 추가하지 않고 프로젝트 라이선스 허용 목록 안에서 해결할 수 있는가.
4. UltraVNC·websockify 소스를 보지 않고 RFC 6455만으로 독립 구현할 수 있는가.

## 4. 선택 근거

1. 스트리밍 버퍼 상한 B 준수: tungstenite의 `FrameSocket::read`와 `FrameCodec::read_frame`은 선언된 페이로드 길이만큼 버퍼를 확보하고 프레임 전체를 다 읽은 뒤에만 반환한다. 완성 프레임 API를 그대로 쓰면 B보다 큰 프레임을 B 이내의 청크로 쪼개어 중계할 수 없다. 반면 `FrameHeader::parse`는 헤더(최대 14바이트)만 해석하므로, 페이로드는 호출자 버퍼(≤ B)로 직접 읽어 제자리에서 마스크를 해제하면서 즉시 TCP로 전달할 수 있다.
2. 논리 메시지 M 검사: RFC 6455 5.4절의 분할 프레임 규칙에 따라 첫 프레임부터 FIN 프레임까지의 페이로드 바이트 누적 합계를 검사하고, M을 초과하면 1009로 닫는다.
3. 의존성 제약 준수: 이미 잠금 파일에 포함된 tungstenite 0.30.0의 공개 모듈을 재사용하므로 Cargo 의존성을 하나도 늘리지 않는다.
4. 독립 구현 원칙: RFC 6455 표준 문서의 프레임 명세·마스킹 알고리즘(XOR)·상태 전이 규칙만으로 구현하므로 외부 구현체 소스를 볼 필요가 없다.

## 5. 대안

| 대안 | 버퍼 B 준수 | M 검사 | 새 의존성 | 제외 이유 |
| --- | --- | --- | --- | --- |

## 6. 결과

### 긍정적 결과

- B보다 큰 대용량 프레임이 들어와도 메모리를 B 이하로 엄격히 제한하면서 TCP로 흘려보낼 수 있다.
- 새 crate 의존성을 늘리지 않고 기존 의존성 안에서 해결한다.
- RFC 6455에 명시된 규칙만으로 작성되어 라이선스 및 코드 독립성이 명확하다.

### 부정적 결과와 비용

- 프레임 파싱 상태 머신, 페이로드 청킹, 인플레이스 언마스킹, 제어 프레임 인터리빙, Close 핸드셰이크 상태를 프로젝트에서 직접 유지보수하고 테스트해야 한다.

### 후속 작업

- `crates/adapters/src/websocket_stream/`에 자체 스트리밍 코덱 및 `RelayStream` 어댑터를 구현한다.
- WS-007~WS-011, WS-018, WS-019에 대한 단위·통합 테스트를 작성한다.

## 8. 재검토 조건

- tungstenite 차기 버전에서 B 이내 청킹 스트리밍을 지원하는 공식 무할당 스트림 API를 제공한다.
- RFC 6455 프레임 처리에서 해결하기 어려운 프로토콜 취약점이 발견된다.
