## 1. 결정

내장 TLS는 유지한다. 중계 WS·WSS 리스너 앞에서 역방향 프록시가 TLS를 종료하는 배치도 지원한다(사용자 지시 2026-11-08, 사용자 결정 2026-11-08(Q182)).

클라이언트 주소는 리스너별 `trusted_proxies`와 `X-Forwarded-For`로 구한다. 소켓 상대가 신뢰 프록시일 때만 헤더를 읽는다. 오른쪽부터 처음 만나는 비신뢰 주소를 쓴다. 소켓 상대가 신뢰 프록시가 아니면 전달 헤더를 무시한다. 정확한 주소 문법과 거절 규칙은 [WebSocket 계약](../contracts/websocket-relay-v2.md#18-신뢰-프록시와-x-forwarded-for)을 따른다.

관리 리스너는 이 지원에서 제외한다. 내장 HTTPS 또는 루프백 평문 HTTP만 허용하며 전달 헤더를 무시한다. 쿠키의 Secure 판단과 로그인 제한의 출발지 주소 기준도 유지한다(사용자 결정 2026-11-08(Q183)). 프록시 인증 종료와 중계 접속 토큰은 이 결정의 범위가 아니다.

## 2. 배경

[ADR-0001](ADR-0001-built-in-tls.md)은 프록시 TLS 종료를 지원 대상에서 제외했다. 사용자 지시 2026-11-08이 공식 지원을 요구했고, 사용자 결정 2026-11-08(Q182)이 신뢰 프록시와 전달 헤더 방식의 주소 판정을 선택했다. 따라서 ADR-0001의 8절 재검토 조건이 충족되었다.

- 맥락 없이 보면 의외인 점: 수락 직후 소켓 주소로만 검사하던 제품이 특정 상대의 HTTP 전달 헤더를 주소 판정 근거로 사용한다.
- 되돌리기 어려운 이유: 주소의 신뢰 경계가 설정, 검사 시점, 운영 로그와 배포 절차에 걸쳐 바뀐다. 주소 의미를 잘못 바꾸면 허용 정책을 우회할 수 있다.
- 범위: 중계 WS·WSS 리스너만 바꾼다. TCP와 관리 리스너의 전달 주소 처리는 추가하지 않는다.

## 3. 결정 요인

1. 클라이언트 주소의 신뢰 근거와 위조 방지.
2. 비허용 접속을 차단하는 시점.
3. HTTP 역방향 프록시와의 연동 및 적용 전송 범위.
4. 운영·설정 부담과 로그의 주소 추적성.

## 4. 선택 근거

사용자 결정 2026-11-08(Q182)이 리스너별 신뢰 프록시 목록과 `X-Forwarded-For`를 채택했다. 신뢰 목록 밖의 소켓 상대는 헤더를 보내도 판정을 바꾸지 못한다. 헤더를 오른쪽부터 검사하므로 첫 비신뢰 주소 왼쪽에 덧붙인 위조 값은 쓰지 않는다.

신뢰 프록시는 수락 때 역할 목록 검사를 건너뛴다. 따라서 프록시 주소를 클라이언트 주소 대신 쓸 수 없다. 헤더가 없거나 비어 있거나 검사 중 잘못된 요소가 나오면 거절한다. 모든 요소가 신뢰 프록시인 체인도 `forwarded_for_invalid`로 거절한다. 프록시 주소가 역할 허용 목록에 있어도 같다. 이때 등록과 `forwarded_ip`는 없다. `trusted_proxies`에는 프록시 주소만 넣어야 하며 클라이언트 범위를 넣어서는 안 된다.

## 6. 결과

### 긍정적 결과

- 내장 TLS 배치를 유지하면서 중계 WS·WSS의 프록시 TLS 종료를 공식 지원한다.
- 운영 로그의 `peer_ip`를 소켓 IP로 유지하고 `forwarded_ip`를 추가해 두 주소를 구분한다.
- 공유 리스너의 역할 구분은 [ADR-0008](ADR-0008-shared-ws-listener-path-roles.md)을 따른다. 역할별 허용 목록을 전달 주소에도 적용한다.

### 부정적 결과와 비용

- 수락 때 보이는 주소는 프록시 주소다. 프록시를 거친 클라이언트의 허용 검사는 업그레이드 시점으로 옮겨간다.
- 잘못된 신뢰 목록은 주소 위조를 허용할 수 있다. 전체 신뢰 목록 경고 `trust_all_proxies`의 이름은 당시 미채택이었다. 후속: 사용자 결정 2026-11-08(Q191)으로 이름과 필드 `listener`·`item`·`phase`를 채택했다.
- 신뢰 프록시 호스트나 신뢰 범위 안에서 시작한 요청은 프록시를 거치면 모두 신뢰 주소인 체인으로 거절될 수 있다. 같은 출발지의 직접 접속도 신뢰 프록시 연결로 취급한다. 그래서 유효한 전달 헤더가 없으면 거절되고, 있으면 같은 전달 주소 판정과 역할 허용 목록 검사를 받는다. 전달 헤더 없이 직접 접속하려면 출발지가 그 리스너의 `trusted_proxies` 밖에 있고 해당 역할의 허용 목록에 들어야 한다.
- 운영자가 프록시→VNC Relay 구간을 보호해야 한다. 앞단 TLS 종료만으로 이 구간의 암호화를 보장하지 않는다.
- 직접 연결과 프록시 연결의 주소 판정·재로드 조합을 추가 검증해야 한다.

## 8. 재검토 조건

- (해결) 전체 신뢰 경고 사건·코드 `trust_all_proxies`와 필드 `listener`·`item`·`phase`는 사용자 결정 2026-11-08(Q191)으로 채택했다.
- 관리 리스너나 TCP의 프록시 전달 주소 지원이 요구사항으로 채택된다.
- 신뢰 프록시 설정이나 체인 해석 때문에 접근 정책 우회 사고가 기록된다.
