## 1. 결정

중계 접근 통제는 진입점별 출발지 IP 허용 목록과 중계 진입점 여섯 곳이 함께 쓰는 출발지 IP 차단 목록 하나로 한다. 차단 목록은 설정 `[relay.deny]`의 `sources`이며 기본값은 `[]`다. 차단 목록은 허용 목록보다 우선한다. 차단 목록의 `[]`는 아무것도 차단하지 않는다(사용자 결정 2026-11-20).

- 적용 범위: TCP Viewer, TCP Server, WS Viewer, WS Server, WSS Viewer, WSS Server. 관리 리스너와 상태 리스너에는 적용하지 않는다.
- 만료: 없다. 운영자가 목록에서 지울 때까지 차단한다.
- 교체 직후 끊기: 차단 목록이 바뀌면 그 주소의 열린 활성 세션과 대기 연결을 바로 끊는다. 파일을 고쳐 재로드한 경우와 대시보드에서 편집한 경우가 같다.
- 신뢰 프록시 겹침 금지: 차단 항목이 신뢰 프록시 주소와 겹치면 설정 오류로 거절한다.
- 대시보드 차단·해제: 기존 설정 편집 경로와 권한(`PATCH /api/v1/config`, `management.config_edit = true`일 때만)을 쓴다. 차단·해제 전용 API는 두지 않는다.
- 화면: SCR-008 접속 출처의 주소별 표에 [차단]·[차단 해제]와 "차단됨" 배지를 둔다. 항목은 SCR-004·005 설정 화면에서도 편집한다.

[ADR-0002](ADR-0002-source-ip-allowlist.md)의 결론은 그대로 이어받는다. 접근 통제는 진입점별 허용 목록이다. 판정은 수락 직후에 한다. 초기 교환에 인증 필드를 추가하지 않는다. 이 ADR은 차단 목록, 차단 우선순위, 교체 직후 끊기, 프록시 겹침 금지를 더한다.

항목 문법, 검사 순서, 종료 코드와 close 코드, 로그·메트릭 값은 [설정 계약](../contracts/config-v4.md)과 각 스펙·계약이 정한다. 이 문서는 그 내용을 다시 쓰지 않는다.

## 2. 배경

허용 목록만으로는 이미 접속한 출처를 막을 수 없다. 허용 목록을 고쳐도 이미 통과한 판정과 열린 연결은 유지된다([PRD 확정 기준 "IP 변경 효과"](../requirements/PRD.md#확정-기준)). 운영자는 문제가 있는 주소를 여섯 진입점의 목록에서 각각 빼야 한다. 허용 범위가 넓은 CIDR 안의 주소 하나를 막으려면 그 항목을 고쳐 써야 한다.

- 맥락 없이 보면 의외인 점: 허용 목록에 있는 주소도 차단 목록에 있으면 거절된다. 만료가 없고, 대시보드에서 주소 하나를 차단하면 열린 세션이 바로 끊긴다. 차단 목록의 `[]`와 허용 목록의 `[]`는 뜻이 반대다. 신뢰 프록시와 겹치는 차단 항목은 설정 오류다.
- 되돌리기 어려운 이유: 설정 키 `relay.deny.sources`, 재로드·편집 대상 키 수, 거절·종료 원인 값 `ip_denied`, WebSocket close 코드, 관리 API의 `GET /api/v1/sources` 필드, 화면의 차단 흐름이 이 선택을 그대로 드러낸다. 배포된 설정 파일과 운영 로그를 읽는 도구가 이 값에 의존하게 된다.
- 범위: 중계 접근 통제만 바꾼다. 관리 로그인 제한, 중계 ID 규칙, 접속 ticket 확인, Origin 검사, Mode I 대상 허용 정책은 바꾸지 않는다. [ADR-0003](ADR-0003-single-instance-memory-state.md)의 단일 인스턴스·메모리 상태를 유지한다.

## 3. 결정 요인

1. 즉시 대응. 문제가 있는 출처의 열린 연결까지 바로 끊을 수 있어야 한다.
2. 한 곳의 관리. 여섯 진입점에 같은 주소를 반복해서 적지 않아야 한다.
3. 기존 규칙 보존. 허용 목록의 규칙(진입점별 목록, 누락은 시작 실패, `[]`는 모두 거절)과 수락 직후 판정을 바꾸지 않는다.
4. 운영 부담. 재시작 없이 바꾸고, 같은 설정 파일에 남아 재시작 뒤에도 유지돼야 한다.
5. 권한 경계. 대시보드의 차단이 기존 설정 편집의 권한과 검증 규칙을 넘지 않아야 한다.
6. 사고 방지. 프록시 같은 공용 주소를 실수로 차단해 모든 접속이 막히는 일을 설정 단계에서 줄인다.

## 4. 선택 근거

사용자 결정 2026-11-20이 정한 범위와 동작이다. 아래는 결정 요인과의 연결이다.

1. 즉시 대응. 교체 직후 열린 활성 세션과 대기 연결을 끊는다. 허용 목록의 변경 규칙(열린 연결 유지)과 다르다. 차단은 "지금 이 주소를 내보낸다"는 행동이므로 새 접속만 막아서는 목적을 이루지 못한다.
2. 한 곳의 관리. 목록 하나가 여섯 진입점에 적용되고, 항목 문법은 허용 목록과 같다. 운영자는 새 문법을 배우지 않는다.
3. 기존 규칙 보존. 차단 검사는 허용 검사 앞에 더한다. 허용 목록과 `[]`의 의미는 그대로다. 초기 교환 바이트는 바꾸지 않는다([ADR-0002](ADR-0002-source-ip-allowlist.md)의 호환 근거가 유지된다).
4. 운영 부담. 차단 목록은 재로드·편집 대상 키다. 파일을 고치거나 대시보드에서 편집하면 같은 재로드 규칙으로 적용된다([ADR-0006](ADR-0006-config-edit-through-file.md)).
5. 권한 경계. 대시보드는 `GET /api/v1/config`로 읽고 `PATCH /api/v1/config`로 `relay.deny.sources` 전체 값을 보낸다. 로그인, CSRF, `management.config_edit`, 충돌 검사, 파일 쓰기 규칙을 그대로 쓴다. 새 권한이나 새 저장소가 생기지 않는다.
6. 사고 방지. 신뢰 프록시 주소를 차단하면 그 프록시를 거치는 모든 클라이언트의 접속이 막힌다. 그래서 차단 항목이 역할이 하나 이상 켜진 WS·WSS 리스너의 신뢰 프록시 항목과 한 주소라도 겹치면 설정 오류로 거절한다. 시작이면 시작 실패, 재로드·편집이면 후보 전체 거절이다.

판정 주소는 클라이언트 주소다. 신뢰 프록시를 거친 WS·WSS는 전달 주소이고, 나머지는 소켓 상대 주소다. 활성 세션은 Viewer의 클라이언트 주소 또는 Mode II Server의 클라이언트 주소가 차단되면 세션 전체를 끊는다. Mode I 대상 주소는 클라이언트가 아니므로 보지 않는다.

## 6. 결과

### 긍정적 결과

- 운영자는 주소 하나를 한 번에 모든 중계 진입점에서 막고, 열린 세션과 대기 연결도 바로 끊는다.
- 허용 목록의 규칙과 초기 교환 형식은 바뀌지 않는다.
- 대시보드의 차단·해제가 설정 파일에 남아 재시작 뒤에도 유지된다. 파일을 직접 고쳐도 같은 결과다.
- 프록시 주소를 차단해 모든 접속이 막히는 설정은 시작·재로드·편집 단계에서 거절된다.

### 부정적 결과와 비용

- 잘못 차단하면 열린 세션이 바로 끊긴다. 해제해도 끊은 연결은 되살아나지 않는다.
- 차단 목록의 `[]`는 아무것도 차단하지 않고 허용 목록의 `[]`는 모두 거절한다. 뜻이 반대여서 문서가 분명히 구분해야 한다.
- `0.0.0.0/0`·`::/0`을 차단 항목으로 쓰는 경우에 특별한 경고나 오류가 없다. 전체 출발지를 차단할 수 있다.
- 같은 공인 IP를 공유한 사용자는 구분되지 않고 함께 차단된다. 이 한계는 [ADR-0002](ADR-0002-source-ip-allowlist.md)와 같다.
- 대시보드의 [차단 해제] 버튼은 단일 주소 항목만 해제한다. 범위·CIDR 항목으로 차단된 주소는 설정에서 해제한다.
- 대시보드에서 차단하려면 `management.config_edit`를 켜고 재시작해야 한다. 꺼져 있으면 파일 편집과 재로드로만 차단한다.
- 재시작이 필요한 변경이 파일에 남아 있는 동안에는 재로드 후보 전체가 거절되므로 차단 변경도 적용되지 않는다([PRD 확정 기준 "재로드 거절 기준"](../requirements/PRD.md#확정-기준)).
- 재로드 대상은 44개 키, 편집 대상은 38개 키로 늘어난다. 끊은 연결을 요약하는 사건은 새로 두지 않는다.

### 후속 작업

- 설정 계약 4.4.0, 운영 정보 계약 2.3.0, 메트릭 계약 1.2.0, WebSocket 중계 계약 2.2.0, 관리 API 계약 1.5.0에 차단 목록의 키·원인 값·close 코드·응답 필드를 반영한다.
- PRD AC-66~68과 각 스펙 시나리오를 구현·테스트에 연결한다.
- 도움말과 운영 how-to에 차단 목록과 허용 목록의 `[]` 차이를 싣는다.
- 대시보드 SCR-004·005·008의 차단 화면은 화면 스펙을 따라 구현한다.

| 요인 5: 대시보드가 기존 설정 편집 경로와 권한을 쓴다 | [MGT-065](../specs/management.md#7-수용-테스트), [DASH-089~091](../specs/dashboard.md#7-수용-테스트) | 편집이 꺼져 있으면 버튼이 없고, 차단·해제는 `PATCH /api/v1/config`로만 반영됨 | 미실행 |

## 8. 재검토 조건

다음 재검토 조건은 이 ADR의 판단이다.

- 운영자의 임시 차단(만료) 요청이 반복해서 접수된다.
- 진입점마다 다른 차단 목록이 필요하다는 요청이 반복해서 접수된다.
- 주소가 아니라 사용자·계정 단위의 차단이 필요하다는 근거가 기록된다.
- 범위 항목으로 차단된 주소를 대시보드에서 해제해야 한다는 요청이 반복해서 접수된다.
- 다중 인스턴스를 도입하여 [ADR-0003](ADR-0003-single-instance-memory-state.md)의 상태 소유 기준이 바뀐다.
