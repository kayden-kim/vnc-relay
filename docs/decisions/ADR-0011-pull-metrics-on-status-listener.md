## 1. 결정

VNC Relay는 OpenTelemetry 의미 규칙(semantic conventions)의 이름·단위·속성을 따르는 메트릭을 제공한다. 외부 수집 도구는 상태 리스너의 `GET /metrics`에서 Prometheus 텍스트 형식 0.0.4로 값을 가져간다(pull). OpenTelemetry Collector의 Prometheus 수신기와 Prometheus가 이 형식을 읽는다. VNC Relay는 OTLP로 값을 보내지(push) 않는다(사용자 결정 2026-11-19).

`/metrics`는 `[metrics] enabled = true`일 때만 응답한다. 기본값은 `false`이며 바꾸면 재시작해야 한다. 꺼져 있으면 지금처럼 404다(사용자 결정 2026-11-19).

텍스트 형식과 관리 API의 JSON은 별도 메트릭 라이브러리 없이 직접 쓴다. OpenTelemetry SDK와 `prometheus` 계열 crate를 의존성에 넣지 않는다(사용자 결정 2026-11-19).

관리 API `GET /api/v1/metrics`와 대시보드 SCR-007 메트릭은 같은 값을 로그인한 관리자에게 항상 보여 준다. `[metrics] enabled`와 관계없다. 최근 1시간의 추이를 10초 간격 360개 점으로 메모리에 둔다. 이 간격과 개수는 설정 키 없이 고정한다(사용자 결정 2026-11-19).

## 2. 배경

지금까지 운영 정보는 JSON Lines 운영 로그와 `/livez`·`/readyz`뿐이었다. 상태 응답은 수·가동 시간·버전을 넣지 않았다. 대시보드는 현재 값만 보여 주고 추이를 남기지 않았다. 운영자가 거절 원인의 추세, 처리량, 지연 분포, 프로세스 자원을 보려면 로그를 따로 집계해야 했다.

- 맥락 없이 보면 의외인 점: 인증 없는 상태 리스너가 연결 수·처리량·버전을 내보낸다. 관리 리스너의 로그인 뒤에 두지 않는다.
- 되돌리기 어려운 이유: 메트릭 이름·속성·단위는 외부 수집 설정, 대시보드, 경보 규칙이 그대로 참조한다. 배포 뒤 이름이나 노출 위치를 바꾸면 소비자 설정을 모두 옮겨야 한다.
- 범위: 운영 로그 형식, `/livez`·`/readyz` 응답, 관리 로그인 규칙은 바꾸지 않는다. [ADR-0003](ADR-0003-single-instance-memory-state.md)의 단일 인스턴스·메모리 상태를 유지한다.

## 3. 결정 요인

1. 수집 도구 호환. OpenTelemetry Collector와 Prometheus가 추가 변환 없이 읽어야 한다.
2. 노출 경계. 비밀·중계 ID·세션 식별자·주소·계정명이 메트릭에 나오면 안 된다.
3. 기존 배포 영향. 켜기 전에는 상태 리스너의 동작이 지금과 같아야 한다.
4. 의존성. [PRD 구현 기술 행](../requirements/PRD.md#확정-기준)의 허용 목록과 라이선스 검사를 유지한다.
5. 수집 인증. 외부 수집 도구가 관리 로그인·CSRF 없이 값을 읽을 수 있어야 한다.
6. 상태 모델. 외부 저장소 없이 메모리에만 둔다.
7. 대시보드. 외부 수집 도구가 없어도 관리자가 추이를 볼 수 있어야 한다.

## 4. 선택 근거

pull 방식은 VNC Relay가 수집 주소·전송 실패·재시도를 관리하지 않게 한다. Prometheus 텍스트 형식은 OpenTelemetry Collector의 Prometheus 수신기가 OpenTelemetry 데이터 모델로 바꿀 수 있다. 그래서 이름·단위·속성은 OpenTelemetry 규칙으로 정하고, 텍스트 표현은 OpenTelemetry의 Prometheus 호환 규칙(`.`→`_`, 단위 접미사, 누적 합계의 `_total`)으로 정한다. 정확한 대응은 [메트릭 계약 1.6절](../contracts/metrics-v1.md#16-prometheus-텍스트-표현)을 따른다.

상태 리스너는 이미 인증 없이 루프백에 바인딩하고 Lm으로 연결을 센다. 수집 도구가 관리 로그인을 하지 않아도 된다. 관리 리스너의 HTTPS·로그인 규칙은 그대로 둔다. 노출 위험은 기본 꺼짐과 고정 값 목록의 속성으로 줄인다. 속성 값은 운영 로그의 고정 값 목록만 쓰므로 수집 도구가 받는 시계열 수에도 상한이 있다.

계측 대상은 운영 로그 사건과 같은 경로에서 센다. 운영 로그 기록부를 감싸는 기록부가 사건마다 값을 올리므로, 로그와 메트릭의 수가 어긋나지 않는다. 로그에 없는 값(초기 교환 시간, Mode I 대상 연결 시간, 진행 중인 전송량, WebSocket ping 시간 초과)만 해당 코드에서 직접 기록한다. 구조는 [메트릭 모듈 설계](../architectures/metrics.md)가 정한다.

텍스트 형식은 줄 단위의 단순한 형식이고 필요한 계측기는 카운터·게이지·히스토그램뿐이다. 직접 쓰면 새 의존성과 라이선스 검토가 필요 없다. 운영 로그를 serde_json으로 직접 쓰는 기존 선택과 같은 방향이다.

## 6. 결과

### 긍정적 결과

- 운영자는 Prometheus나 OpenTelemetry Collector로 연결·세션·지연·자원 추이를 수집할 수 있다.
- 로그와 메트릭이 같은 사건에서 나오므로 두 수가 일치한다.
- 외부 수집 도구가 없어도 대시보드에서 최근 1시간 추이와 원인별 수를 본다.
- 새 crate 의존성이 없다.

### 부정적 결과와 비용

- `/metrics`를 켜면 인증 없는 응답에 연결 수·처리량·버전·L·Lm 상한이 나온다. 상태 리스너를 루프백이 아닌 주소에 두면 그 망의 누구나 읽는다. 운영자가 상태 리스너 주소를 보호해야 한다.
- 값은 메모리에만 있다. 재시작하면 카운터는 0부터 다시 세고 대시보드 추이는 비워진다. 장기 보관은 외부 수집 도구가 맡는다.
- OTLP push가 필요한 환경은 Collector의 Prometheus 수신기를 거쳐야 한다.
- 히스토그램 경계는 계약에 고정한다. 경계를 바꾸면 계약 버전을 올려야 한다.
- 프로세스 CPU·메모리·핸들 수를 Windows에서 읽으려면 Win32 API를 windows-sys로 직접 호출한다. [Rust 코드 컨벤션](../conventions/rust.md)의 `unsafe` 예외 모듈이 하나 늘어난다.

### 후속 작업

- PRD AC-60~62와 각 스펙 시나리오를 구현·테스트에 연결한다.
- 대시보드 SCR-007은 디자인 기준의 차트 구성 요소와 시안을 사용자가 채택한 뒤 구현한다.
- 도움말에 Prometheus·OpenTelemetry Collector 수집 예를 싣는다.

## 8. 재검토 조건

다음 재검토 조건은 사용자 결정으로 확정한 새 동작이 아니라 이 ADR의 판단이다(이 문서의 판단, 사용자 결정 없음).

- 다중 인스턴스를 도입하여 [ADR-0003](ADR-0003-single-instance-memory-state.md)의 상태 소유 기준이 바뀐다.
- 사용처가 OTLP push만 받는 수집 환경을 요구한다.
- 상태 리스너를 루프백 밖에 두는 배포가 늘어 인증 있는 수집이 필요해진다.
- Prometheus 텍스트 형식 0.0.4를 수집 도구가 더 이상 지원하지 않는다.
