# VNC Relay — PRD

- 문서 상태: 초안 0.11
- 작성일: 2026-10-16
- 프로젝트명 / 디렉터리: `vnc-relay`
- 제품 정의: Rust로 독립 구현하는 VNC Relay. UltraVNC Repeater와 호환된다. TCP 중계, WS·WSS ↔ TCP 프록시와 웹 대시보드를 제공한다.

## 1. 문서의 결정 수준

이 문서는 제품 요구사항 초안이며, 구현 완료나 호환성 검증 결과를 의미하지 않는다.

| 구분 | 내용 |
| --- | --- |
| 사용자 확정 | Rust 독립 구현(tokio·rustls), TCP·WS·WSS와 Mode I·II, Windows 11 x64·Ubuntu 24.04 LTS x64, 실행파일 하나의 CLI, TOML 설정, 내장 TLS, 서버 내장 관리 로그인·조회·종료·동적 설정 편집, 진입점별 출발지 IP 허용 목록, 공유 WS·WSS 리스너의 경로별 Viewer·Server 역할, 역할별 선택형 접속 ticket 확인, 중계 WS·WSS 리스너 앞의 프록시 TLS 종료와 신뢰 프록시 전달 주소, Origin 정확 일치, 최근 종료 목록과 최근 로그 화면, 정적 HTML·JS 대시보드와 한국어·영어 지원, 43개 키의 부분 재로드와 37개 키의 편집, 단일 인스턴스, 연결 상한·끊긴 연결 감지·정상 종료, 독립 구현과 MIT, 실제 UltraVNC 호환 검증, noVNC는 외부 검증 도구로만 사용, 한국어·영어 운영 도움말 사이트와 GitHub Pages 게시. 세부 범위와 근거는 아래 확정 기준 표를 따른다 |

| 미확정 | `vnc-relay`의 실제 검증 환경(대상 버전의 통신 관찰은 2026-11-01에 마쳤다. [호환성 검증 기록](../contracts/repeater-compat-record.md) 3절), 파일 감지의 플랫폼별 세부, 주소 재사용 같은 OS 동작의 관찰 확인. Windows 콘솔 닫기 처리는 사용자 결정 2026-11-04(Q102)로 확정 기준 표의 "종료 유예 중 동작" 행에 옮겼다 |

이하 요구사항은 별도 표시가 없으면 제안된 제품 기준이다. 확정 기준 표의 항목과 그 내용을 옮긴 문장은 사용자 확정 사항이다. 미확정 사항을 이미 합의된 조건이나 검증된 사실로 취급하지 않는다.

TCP·WS·WSS와 아래 기준은 이번 사용자 선택으로 확정한 요구사항이다. WS는 TLS 없는 WebSocket(`ws://`), WSS는 TLS로 보호하는 WebSocket(`wss://`)이다. 중계 리스너는 내장 TLS와 프록시 TLS 종료를 지원한다. 확정한 지원 목표는 구현·테스트 완료를 뜻하지 않는다.

### 확정 기준

| 항목 | 확정 내용 |
| --- | --- |
| 중계 모드 | Mode I·II 모두 구현·검증 |
| 서버 플랫폼 | Windows 11 x64·Ubuntu 24.04 LTS x64, 양쪽에서 실행·종료·호환성 검증. Windows Server는 제외 |
| 실행 형태 | 실행파일 하나에 하위 명령을 둠. 서버 실행과 관리자 계정 준비는 같은 실행파일의 서로 다른 하위 명령. 하위 명령 이름·옵션·종료 코드는 [CLI 계약](../contracts/cli-v1.md)이 정함(Active, 2026-10-16 채택). 인증서·개인키 파일 오류는 설정 오류와 같은 종료 코드를 쓰고 리스너 바인드 실패와 구분. 시작 키(RelayIdKey·SessionIdKey)는 OS 난수원으로 생성하며 실패 시 `runtime_unavailable`(종료 코드 1)로 멈춤(사용자 결정 2026-11-01(Q76)) |
| 설정 형식 | 설정 파일은 TOML. 키 이름·구조는 [설정 계약 v4](../contracts/config-v4.md)의 `vnc-relay-config` 4.1.0을 따름. WS·WSS 리스너와 역할 표를 분리한 4.0.0은 호환성 파괴 변경이며 v3 파일은 [3.3절](../contracts/config-v4.md#33-v3-파일을-v4로-옮기기)에 따라 옮겨야 함(사용자 결정 2026-11-08(Q188)). 4.1.0은 접속 ticket 표를 더하는 호환 변경이다(사용자 결정 2026-11-11(Q197·Q200·Q207·Q212·Q213)) |
| 수치 기본값 | 한도·시간·세션·해시 매개변수의 기본값과 유효 범위, 진입점·모드의 기본 비활성, TCP 진입점의 기본 포트는 [설정 계약](../contracts/config-v4.md)을 따름(2026-10-16 승인) |
| TLS 종료 | WSS·관리 HTTPS의 내장 TLS는 유지. 중계 WS·WSS 리스너 앞에서는 역방향 프록시 TLS 종료도 지원. 관리 리스너는 이 지원에서 제외하며 내장 HTTPS 또는 루프백 평문 HTTP 규칙을 유지(사용자 결정 2026-11-08(Q182·Q183)). 내장 TLS는 1.2 미만 협상을 거절. 암호 스위트는 aws-lc-rs의 rustls 기본 목록이며 변경 키가 없음(사용자 결정 2026-10-20). [ADR-0007](../decisions/ADR-0007-proxy-tls-termination.md) 참조 |
| 관리 접근 | 외부 HTTPS 접근 허용, 서버 내장 관리자 로그인 필수. 관리 리스너는 HTTPS가 원칙이며, 평문 HTTP는 루프백 주소에 바인딩한 경우에만 허용. 루프백이 아닌 주소에 평문 HTTP를 설정하면 시작 실패. 루프백에서도 관리자 로그인은 생략하지 않음 |
| 관리 로그인 보호 | 로그인 실패를 계정별·출발지 IP별로 세며, 기준을 넘으면 일정 시간 로그인을 지연하거나 거절. 응답은 계정 존재 여부를 드러내지 않음. 제한 중에는 올바른 비밀번호도 거절. 기준과 제한 시간은 설정 계약에서 정함 |
| 관리 세션 수명 | 유휴 만료 시간과 절대 최대 수명을 가짐. 대시보드 자동 폴링은 유휴 만료를 연장하지 않음. 절대 최대 수명이 지나면 활동과 관계없이 무효화. 수치와 요청 구분 방식은 설정 계약과 관리 API 계약에서 정함 |
| 관리 세션 보관 | 서버 메모리에 보관하고 불투명 식별자 쿠키를 사용. 프로세스를 재시작하면 이전 관리 세션은 모두 무효이며 다시 로그인해야 함 |
| 관리 세션 쿠키 | HttpOnly, SameSite=Strict. HTTPS에서는 Secure를 붙임. 평문 HTTP 루프백 관리 리스너에서는 Secure만 빼고 HttpOnly·SameSite=Strict를 유지. CSRF 방어는 별도로 유지 |
| 관리 기능 | 서버·대기 연결·활성 세션 조회, 최근 종료 목록·최근 로그 조회, 확인 절차를 거친 활성 세션 종료, 설정 보기·동적 설정 편집(사용자 지시 2026-11-08) |
| 관리 API | JSON over HTTP, 경로 접두사 `/api/v1/`. 개별 경로·메서드·오류 본문·로그인 교환은 [관리 API 계약](../contracts/management-api-v1.md)이 정함(Active, 2026-10-16 채택). 인증 실패 401 응답에는 `WWW-Authenticate: Session realm="vnc-relay"`를 붙임(사용자 승인). 브라우저가 기본 인증 창을 띄우는지는 구현에서 확인 |
| 대시보드 구현 | 별도 빌드 단계 없는 정적 HTML·JS로 만들고 실행파일에 넣어 관리 리스너가 제공. Node 빌드 체인·JS 프레임워크 의존성을 추가하지 않음. 시각 기준(색·간격·토큰·배치)은 [디자인 기준](../design/DESIGN.md)과 그 HTML 시안을 따름(사용자 채택, 2026-10-20) |
| 화면·브라우저 | 데스크톱 폭과 모바일 폭, 최신 Chrome·Edge·Firefox·Safari를 지원. 두 폭 모두에서 필수 정보와 상세 이동·종료·취소·로그아웃 행동을 쓸 수 있어야 함. 모바일 폭의 구체 배치(중단점·표 표시 방식)는 디자인 기준이 정함 |
| 대시보드 언어 | 화면 문구는 한국어·영어. 저장된 선택이 없으면 브라우저 선호 언어 목록에서 처음 만나는 한국어 또는 영어를 쓰고, 둘 다 없으면 영어. 언어 선택은 상단 막대와 로그인 화면에 두며, 직접 고른 언어는 브라우저 저장소에 남겨 자동 선택보다 우선. 시각·전송량 형식은 언어와 관계없이 같고 문구만 번역(사용자 결정, 2026-10-20) |
| 최근 종료 목록 | 정리가 끝난 활성 세션만 메모리에 보관. 보관 최대 개수는 설정 계약에서 정하며, 초과하면 가장 오래된 항목부터 제거. 재시작하면 비어 있음. 장기 이력 검색이 아님 |
| 최근 로그 | 운영 로그 사건의 최근 N개를 메모리에 보관하고 SCR-006 로그(`/#/logs`)에서 조회. `recent_logs.max_entries`는 기본 1000, 범위 0~10000이며 0이면 보관하지 않음. 재시작이 필요하며 재시작 뒤 목록은 비어 있음(사용자 결정 2026-11-08(Q185)). 수준·사건 이름 필터, 값 검색, 일시 정지 가능한 P 주기 자동 갱신, 세션 상세에서 해당 세션 로그 열기, 현재 필터 결과 전체의 JSON Lines 내려받기를 제공(사용자 결정 2026-11-08(Q186)) |
| 전송량·시각 표현 | 방향별 전송량은 상대 전송 계층에 쓰기 성공한 바이트로 센다. 관리 API는 시각을 UTC ISO 8601로, 전송량을 바이트 정수로 제공. 대시보드는 브라우저 현지 시각(시간대 표시)과 KiB·MiB(이진 단위)로 표시 |
| 관리자 종료 응답·종료 중 집계 | 관리자 종료 요청은 정리가 끝난 뒤 완료 응답한다. 별도 "처리 중" 응답 상태는 두지 않음. 응답 시간은 최대 정리 제한 시간 E까지 길어질 수 있음. 종료 중인 세션은 정리가 끝날 때까지 활성 수에 포함 |
| 관리 권한 | 단일 관리자 역할. 로그인한 모든 관리자 계정이 같은 권한(조회·활성 세션 종료·동적 설정 변경)을 가짐. 활성 세션 종료와 동적 설정 변경에는 유효한 관리 세션이 필요함. 관리자 종료·설정 편집 사건 로그에 수행한 계정명을 기록하고, 편집 사건에는 바뀐 키도 기록하되 값은 기록하지 않음(사용자 결정 2026-11-08(Q169)) |
| 상태 확인 | 생존·준비 상태는 관리 리스너와 분리한 상태 리스너에서 제공. 기본 바인딩은 루프백이며, 인증 없이 생존·준비 결과만 응답. 세션 목록·중계 ID·상대 주소·인증 비밀은 포함하지 않음 |
| WS·WSS 중계 접근 | WS·WSS 공유 리스너에서 `/relay/viewer`는 Viewer, `/relay/server`는 Server 역할(Viewer 경로: 사용자 결정 2026-11-10). 출발지 IP 허용 목록은 리스너와 역할의 조합인 진입점마다 분리. 접속 수락 때는 켠 역할 목록의 합집합 또는 신뢰 프록시 여부를 검사하고, 업그레이드 때는 해당 역할 목록으로 클라이언트 주소를 검사(사용자 결정 2026-11-08(Q181·Q182·Q188)). 관리자 로그인과 분리. 접속 ticket은 기본으로 쓰지 않고, 설정으로 켠 WS·WSS 역할에서만 확인(사용자 결정 2026-11-11(Q192·Q193)). 평문 WS는 기본 비활성이며 명시적으로 켠 경우에만 열림 |

## 2. 배경과 문제

UltraVNC Server와 Viewer 사이의 TCP 연결을 중계하면서, WS 또는 WSS를 사용하는 외부 클라이언트도 같은 중계 기능을 이용할 수 있는 서버가 필요하다. 운영자는 별도 화면 뷰어 없이 접속 대기와 활성 세션을 확인하고 관리할 수 있어야 한다.

기존 코드를 다른 언어로 옮기는 방식이 아니라, 외부 통신 동작을 근거로 독립적인 Rust 구현을 만든다. 원본 프로그램의 내부 구조나 UI를 복제하는 것은 목표가 아니다.

## 3. 목표

1. 선정된 UltraVNC Server/Viewer 버전과 Repeater 연결 호환성을 확보한다.
2. TCP·WS·WSS 클라이언트가 동일한 중계 기능을 이용하게 한다.
3. 운영자가 대기 연결, 활성 세션, 전송량과 종료 원인을 대시보드에서 확인하게 한다.
4. 연결 수명과 리소스 사용을 제한하고, 운영상 실패가 다른 세션으로 전파되지 않게 한다.
5. 코드 출처와 의존성 라이선스를 관리하여 독립 구현 경위를 설명할 수 있게 한다.

## 4. 범위

### 4.1 포함

- Repeater Mode I: Viewer가 요청한 대상으로 TCP 연결을 생성하고 중계.
- Repeater Mode II: Server와 Viewer의 연결을 ID 기준으로 매칭하고 중계.
- WS·WSS ↔ TCP/중계 스트림 변환.
- 연결·세션 상태와 설정 보기·동적 설정 편집을 제공하는 관리 API.
- 웹 대시보드: 서버 상태, 대기 연결, 활성 세션, 세션 상세, 최근 종료 목록, 최근 로그, 활성 세션 종료, 설정 보기, 동적 설정 편집.
- 운영 설정, 확대된 재로드 범위와 설정 파일 편집, 상태 확인 엔드포인트, 구조화된 운영 로그.
- 운영 도움말 사이트: 한국어·영어의 설치·설정·운영·문제 해결 안내, GitHub Pages 게시, 대시보드의 도움말 링크.
- 실제 UltraVNC 실행 파일을 이용한 호환성 검증.

### 4.2 제외

- noVNC 클라이언트의 제품 구현·번들링·배포물·제품 의존성 추가. noVNC는 외부 상호운용 검증 도구로만 사용한다.
- 대시보드 내 원격 화면 표시, 키보드·마우스 제어.
- VNC Server 또는 Viewer 자체 구현.
- 화면 인코딩 변환, 영상 트랜스코딩, 클립보드·파일 전송의 독자적 해석.
- VNC 인증을 대신 수행하거나 기존 인증을 우회하는 기능.
- UltraVNC 전용 암호화 플러그인이나 SSL Repeater 변형의 별도 종단 처리. WSS를 위한 TLS 종료는 이 제외 범위에 해당하지 않는다.
- 세션 녹화, 원격 에이전트 배포, 자동 업데이트.
- 다중 노드 매칭, 클러스터링, 무중단 세션 이동.

단순 바이트 중계가 가능한 확장은 그대로 통과할 수 있으나, 이를 검증된 기능 지원으로 표기하지 않는다. VNC Relay가 인증·암호화를 종단 처리해야 하는 변형은 별도 범위 결정이 필요하다.

## 6. 기능 요구사항

### FR-01. TCP 접속과 프로토콜 처리

- Viewer용과 Server 역접속용 리스닝 주소·포트를 설정할 수 있어야 한다.
- Repeater 초기 교환의 메시지 방향, 길이, 필드와 패딩은 대상 버전의 통신 관찰로 확정했다([Repeater 초기 교환 계약](../contracts/repeater-handshake-v1.md) 1절, 2026-11-01).
- TCP의 분할 수신과 병합 수신에 영향을 받지 않아야 한다. 단일 읽기를 단일 메시지로 가정하지 않는다.
- 초기 메시지와 함께 들어온 후속 데이터는 유실하지 않고 보존한다.
- 잘못된 요청, 불완전한 초기 교환과 시간 초과를 구분하고 자원을 해제한다.
- 공개 문서에서 확인되지 않은 바이트 형식을 추정하여 호환 명세로 확정하지 않는다.

### FR-02. Mode I — 대상 지정 중계

- Viewer가 지정한 대상 주소를 호환 규칙에 맞게 해석한다.
- 허용된 대상에만 연결하며, 연결 성공 후 양방향 스트림을 중계한다.
- 대상 연결 실패는 연결 거절, 주소 해석 실패, 시간 초과 등으로 구분하여 운영자가 확인할 수 있어야 한다.
- 임의 대상에 접속하는 공개 프록시가 되지 않도록 대상 주소·포트 허용 정책을 제공한다.
- 정책은 최종 연결 IP에도 적용한다. DNS 이름을 허용하는 경우 주소 해석 결과로 정책을 우회할 수 없어야 한다.

### FR-03. Mode II — ID 기반 연결 매칭

- Server와 Viewer의 연결을 같은 ID로 매칭한다.
- Server 선접속과 Viewer 선접속을 모두 지원한다.
- 한 쌍을 연결할 때 매칭을 원자적으로 처리하여 하나의 연결이 여러 세션에 할당되지 않게 한다.
- ID 형식과 비교 규칙은 호환성 조사로 확정하며, 임의의 정규화로 다른 ID를 합치지 않는다.
- 대기 연결에는 제한 시간을 적용한다. 상대가 없으면 종료하고 등록 정보를 제거한다.
- 중복 ID의 같은 역할 연결은 후발 연결을 거절한다(사용자 결정 2026-11-01(Q74)). 기존 연결을 묵시적으로 교체하지 않는다.
- 중복 ID 동작은 실제 제품 동작과 비교하고, 호환성 차이가 있으면 문서에 명시한다. 대상 버전과의 차이(후발 연결을 닫음)는 [Repeater 초기 교환 계약 3.1절](../contracts/repeater-handshake-v1.md#31-대상-버전-repeater와-다르게-처리하는-입력)에 있다. 활성 세션 ID의 중복은 대상 버전에서 관찰하지 않았다(사용자 결정 2026-11-01(Q75)).
- 활성 세션은 중계 ID와 별개의 고유 세션 식별자를 가진다. 종료·재접속 시 이전 상태가 새 연결에 섞이지 않아야 한다.

### FR-04. 양방향 스트림 중계

- 초기 Repeater 메시지 처리 후에는 RFB 메시지 내용을 수정하지 않고 전달한다.
- 화면 압축, VNC 인증, 키보드·마우스 처리는 양 끝점의 책임으로 유지한다.
- 느린 수신자에 맞춰 읽기 속도를 제어하고, 버퍼가 무제한 증가하지 않게 한다.
- EOF, 연결 오류, 관리자 종료 시 세션 자원을 정리하고 종료 원인을 남긴다.
- 중계 측 TCP 소켓(Viewer·Server·Mode I 대상, WS·WSS 하부 TCP 포함)에 TCP keepalive를 적용한다. 응답하지 않는 상대의 대기·활성 연결은 감지 시간 K 안에 끊긴 연결로 판정하고 회수한다.
- keepalive에 응답하는 연결은 데이터가 없다는 이유만으로 종료하지 않는다. 활성 세션의 유휴 제한과 관리자의 대기 연결 강제 해제는 추가하지 않는다.
- 한쪽 TCP 연결이 정상 EOF로 끝나면, 이미 받은 데이터를 전달한 뒤 상대 쓰기 방향만 닫는다. 반대 방향은 정리 제한 시간 E까지 계속 전달한다. WebSocket이 섞인 경우의 종료는 WebSocket 규칙을 따르며, 의미 차이는 계약에 명시한다.

### FR-05. WS·WSS 프록시

- 외부 클라이언트가 WS와 WSS 모두에서 바이너리 WebSocket 메시지로 중계 스트림을 주고받을 수 있어야 한다.
- 평문 WS 리스너는 기본 비활성이며, 설정에서 명시적으로 켠 경우에만 연다([7절](#7-보안-및-신뢰-경계)).
- 공유 WS·WSS 리스너에서 정확한 경로 `/relay/viewer`는 Viewer, `/relay/server`는 Server 역할을 선택한다. 꺼진 역할의 경로와 나머지 경로는 404로 거절한다(사용자 결정 2026-11-08(Q181·Q188)). Viewer 경로는 `/relay`에서 `/relay/viewer`로 바꿨으며 이전 경로 `/relay`도 404다(사용자 결정 2026-11-10).
- 바이너리 페이로드의 연결 순서가 보존되어야 하며, WebSocket 메시지 경계를 RFB 메시지 경계로 취급하지 않는다.
- Viewer 역할은 Mode I·II를 제공한다. 다만 접속 ticket을 켠 Viewer 역할은 Mode I 요청을 거절한다(사용자 결정 2026-11-11(Q203)). Server 역할은 TCP Server와 같은 Mode II 초기 교환을 사용하며 `ID:`를 보낸다. Server에 greeting을 보내지 않는다. 바이트 형식은 [Repeater 초기 교환 계약](../contracts/repeater-handshake-v1.md)을 따른다.
- WS·WSS Mode II 상호운용은 검증 시작 시 고정한 noVNC 버전의 repeaterID 옵션으로 확인한다. noVNC는 검증 도구이며 제품 의존성이 아니다.
- URL로 직접 대상이나 ID를 선택하는 별도 API는 초기 범위에 추가하지 않는다.
- ping/pong, close, 프레임 분할과 메시지 크기 제한을 처리한다. 텍스트 데이터 메시지는 지원하지 않는 계약으로 명시한다.
- WS·WSS 연결에 주기 Kw로 ping을 보낸다. 응답 제한 시간 안에 pong이 없으면 끊긴 연결로 처리해 정리한다. pong에 응답하는 유휴 클라이언트는 유지한다. ping은 TCP 스트림에 섞이지 않는다.
- 관리 API(`/api/v1/` 접두사)와 WebSocket 업그레이드 경로를 구분한다. 경로·서브프로토콜·Origin·인증·종료 코드 계약은 구현 전에 문서화한다.
- noVNC 소스나 websockify 실행 파일 없이 프록시 기능을 제공한다.
- WS·WSS는 TCP 접속 수락 직후(TLS 협상과 HTTP 처리 전)에 소켓 상대 IP를 검사한다. 해당 리스너의 켠 역할 목록 합집합에 없고 신뢰 프록시도 아니면 HTTP 응답 없이 닫는다.
- 업그레이드 직전에는 그 시점에 유효한 해당 역할 목록으로 클라이언트 주소를 검사한다. 리스너별 `trusted_proxies`에 속한 상대의 `X-Forwarded-For`를 오른쪽부터 읽어 첫 비신뢰 주소를 쓴다. 헤더 누락·오류 또는 모든 요소가 신뢰 프록시인 체인은 400 `forwarded_for_invalid`로 거절한다. `trusted_proxies`에는 프록시 주소만 넣어야 하며 클라이언트 범위를 넣어서는 안 된다. 세부 규칙은 [WebSocket 계약 1.8절](../contracts/websocket-relay-v2.md#18-신뢰-프록시와-x-forwarded-for)을 따른다(사용자 결정 2026-11-08(Q182)).
- Origin 헤더가 있으면 해당 역할의 허용 값과 `scheme://host[:port]`가 정확히 일치할 때만 업그레이드한다. 와일드카드는 없다. Origin이 없으면 Origin 검사만 생략한다. IP 검사와 켠 역할의 ticket 확인은 유지한다. 정규화 세부는 WebSocket 계약을 따른다.
- 관리자 로그인 쿠키·중계 ID로 IP 제한을 우회하지 못하게 한다. 신뢰하지 않는 상대의 전달 헤더는 무시한다. 신뢰 프록시의 전달 주소에도 역할별 IP 제한을 적용한다.
- 접속 ticket 확인은 기본으로 꺼져 있다. 역할마다 켜며 같은 역할의 WS·WSS에 함께 적용한다. 켠 역할은 유효한 ticket 하나를 받아야 한다. 없음·무효·만료·기동 전 발급·재사용은 101 전에 HTTP 401로 거절한다. ticket은 초기 요청의 중계 ID와 일치해야 하며, `sx`가 있으면 그 시각에 연결을 끝낸다. 형식과 판정은 [WebSocket 계약 1.9절](../contracts/websocket-relay-v2.md#19-접속-ticket)을 따른다(사용자 결정 2026-11-11(Q192·Q196·Q197·Q201~Q204·Q213)).

### FR-06. 관리 API와 대시보드

- 실행 상태, 가동 시간, 대기 연결 수, 활성 세션 수를 표시한다.
- 서버 요약에 초기 교환 중 연결 수와 Mode I 대상 연결 중 연결 수를 표시한다. 중계 측 연결 상한 L과 관리·상태 연결 상한 Lm의 현재 사용량과 상한도 표시한다.
- 대기 연결 목록에서 역할, 중계 ID, 접속 시각, 대기 시간을 확인할 수 있어야 한다.
- 활성 세션 목록과 상세에서 모드, Viewer와 Server/대상의 전송 경로, 시작 시각, 양방향 누적 전송 바이트 수, 소켓 상대 주소를 확인한다. 신뢰 프록시를 거친 쪽은 전달 주소도 구분해 표시한다.
- 방향별 전송량은 상대 전송 계층에 쓰기 성공한 바이트로 센다. 관리 API는 시각을 UTC ISO 8601로, 전송량을 바이트 정수로 제공한다. 대시보드는 시각을 브라우저 현지 시각(시간대 표시)으로, 전송량을 KiB·MiB(이진 단위)로 표시한다.
- 최근 종료 목록을 제공한다. 정리가 끝난 활성 세션만 담으며, 세션 식별자, 모드, Viewer와 Server/대상의 전송 경로, 시작·종료 시각, 방향별 최종 누적 바이트 수, 종료 원인을 보여준다. 대기 만료 등 활성 세션이 되지 못한 연결의 종료는 운영 로그에만 남긴다.
- 종료 원인은 정상 EOF, 연결 오류, 관리자 종료, 세션 만료(`session_expired`), 끊긴 연결 감지, 정리 제한 시간 초과, 서버 종료(정상 종료 유예 만료나 유예 중 두 번째 종료 요청으로 강제 정리), 내부 오류로 구분한다. 세션 만료는 ticket의 `sx`에 도달해 활성 세션을 끝낸 경우다(사용자 결정 2026-11-11(Q213)). 내부 오류는 Running 중 세션 소유 작업이 버그로 끝났고 기존 종료 원인이 없는 경우다(사용자 결정 2026-11-02(Q94), [관리 스펙 2.3절](../specs/management.md#23-최근-종료-목록)). 목록은 메모리에만 두며 보관 최대 개수는 설정 계약에서 정한다. 최대 개수를 넘으면 가장 오래된 항목부터 제거한다. 재시작하면 비어 있다. 장기 이력 검색 기능이 아니며, 종료된 세션 식별자로 상세나 종료를 요청하면 대상 없음으로 응답한다.
- 중계 ID는 인증 비밀이 아니지만 운영 정보로 취급하고, 로그 노출 범위를 제한한다.
- 활성 세션 종료에는 유효한 관리 세션과 UI 확인 절차를 적용한다. 종료 대상은 고유 세션 식별자로 지정한다.
- 관리자 종료 요청은 정리가 끝난 뒤 완료 응답한다. 별도 "처리 중" 응답 상태는 두지 않는다. 응답 시간은 최대 정리 제한 시간 E까지 길어질 수 있다. 응답을 받지 못했을 때 결과를 다시 조회하는 규칙은 관리 스펙을 따른다. 종료 중인 세션은 정리가 끝날 때까지 활성 세션 수에 포함한다.
- 대시보드·관리 API는 서버 내장 관리자 로그인으로 보호한다. 대시보드 중 로그인 화면만 인증 없이 접근할 수 있다. 상태 엔드포인트는 관리 리스너가 아니므로 이 규칙 대상이 아니다. 로그인·관리 세션 만료·로그아웃 동작은 관리 스펙에서 정한다.
- 관리 API는 JSON over HTTP이며 경로 접두사는 `/api/v1/`다. 개별 경로·메서드·오류 본문·로그인 교환은 관리 스펙에서 정한다.
- 관리자 로그인 실패는 계정별·출발지 IP별로 센다. 실패 기준을 넘으면 제한 시간 동안 로그인을 지연하거나 거절한다. 이 응답은 계정 존재 여부를 드러내지 않는다. 제한 중에는 올바른 비밀번호도 거절한다.
- 관리 세션은 유휴 만료 시간과 절대 최대 수명을 가진다. 사용자 행동 요청만 유휴 만료를 연장한다. 대시보드의 자동 폴링 요청은 연장하지 않는다. 절대 최대 수명이 지나면 활동과 관계없이 무효화한다. 자동 요청과 사용자 요청을 구분하는 방식은 관리 API 계약에서 정한다.
- 관리 세션은 서버 메모리에 보관하며 불투명 식별자 쿠키를 쓴다. 쿠키는 HttpOnly·SameSite=Strict이며 HTTPS에서는 Secure를 붙인다. 평문 HTTP 루프백 관리 리스너에서는 Secure만 뺀다. CSRF 방어는 별도로 유지한다. 프로세스를 재시작하면 이전 관리 세션은 모두 무효이며, 관리자는 다시 로그인해야 한다.
- 관리자 계정은 로컬 CLI로 준비한다. 여러 계정을 준비할 수 있으며, 로그인한 모든 관리자 계정은 같은 권한(조회·활성 세션 종료·동적 설정 변경)을 가진다(사용자 결정 2026-11-08(Q169)). 비밀번호는 Argon2id 해시로 저장한다. 계정 준비의 입력·저장·실패 동작은 운영 스펙이 소유하며 웹 계정 생성 기능은 추가하지 않는다.
- 종료 실패, 조회 실패, 연결 없음 상태를 빈 목록과 구분하여 표시한다.
- 대시보드 폴링 주기 P는 설정할 수 있으며 기본값은 2초다. 화면은 서버 설정의 P를 따르고 마지막 갱신 시각을 표시한다. P는 재시작이 필요한 설정이다. 유효 범위와 조회 제한 시간은 설정 계약에서 정한다.
- SCR-006 로그(`/#/logs`)에서 최근 로그를 확인한다. 수준·사건 이름 필터, 값 검색, 일시 정지 가능한 P 주기 자동 갱신, 세션 상세에서 해당 세션으로 거른 로그 열기, 현재 필터 결과 전체의 JSON Lines 내려받기를 제공한다(사용자 결정 2026-11-08(Q185·Q186)).
- 브라우저에서 원격 화면을 열거나 조작하는 기능은 제공하지 않는다.
- 대시보드는 별도 빌드 단계 없는 정적 HTML·JS로 만들고 실행파일에 넣어 관리 리스너가 제공한다. Node 빌드 체인과 JS 프레임워크 의존성을 추가하지 않는다. 시각 기준(색·간격·토큰·배치)은 [디자인 기준](../design/DESIGN.md)(2026-10-20 채택)을 따른다.
- 대시보드는 데스크톱 폭과 모바일 폭, 최신 Chrome·Edge·Firefox·Safari를 지원한다. 두 폭 모두에서 필수 정보와 상세 이동·종료·취소·로그아웃 행동을 쓸 수 있어야 한다. 모바일 폭의 구체 배치(중단점·표 표시 방식)는 디자인 기준이 정한다.
- 대시보드 화면 문구는 한국어와 영어로 제공한다. 저장된 선택이 없으면 브라우저 선호 언어로 자동 선택하고, 한국어·영어가 모두 없으면 영어를 쓴다. 사용자가 상단 막대나 로그인 화면에서 고른 언어는 브라우저에 저장해 자동 선택보다 우선한다. 시각·전송량 형식은 언어와 관계없이 같다. 세부 동작은 [화면 스펙](../specs/dashboard.md#화면-언어)이 정한다.
- 설정 보기 화면을 항상 제공한다. 실행 중 유효 설정과 파일의 반영 상태를 구분해 볼 수 있어야 한다. 인증서·개인키와 접속 ticket 공개 키는 경로만 표시하고 파일 내용은 표시하지 않는다.
- 동적 설정 편집 화면을 제공한다. 편집 기능은 기본으로 꺼져 있으며 설정 키로 켜고 재시작해야 쓸 수 있다(사용자 결정 2026-11-08(Q170)). 관리 API의 편집 대상은 37개 키다. 진입점·모드에 속한 키는 그 진입점·모드가 켜져 있을 때만 편집할 수 있다. TLS 경로 4개와 접속 ticket 공개 키 파일 경로 2개는 편집에서 제외한다(사용자 결정 2026-11-08(Q172·Q184·Q188), 사용자 결정 2026-11-11(Q200)). ticket 키 편집 입력과 `session_expired` 표시 문구는 구현 작업에서 시안·문구(CPY)와 함께 정하기로 했다(사용자 결정 2026-11-11(Q214)). 후속: 사용자 결정 2026-11-11(Q215~Q219)으로 채택해 구현했다(커밋 `4be8e0e`). SCR-005는 편집할 수 있는 ticket 키를 마지막 구역 "접속 ticket"에 둔다. 화면 흐름·입력 검증·실패와 복구는 [화면 스펙](../specs/dashboard.md)이 정한다.
- 장기 세션 이력 검색은 초기 범위에 포함하지 않는다.

### FR-07. 설정과 프로세스 수명

- TCP 리스너와 WS·WSS 공유 리스너의 주소·포트, 역할·모드 활성화 여부, 진입점별 출발지 IP 허용 목록, 리스너별 신뢰 프록시, 대상 허용 정책, 연결 수·시간 제한, 관리·상태 리스너를 구성할 수 있어야 한다. 내장 TLS는 유지하며 중계 WS·WSS 앞의 프록시 TLS 종료도 지원한다. 프록시 인증 종료는 전제로 하지 않는다. 관리 리스너는 프록시 TLS 종료 지원에서 제외한다(사용자 결정 2026-11-08(Q181~Q184·Q188)).
- v4에서는 `[relay.ws]`·`[relay.wss]`가 리스너 주소·신뢰 프록시·WSS 인증서를 갖고, 하위 `[relay.{ws,wss}.{viewer,server}]`가 역할별 `enabled`·`allow`·`allowed_origins`를 갖는다. `recent_logs.max_entries`는 최근 로그 보관 개수이며 재시작으로 적용한다. 정확한 키와 이전·롤백은 [설정 계약](../contracts/config-v4.md)을 따른다.
- `[relay.ticket.viewer]`·`[relay.ticket.server]`로 접속 ticket 확인을 역할마다 구성한다. 각 표는 `enabled`·`issuer`·`relay_host`·`public_keys_file`·`max_lifetime_secs`를 가진다. 10개 키 모두 재로드 대상이며 공개 키 파일 경로 2개를 뺀 8개는 편집 대상이다. 기본 꺼짐, 역할별 수명 상한과 서로 다른 공개 키의 검증은 [설정 계약](../contracts/config-v4.md#111-접속-ticket-공개-키-파일-형식)을 따른다(사용자 결정 2026-11-11(Q197·Q200·Q207·Q212·Q213)).
- 비밀값을 로그나 대시보드에 노출하지 않는다.
- 잘못된 설정은 시작 시 명확한 오류로 거절하며, 보안 설정 누락을 조용히 완화하지 않는다.
- 다음 설정은 시작 실패로 거절한다: 준비된 관리자 계정이 없음, 켠 진입점의 출발지 IP 허용 목록 누락, 루프백이 아닌 주소에 대한 평문 HTTP 관리 리스너 설정. 이미 사용 중인 리스너 주소로 두 번째 프로세스를 시작하는 경우도 시작 실패로 보고한다.
- 출발지 IP 허용 목록 항목은 단일 IP, CIDR, 범위(`a-b`)만 받는다(IPv4·IPv6 모두). 잘못된 표기, 시작이 끝보다 큰 범위, 주소 체계가 섞인 범위는 설정 오류다. 시작이면 시작 실패로, 재로드면 후보 전체 거절로 처리한다.
- 설정 파일은 TOML이며 `vnc-relay-config` 4.1.0을 따른다. 서버 실행과 관리자 계정 준비는 같은 실행파일의 서로 다른 하위 명령이다. 확정 기준 표의 43개 키를 파일 변경 자동 감지로 재로드한다. 켠 ticket 표의 공개 키 파일도 감시한다. OS 파일 알림을 놓친 변경도 주기 확인으로 감지한다. 이미 통과한 판정·기존 연결·시작한 타이머·설정한 소켓 옵션은 유지한다. 새 값의 적용 경계는 [설정 계약 1.8절](../contracts/config-v4.md#18-재로드-구분)을 따른다(사용자 결정 2026-11-11(Q200)).
- 재로드 후보는 실행 중 유효 설정과 비교한다. 재로드 대상이 아닌 값이 실행 중 값과 다르면 후보 전체를 "재시작 필요"로 거절한다. 그 차이가 파일에 남아 있는 동안에는 이후 재로드 대상 변경도 모두 거절한다(급한 인증서 교체와 관리 API 편집 포함). 운영자는 그 값을 되돌리거나 재시작해야 한다.
- 재로드 후보 검증 실패나 재시작이 필요한 변경은 후보 전체를 미적용하고 이전 유효 설정·연결을 유지한다. 리스너·리스너 하위 역할의 `enabled`와 리스너의 `listen`, 계정·관리 로그인 제한·관리 세션 수명·`dashboard.*`·`recent_closed.max_entries`·`recent_logs.max_entries` 등 재로드 대상이 아닌 변경은 정상 종료·재시작으로 적용한다. 접속 ticket 표의 `enabled`는 재로드 대상이다(사용자 결정 2026-11-11(Q200)).
- 설정 조회·편집 관리 API를 제공한다. 편집은 같은 설정 파일의 바뀐 키만 기록하고 나머지 내용의 주석·공백·키 순서·다른 값을 보존한다. 같은 재로드 검증·전체 적용 규칙으로 반영하고 재시작 뒤에도 유지한다(사용자 결정 2026-11-08(Q167)). API 형식·충돌과 파일 쓰기 실패는 [관리 API 계약](../contracts/management-api-v1.md)이 정한다.
- 재로드의 자동 감지·원자적 적용·실패 결과·키별 적용 경계는 [운영 스펙](../specs/operations.md)이 정한다. 수동 재로드 API·수동 재로드 CLI는 추가하지 않는다.
- 종료 요청 시 신규 접속을 중지하고, 대기 연결을 해제하며, 활성 세션에 유예 시간을 준 뒤 정리한다.
- 정상 종료 유예 중에도 관리 조회·관리자 로그인·관리자 종료를 처리한다. 서버 상태는 유예 중으로 표시하고 상태 리스너의 준비 확인은 준비 아님이다.
- 유예 중 두 번째 종료 요청을 받으면 남은 유예를 건너뛰고 남은 세션을 즉시 강제 정리한다. 종료 원인은 서버 종료다.
- 재시작 후 기존 TCP 세션의 복구나 자동 재매칭을 보장하지 않는다.
- 단일 인스턴스로 운영한다. 프로세스 사이에 대기·세션·카운터 상태를 공유하지 않는다.

### FR-08. 운영 정보

- 접속 수락·거절, 대기 등록, 매칭, 연결 실패, 종료를 구조화된 로그로 기록한다. 로그는 JSON Lines다. 한 줄에 사건 하나를 쓰고, 줄마다 JSON 객체 하나를 쓴다. 관리자의 활성 세션 종료 사건 로그에는 수행한 계정명을 기록한다. 평문 WS 활성화와 전체 허용 항목 사용은 시작·재로드 때 경고로 기록한다.
- 설정 편집 성공·거절 사건을 기록한다. 편집 사건에는 수행한 관리자 계정명과 바뀐 키 또는 요청한 키를 남기되 설정 값은 남기지 않는다(사용자 결정 2026-11-08(Q169)). 사건·필드의 형식은 [운영 정보 계약](../contracts/ops-info-v2.md)이 정한다.
- ticket을 켠 역할에 같은 역할의 TCP 진입점이 열려 있으면 `ticket_tcp_bypass`, 평문 WS에서 그 역할이 열려 있으면 `ticket_plaintext_ws`를 시작·재로드 때 경고한다. 경고만으로 시작·재로드를 거절하지 않는다. 평문 WS 구간은 믿을 수 있는 망 안에 있어야 한다(사용자 결정 2026-11-11(Q198·Q199)).
- 접속 ticket 원문(JWS 전체·서명 부분)과 공개 키 파일 내용을 운영 로그·진단·상태 응답·관리 API 응답에 넣지 않는다. 허용 필드는 [운영 정보 계약](../contracts/ops-info-v2.md)을 따른다(사용자 결정 2026-11-11(Q213)).
- 세션 식별자, 역할, 모드, 시각, 종료 원인으로 장애를 추적할 수 있어야 한다.
- 화면 데이터, 입력 내용, VNC 인증 데이터, 전체 원시 페이로드를 로그에 기록하지 않는다.
- 프로세스 생존과 리스너 준비 여부를 확인하는 상태 엔드포인트를 관리 리스너와 분리한 상태 리스너에서 제공한다. 기본 바인딩은 루프백이며, 인증 없이 생존·준비 결과만 응답한다. 세션 목록·중계 ID·상대 주소·인증 비밀은 노출하지 않는다.
- 활성 세션 상태와 카운터는 메모리에 유지한다. 장기 저장용 데이터베이스는 초기 필수 요소로 두지 않는다.
- 최근 운영 로그 사건을 `recent_logs.max_entries`개까지 기록 순서대로 메모리에 보관한다. 가득 차면 가장 오래된 사건부터 제거한다. `log.output`과 출력 쓰기 성공 여부에 영향받지 않는다. 0이면 보관하지 않으며 재시작하면 비어 있다(사용자 결정 2026-11-08(Q185)).
- 소켓 상대 IP인 `peer_ip`는 유지한다. 신뢰 프록시의 전달 주소를 구한 WS·WSS 연결 사건에는 `forwarded_ip`를 추가한다. 리스너와 역할의 구분은 `ops-info` 2.0.0에서 정한 의미를 유지하며, 접속 ticket 사건·필드·값은 2.1.0에서 더한다(사용자 결정 2026-11-08(Q187·Q188), 사용자 결정 2026-11-11(Q198·Q199·Q213)).

### FR-09. 운영 도움말

- 운영자용 도움말 사이트를 한국어와 영어로 제공한다. 범위는 설치, 빠른 시작, UltraVNC·noVNC 연결 구성, 설정, 대시보드, 접속 ticket, 운영, 문제 해결, 참조다(사용자 결정 2026-11-11(Q220·Q222)).
- 도움말은 기준 문서가 아니다. 정확한 키·형식·오류 코드는 GitHub의 계약 문서로 연결하고 계약의 표를 복제하지 않는다(사용자 결정 2026-11-11(Q220)).
- 기준 시점은 `main`이다. `main`에 push할 때마다 GitHub Pages로 다시 게시한다. 첫 페이지에 최신 Release와 다른 동작을 적는다(사용자 결정 2026-11-11(Q221)).
- mdBook으로 만들고 대시보드 디자인 기준에 맞춘 테마를 쓴다. 대시보드 설명에는 실제 화면 캡처를 쓴다(사용자 결정 2026-11-11(Q223·Q224)).
- 대시보드에는 현재 화면 언어의 도움말을 새 탭에서 여는 링크를 둔다(사용자 결정 2026-11-11(Q226)). 대시보드는 도움말 사이트에 요청을 보내지 않는다.
- 사이트에 싣는 제3자 파일의 이름·버전·라이선스·출처를 사이트의 고지 페이지에 적는다(사용자 결정 2026-11-11(Q227)). 사이트는 외부 출처의 글꼴·스크립트·그림을 불러오지 않는다.
- 화면 동작은 [도움말 사이트 스펙](../specs/help-site.md)과 [대시보드 화면 스펙](../specs/dashboard.md)이 정한다.

## 7. 보안 및 신뢰 경계

- **중계 ID는 인증 수단이 아니다.** ID를 안다는 이유만으로 접속 권한이 있다고 간주하지 않는다.
- 대시보드·관리 API의 외부 공개는 HTTPS와 서버 내장 관리자 로그인을 필수로 한다. 관리 리스너는 HTTPS가 원칙이다. 평문 HTTP는 루프백 주소에 바인딩한 경우에만 허용한다. 루프백이 아닌 주소에 평문 HTTP를 설정하면 시작에 실패한다. 기본 바인딩을 루프백으로 두더라도 관리자 로그인을 생략하지 않는다.
- TCP Viewer·Server 역접속은 진입점별 실제 출발지 IP 허용 목록을 적용한다. TCP 접속 수락 직후, 데이터를 읽기 전에 검사한다. 기존 호환 초기 교환에 임의 인증 필드를 추가하지 않는다. Mode I 대상 허용 정책과 출발지 제한은 별개다.
- 출발지 IP 허용 목록은 TCP Viewer·TCP Server·WS Viewer·WS Server·WSS Viewer·WSS Server마다 따로 둔다. WS·WSS는 수락 때 켠 역할 목록의 합집합 또는 신뢰 프록시 여부를 검사하고, 업그레이드 때 해당 역할 목록을 검사한다. 한 역할의 허용이 다른 역할의 업그레이드를 허용하지 않는다. 켠 진입점의 목록이 없으면 시작에 실패하며, 빈 목록은 모두 거절한다.
- 0.0.0.0/0·::/0 같은 전체 허용 항목을 명시적으로 쓰면 허용하고, 시작·재로드 때 경고를 기록한다. 항목은 단일 IP, CIDR, 범위(`a-b`)이며 IPv4·IPv6 모두 쓸 수 있다. 범위의 시작이 끝보다 크거나 두 주소의 체계가 다르거나 표기가 잘못되면 설정 오류로 처리한다. 목록을 생략한 기본 허용은 하지 않는다. 출발지 IP 허용은 같은 공인 IP를 공유한 개별 사용자를 구분하지 못한다.
- 관리 세션은 중계 접속 권한이 아니다. 관리 세션 쿠키는 HttpOnly·SameSite=Strict이며 HTTPS에서는 Secure를 붙인다. 평문 HTTP 루프백에서는 Secure만 뺀다. 관리 상태 변경 요청(POST·DELETE·PATCH)에는 CSRF 방어를 적용한다. WS·WSS 중계는 출발지 IP 허용 목록과 별도로 Origin 정책을 검사한다. Origin은 허용 값과 `scheme://host[:port]` 정확 일치로 비교하며 와일드카드는 없다.
- 접속 ticket은 출발지 IP 허용 목록 위에 더하는 선택 확인이다. 외부 발급 쪽이 서명하며 관리 세션과 무관하다. TCP 진입점은 ticket을 확인하지 못한다. 평문 WS에서는 ticket이 노출되므로 그 구간은 믿을 수 있는 망 안에 있어야 한다. 같은 역할의 열린 TCP 진입점과 평문 WS 사용은 경고하며, 출발지 IP 허용 목록은 계속 적용한다(사용자 결정 2026-11-11(Q192·Q193·Q197~Q199·Q207)).
- 관리 HTTPS와 중계 WSS의 내장 TLS는 유지한다. TLS 1.2 미만 협상을 거절한다. 암호 스위트는 aws-lc-rs의 rustls 기본 목록이며 변경 키가 없다. 중계 WS·WSS 앞의 프록시 TLS 종료도 지원한다. 운영자는 프록시→VNC Relay 구간을 보호해야 한다(사용자 결정 2026-11-08(Q182·Q183)).
- 전달 헤더는 중계 WS·WSS 리스너의 `trusted_proxies`에 속한 소켓 상대에게서만 신뢰한다. 목록 오류는 주소 위조로 이어질 수 있다. 관리 리스너는 전달 헤더를 무시하며 쿠키 Secure 판단과 로그인 제한의 주소 기준을 바꾸지 않는다(사용자 결정 2026-11-08(Q182·Q183)).
- 평문 WS 리스너는 기본 비활성이다. 설정에서 명시적으로 켠 경우에만 열고, 켜면 시작 시 경고를 기록한다. 보호된 네트워크인지 판단하는 책임은 운영자에게 있다.
- WSS가 보호하는 범위는 WebSocket 연결 구간이다. 별도의 평문 TCP 구간까지 암호화되는 것으로 설명하지 않는다.
- 중계 측 연결 상한은 중계 리스너가 수락한 연결(TLS·업그레이드 단계 포함)과 Mode I 대상 연결을 센다.
- 관리 리스너·상태 리스너 연결은 중계 측 연결 상한과 별도로 센다. 한쪽이 고갈돼도 다른 쪽 수락을 막아서는 안 된다.
- 대기 수, WebSocket 메시지 크기, 초기 교환·대기·대상 연결 시간을 별도로 제한한다. 초기 요청은 250바이트 고정이다.
- Mode I의 허용 대상은 명시적으로 설정한다. 내부망 접근이 목적일 수 있으므로 사설 IP 전체를 무조건 금지하는 정책으로 대체하지 않는다.
- VNC Relay는 운영 로그를 표준 출력 또는 파일로 출력하고 최근 N개를 메모리에 보관한다. 파일 교체·장기 보관 기간·접근 권한은 운영자 책임이다. 최근 로그는 장기 이력 저장소가 아니다.
- 편집 기능을 켜면 VNC Relay를 실행하는 서비스 계정에 설정 파일 쓰기 권한이 필요하다. 같은 디렉터리에서 임시 파일 생성과 설정 파일 교체도 허용해야 한다. 이 권한은 설정을 보는 권한과 구분하며, OS별 권한 안내는 [수동 운영 안내](../how-to/operate-relay.md)에 둔다.

## 9. 호환성 조사와 독립 구현 원칙

1. 공식 사용 문서와 공개 RFB 명세로 역할·연결 흐름을 정리한다.
2. 사용 권한이 있는 실행 파일과 통제된 테스트 환경에서 초기 통신과 오류 동작을 관찰한다.
3. 메시지 방향·길이·필드·패딩·상태 전이를 별도 명세로 기록하고, 근거와 대상 버전을 함께 남긴다.
4. 명세를 바탕으로 자체 구현한다. 원본 코드를 AI 또는 변환 도구에 넣어 다른 언어로 번역하는 방식도 사용하지 않는다.
5. 실제 UltraVNC Server/Viewer와 검증하여 지원 범위와 차이를 기록한다.

패킷 관찰과 역공학 절차의 허용 여부는 관할법·제품 약관·사용 권한에 따라 별도 검토한다. 독립 구현 가능성이 모든 분석 행위의 법적 허용을 보장하는 것은 아니다.

엄격한 클린룸 인증을 완료했다고 주장하지 않는다. 필요하면 분석자와 구현자 분리 및 법률 검토를 별도 절차로 결정한다.

### 9.1 조사에서 확정할 항목

- Viewer 및 Server 측 초기 메시지 방향과 형식.
- Mode I 대상 주소·포트 문법과 기본값 처리.
- Mode II ID 형식, 길이, 비교·중복 처리.
- 매칭 전후에 이미 수신된 데이터의 처리 순서.
- 연결 종료·재접속과 대상 버전별 차이.
- WebSocket으로 같은 스트림을 제공할 때 외부 클라이언트가 지켜야 할 계약.

2026-11-01 상태: 앞의 다섯 항목은 [호환성 검증 기록 3절](../contracts/repeater-compat-record.md#3-관찰-증거-todo-14)의 관찰로 확정해 [Repeater 초기 교환 계약](../contracts/repeater-handshake-v1.md)에 반영했다. 같은 역할 중복 ID의 정책은 관찰 결과를 보고 사용자 결정 2026-11-01(Q74·Q75)로 정했다(후발 거절). 외부 WebSocket 클라이언트의 계약은 [WebSocket 중계 계약](../contracts/websocket-relay-v2.md)이 정한다. 고정 버전 noVNC 1.7.0이 `Sec-WebSocket-Protocol` 헤더를 보내지 않는다는 관찰 결과도 같은 날 그 계약 1.2절에 반영했다.

자동 회귀 검증은 매칭 경쟁, 스트림 경계, 정책 우회, 자원 회수 등 소비자에게 영향을 주는 동작을 중심으로 둔다. 문구나 내부 구현 구조를 고정하는 검증으로 대체하지 않는다.

| 4. 관리 기능 | 로컬 CLI 계정 준비, 내장 로그인·관리 세션, 관리 API·대시보드 | AC-09~10·AC-14의 계정 준비 검증·AC-19~22·AC-25·AC-27~28·AC-30~31·AC-36 통과 |

## 14. 관련 스펙과 추적

스펙 5개는 사용자 결정 2026-11-07(Q150)으로 전체를 채택해 Active로 바꿨다. 채택과 구현·테스트 완료 여부는 구분한다. 기존 범위의 지원 판정은 [작업 5.9 판정표](../how-to/set-up-and-verify.md#41-작업-59-판정표)를 따른다. 2026-11-08에 더한 설정 보기·동적 설정 편집과 확대 재로드는 사용자 결정 2026-11-08(Q174~Q177)으로 시안·문구·이름·직접 적용 설계를 채택했다. 구현·테스트는 작업 6.2~6.9에서 마쳤고, 판정은 [작업 6.9 판정표](../how-to/set-up-and-verify.md#42-작업-69-판정표)를 따른다. Mode I·II 및 TCP·WS·WSS의 지원 조합은 모두 검증 대상이다. 각 스펙의 규칙 ID는 기존 FR ID를 세부 동작으로 나누어 추적하며, 상위 요구사항 ID를 대체하지 않는다.

후속: 사용자 지시 2026-11-08와 사용자 결정 2026-11-08(Q181~Q188)로 더한 WS·WSS Server·프록시 TLS 종료·최근 로그는 미실행(구현 전)이다. 기존 판정표의 통과는 이 새 범위를 포함하지 않는다. 후속: 구현은 커밋 `3df0693`이며, 시험은 커밋 `51bd747`의 두 OS 게이트에서 통과했다([WSS Server·프록시·최근 로그 판정표](../how-to/set-up-and-verify.md#43-wss-server프록시-tls-종료최근-로그-판정표)).

접속 ticket은 사용자 결정 2026-11-11(Q192~Q204·Q207·Q212·Q213)으로 채택했다. Q211 당시에는 기준 문서만 반영했다. 후속: 구현은 커밋 `4be8e0e`이며, 계약 테스트는 같은 커밋의 두 OS 전체 게이트에서 통과했다([접속 ticket 판정표](../how-to/set-up-and-verify.md#45-접속-ticket-판정표)).
