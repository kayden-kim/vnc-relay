## 1. 범위와 적용 상태

- 대시보드의 조회·활성 세션 종료·내장 관리자 로그인과 외부 HTTPS 접근은 사용자 확정 범위다. 관리 세션 수명의 기본값과 유효 범위는 사용자 승인으로 [설정 계약](../contracts/config-v4.md)이 기준이다. 개별 API 경로·본문 형식은 [관리 API 계약](../contracts/management-api-v1.md)이 정한다(Active, 2026-10-16 채택).
- 대시보드·관리 API는 서버가 관리자 로그인을 검증한다. 중계용 출발지 IP 허용은 관리 권한을 부여하지 않는다.
- 관리 API는 JSON over HTTP이고 경로 접두사는 `/api/v1/`이다. 이 문서는 논리적인 조회·종료·설정 편집 결과를 정의한다. 개별 경로·메서드·JSON 필드 이름·오류 본문은 [관리 API 계약](../contracts/management-api-v1.md)이 정한다.
- 화면 동작·폴링·확인 대화상자는 [화면 스펙](dashboard.md)이 소유한다. 생존·준비 상태 엔드포인트와 상태 리스너는 [운영 스펙](operations.md)이 소유한다.
- 설정 보기와 동적 설정 변경 API·UI를 제공한다(사용자 지시 2026-11-08). 수동 재로드 API·CLI는 추가하지 않는다. 원격 화면 제어, 장기 이력 검색, 데이터베이스 저장도 추가하지 않는다. 최근 종료 목록은 장기 이력이 아니며 메모리에만 둔다([2.3절](#23-최근-종료-목록)).
- 최근 로그 조회를 제공한다(사용자 지시 2026-11-08, 사용자 결정 2026-11-08(Q185), 사용자 결정 2026-11-08(Q186)). 이는 메모리의 최근 운영 로그이며 장기 이력 저장이 아니다. Viewer·장치용 티켓과 인증은 이 변경의 범위가 아니다.

초기 교환 중이거나 Mode I 대상에 연결 중인 연결은 대기 연결 수와 구분한다. 하나의 중계 연결 쌍은 활성 세션 한 개로 센다. 종료 중인 세션은 정리가 끝날 때까지 활성 수에 포함한다.

서버 요약은 다음 연결 수와 사용량도 제공한다. 이 문단이 연결 수 의미의 기준이며 화면은 다시 정의하지 않는다.

- 초기 교환 중 연결 수: Repeater 초기 교환을 아직 마치지 않은 연결의 수.
- Mode I 대상 연결 중 연결 수: Mode I에서 VNC Relay가 대상에 연결을 시도하고 있는 연결의 수.
- L 사용량: 중계 측 연결 소켓의 현재 수와 상한 L. 집계 범위는 [운영 스펙 2절](operations.md#2-상태와-검증-매개변수)의 L을 따른다.
- Lm 사용량: 관리·상태 리스너 연결 소켓의 현재 수와 상한 Lm. L과 독립해 센다.
- 사용량이 상한에 도달하면 현재 수는 상한과 같다. 값을 읽지 못하면 0으로 대신하지 않고 확인 불가로 구분한다.

### 2.1 전송량의 의미

다음은 확정한 집계 기준이다. 이 정의가 전송량 의미의 유일한 기준이며 화면은 다시 정의하지 않는다. 방향별 전송량은 상대 전송 계층에 쓰기에 성공한 바이트로 센다.

- 방향은 Viewer → Server/Mode I 대상, Server/Mode I 대상 → Viewer로 고정한다.
- 카운터는 Repeater 초기 교환을 처리한 뒤 상대 전송 계층의 쓰기에 성공한 스트림 바이트 수를 누적한다. 부분 쓰기는 성공한 바이트만 센다.
- Repeater 초기 메시지와 WebSocket·TLS 프레이밍·제어 데이터는 제외한다. 초기 교환 뒤의 RFB 핸드셰이크·인증·화면 스트림은 포함한다.
- 카운터는 상대 애플리케이션이 실제로 읽었거나 화면에 표시했다는 증거가 아니다.
- 한 세션의 카운터는 감소하거나 순환해서는 안 된다. 재접속 세션은 새 세션 식별자와 0의 카운터로 시작한다.
- 시각 정보는 표시용 시각과 구분해 경과 시간을 계산한다. 시스템 시각 보정 때문에 가동 시간·대기 시간이 음수가 되지 않게 한다.
- 관리 API는 시각을 UTC ISO 8601 문자열로, 전송량을 바이트 정수로 준다. 단위를 바꾸거나 반올림한 값을 API에 넣지 않는다.
- 대시보드는 이 값을 브라우저 현지 시각(시간대 표시)과 KiB/MiB(이진 단위)로 바꿔 보여준다. 표시 규칙은 [화면 스펙](dashboard.md#시각전송량-표시-형식)이 소유한다.

### 2.2 주소와 스냅샷

- `viewer_address`·`target_address`는 실제 소켓 상대 주소다. 중계 연결이 프록시를 거쳐도 이 주소를 전달 헤더로 바꾸지 않는다.
- 활성 세션 목록·상세는 양 끝의 전송 경로를 제공한다. `target_transport`는 Mode I에서 `tcp`, Mode II에서 Server의 `tcp`·`ws`·`wss`다. 이 필드는 최근 종료 항목과 관리자 종료 응답의 `closed_session`에도 남긴다(사용자 결정 2026-11-08(Q187)).
- WS·WSS 중계 리스너의 신뢰 프록시에서 구한 전달 주소만 `viewer_forwarded_ip`·`target_forwarded_ip`로 제공한다. 전달 주소가 없으면 필드를 생략하지 않고 `null`로 준다. Mode I의 `target_forwarded_ip`는 항상 `null`이다. 결정 규칙은 [WebSocket 계약 1.8절](../contracts/websocket-relay-v2.md#18-신뢰-프록시와-x-forwarded-for)을 따른다.
- 관리 리스너 자체는 전달 헤더를 계속 무시한다. 관리 TLS 종료를 프록시로 확대하지 않는다. 내장 HTTPS·루프백 평문 HTTP·Secure 쿠키·로그인 제한의 실제 소켓 출발지 IP 규칙은 그대로다(사용자 결정 2026-11-08(Q183)). MGT-015는 유지한다.
- 읽기 응답 하나 안의 집계와 목록은 그 응답의 기준 시점에 일관돼야 한다. 집계와 목록은 한 번 포착한 상태에서 만든다. 서로 다른 시점의 요청 결과가 완전히 같은 전역 상태라고 보장하지 않는다.
- 서버 요약의 L·Lm 사용량은 위 일관성의 대상이 아니다. 사용량은 응답을 만들 때 따로 읽는 자원 사용량이다. 연결이 바뀌는 동안에는 같은 응답의 집계와 잠깐 어긋날 수 있다. 예를 들어 막 수락한 연결은 초기 교환 중 집계보다 L 사용량에 먼저 나타날 수 있다. 연결이 바뀌지 않는 동안에는 사용량이 실제 연결 수와 같다(MGT-026). 사용자 결정 2026-11-04(Q100).
- 목록을 조회한 뒤 세션이 종료될 수 있다. 이후 상세·종료 요청에서 대상 없음은 정상적인 경합 결과다.

### 2.3 최근 종료 목록

최근 종료 목록은 활성 세션이었다가 정리가 끝난 세션의 목록 정보다. 이 절이 의미의 기준이며, 화면 스펙은 이 정의를 다시 쓰지 않고 링크한다.

- 대상: 정리가 끝난 활성 세션만 담는다. 대기 만료 같은 사건은 목록에 넣지 않고 로그에만 남긴다.
- 항목: 세션 식별자, 모드, Viewer와 Server/Mode I 대상의 전송 경로, 시작·종료 시각, 방향별 최종 누적 바이트(2.1절의 방향), 종료 원인.
- 종료 원인: 정상 EOF, 연결 오류, 관리자 종료, 끊긴 연결 감지, 정리 제한 시간(E) 초과, 서버 종료, 내부 오류, 세션 만료(`session_expired`)를 구분한다. 세션 만료는 접속 ticket의 세션 만료 시각(`sx`)이 되어 서버가 세션을 끝낸 경우다([WebSocket 계약 1.9.5절](../contracts/websocket-relay-v2.md#195-101-뒤의-중계-id-대조와-세션-만료), 사용자 결정 2026-11-11(Q213)). 서버 종료는 정상 종료 유예 G 만료나 유예 중 두 번째 종료 요청으로 강제 정리한 경우다. 한 세션의 종료 원인은 정리를 시작하게 한 최초 원인이다. 강제 정리 시점에 이미 정리를 시작한 세션은 최초 원인을 유지하고 아직 정리를 시작하지 않은 세션만 서버 종료(`server_shutdown`)가 된다(사용자 결정 2026-11-01(Q82)). 서버가 Running일 때 세션 소유 작업이 panic 등 버그로 끝났고 기존 종료 원인이 없으면 내부 오류(`internal_error`)를 쓴다. 정상 종료 중(Grace·Force)에 소유 작업이 취소되면 기존 원인이 없는 경우 `server_shutdown`을 쓴다. 두 경우 모두 기존 원인이 있으면 유지한다(사용자 결정 2026-11-02(Q94)). 끊긴 연결 감지는 응답하지 않는 상대를 TCP keepalive나 WebSocket ping으로 판정해 종료한 경우다. K·Kw와 E, G의 정의는 [운영 스펙](operations.md)을 따른다. 서버 종료 항목은 프로세스가 끝나면 목록도 사라지므로 이 목록에서 조회되는지는 구현에서 확인한다.
- 보관: 메모리에만 둔다. 최대 R개를 보관하며, 초과하면 가장 오래된 항목부터 제거한다. 프로세스를 재시작하면 비운다.
- 상세·종료: 목록의 세션 식별자로 상세 조회나 종료를 요청하면 기존처럼 대상 없음을 반환한다. 목록은 목록 정보만 제공하며 상세 이력을 제공하지 않는다.
- 조회: 운영 데이터이므로 유효한 관리 세션이 있어야 조회할 수 있다([3.0절](#30-관리자-로그인과-세션)).

### 2.4 최근 로그

유효한 관리 세션으로 메모리의 최근 운영 로그를 조회한다. 보관 상한은 `recent_logs.max_entries`이며 기본 1000, 범위 0~10000이다. 0이면 아무 사건도 보관하지 않는다. 재시작하면 목록을 비운다. 보관·제거·출력 대상과의 독립성은 [운영 스펙](operations.md)이 정한다(사용자 결정 2026-11-08(Q185)).

- 운영 로그 사건 원본을 기록 순번과 함께 반환한다. `entry`는 [운영 정보 계약](../contracts/ops-info-v2.md)의 로그 한 줄과 같은 객체다. 비밀과 원시 스트림을 담지 않으며 중계 ID는 `relay_id_ref`로만 나온다.
- 레벨·사건 이름·값 검색·세션 식별자 필터를 각각 또는 함께 적용할 수 있다. 필터 사이에는 AND를 적용한다. 세션 필터는 해당 `session_id` 사건을 포함한다. 보관 중인 `session_started`로 양 끝의 연결을 찾을 수 있으면 같은 `conn_id` 사건도 포함한다. 이미 제거한 시작 사건의 관계는 복구하지 않는다.
- 커서가 없으면 일치하는 최신 `limit`개를 반환한다. `before`는 지정 순번 이전의 최신 항목, `after`는 지정 순번 이후의 가장 오래된 항목부터 고른다. 응답 항목은 항상 `seq` 오름차순이다. `has_more`로 요청 방향의 다음 페이지 유무를 알린다.
- 보관 상한과 보관 목록 전체의 가장 오래된·최근 순번을 제공한다. 순번 경계는 필터 전 기준이다. 보관 목록이 비었으면 두 경계는 `null`이다. 필터 결과만 비었으면 보관 경계를 유지한다.
- 정상적인 빈 목록과 보관 꺼짐은 `200`의 빈 `items`다. 조회 실패나 인증 실패로 대신하지 않는다. 존재하지 않는 세션 식별자도 형식이 맞으면 빈 결과다.
- `X-Relay-Poll: 1` 자동 조회는 유휴 만료를 연장하지 않는다. 헤더 없는 사용자 행동 조회는 기존 규칙대로 연장한다. 관리 세션이 없으면 `401 unauthenticated`다.
- 정확한 매개변수 범위·필터 비교·순번·페이지·오류·응답 형식은 [관리 API 계약 1.15절](../contracts/management-api-v1.md#115-최근-로그-get-apiv1logs)을 따른다. SCR-006 필터·갱신·세션에서 이동·JSON Lines 다운로드는 [화면 스펙](dashboard.md)이 소유한다(사용자 결정 2026-11-08(Q186)).


## 3. 정상 흐름과 규칙

### 3.0 관리자 로그인과 세션

1. 외부 관리 접속은 서버 내장 HTTPS로 제공한다. 관리 리스너는 HTTPS가 원칙이다. 평문 HTTP는 루프백 주소에 바인딩한 경우에만 허용한다. 루프백이 아닌 주소에 평문 HTTP를 설정하면 시작에 실패한다([운영 스펙](operations.md)의 OPS-R18). 평문 루프백에서도 관리자 로그인은 생략하지 않는다. 로그인 화면만 인증 없이 접근할 수 있으며, 운영 데이터와 상태 변경은 유효한 관리 세션이 필요하다.
2. 서버는 로컬 CLI로 준비한 관리자 자격 증명을 검증한다. 관리자 비밀번호는 Argon2id 해시로 저장하고 검증한다([운영 스펙](operations.md#32-로컬-cli-계정-준비)). 잘못된 로그인은 세션을 발급하지 않으며 계정 존재 여부·비밀값을 응답으로 노출하지 않는다. 웹 계정 생성·다중 사용자 관리 기능은 추가하지 않는다.
3. 관리 권한은 단일 역할이다. 로그인한 모든 관리자 계정은 같은 권한(운영 조회·설정 보기·활성 세션 종료·동적 설정 변경)을 가진다(사용자 결정 2026-11-08(Q169)). 로컬 CLI로 여러 계정을 준비할 수 있다. 관리자 종료 사건 로그에는 수행한 계정명을 기록한다([운영 스펙](operations.md)의 OPS-011). 설정 편집 사건에는 수행한 계정명과 바뀐 키를 기록한다([3.3절](#33-설정-보기와-동적-설정-편집)).
4. 로그인 실패는 계정별·출발지 IP별로 센다. 실패 횟수가 기준 F를 넘으면 일정 시간 로그인을 지연하거나 거절한다(MGT-R14). 이 응답은 계정 존재 여부를 드러내지 않는다. 제한 중에는 올바른 비밀번호도 거절한다. F의 기본값과 유효 범위는 [설정 계약](../contracts/config-v4.md)이 정한다.
5. 관리 세션은 서버 메모리에 보관하고, 브라우저에는 불투명 식별자 쿠키만 발급한다. 따라서 프로세스를 재시작하면 이전 관리 세션은 모두 무효이며 관리자는 다시 로그인해야 한다(MGT-R18). 관리 세션 쿠키는 HttpOnly이고 SameSite=Strict다. HTTPS에서는 Secure를 붙인다. 평문 HTTP 루프백 관리 리스너에서는 Secure만 빼고 HttpOnly·SameSite=Strict를 유지한다. SameSite와 별개로 CSRF 방어도 유지한다(MGT-R09). 비밀번호를 쿠키·URL에 넣지 않는다.
6. 관리 세션은 유휴 만료 Si와 절대 최대 수명 Sa를 가진다. 사용자 행동 요청만 유휴 만료 시각을 연장한다. 대시보드 자동 폴링 요청은 연장하지 않는다(MGT-R16). Sa가 지나면 활동과 관계없이 세션을 무효화한다. Si·Sa의 기본값과 유효 범위는 [설정 계약](../contracts/config-v4.md)이 정한다. 자동·사용자 요청 구분 방식은 [관리 API 계약](../contracts/management-api-v1.md)이 정한다.
7. 만료·로그아웃된 관리 세션은 서버에서 무효화한다. 이전 쿠키로 조회·종료를 요청하면 거절한다. 로그아웃과 관리 세션 만료 자체가 활성 VNC 중계 세션을 종료하지는 않는다.
8. 로컬 CLI 준비는 [운영 스펙](operations.md#32-로컬-cli-계정-준비)이 소유한다. 세션 수명과 Argon2id 매개변수의 기본값은 [설정 계약](../contracts/config-v4.md)이, 실제 교환 형식은 [관리 API 계약](../contracts/management-api-v1.md)이 정한다.

### 3.1 조회

1. 유효한 관리 세션을 확인한다.
2. 현재 상태와 필요한 운영 정보만 반환한다.
3. 정상적으로 조회한 빈 목록은 성공한 빈 결과다. 조회 실패나 관리 세션 없음으로 대체하지 않는다.
4. 세션 상세는 세션 식별자로 찾는다. 같은 중계 ID를 가진 다른 세션으로 대체하지 않는다.

### 3.2 관리자 종료

1. 관리자는 세션 식별자가 지정된 요청을 보낸다. UI 확인 절차는 화면 스펙에 따른다.
2. 서버가 유효한 관리 세션을 검증한다. 버튼 숨김만으로 검증을 대신하지 않는다.
3. 그 세션이 존재하면 신규 데이터 수락을 중단하고 해당 양 끝점을 종료한다.
4. 종료 요청에는 해당 자원 정리가 끝난 뒤에 완료 응답을 한다. 별도의 "처리 중" 응답 상태는 두지 않는다. 그래서 응답 시간은 최대 정리 제한 시간 E까지 길어질 수 있다. 정리 중에는 그 세션이 활성 수에 계속 포함된다([2절](#2-조회-대상과-상태)).
5. 대상이 이미 사라졌으면 대상 없음을 반환한다. 오래된 요청이 같은 중계 ID의 새 세션을 종료해서는 안 된다.

### 3.3 설정 보기와 동적 설정 편집

설정 보기는 로그인한 모든 관리자에게 제공한다. 기본값을 포함한 실행 중 유효 설정을 보여 준다. 설정 파일의 미적용 값을 실행 중 값으로 대신 보여 주지 않는다. 서버는 요청 때 파일을 다시 읽고 실행 중 유효 설정과 비교한다. 파일 상태는 차이 없음·재로드 대기·재시작 필요·검증 실패·읽기 실패를 구분한다. 파일 읽기·검증에 실패해도 실행 중 유효 설정은 조회할 수 있다. 리비전은 파일 바이트를 식별하며 주석·공백만 바뀌어도 달라진다. 정확한 필드와 상태 값은 [관리 API 계약 1.13절](../contracts/management-api-v1.md#113-설정-보기-get-apiv1config)이 정한다.

편집은 `management.config_edit = true`일 때만 제공한다. 기본은 `false`다. 이 키를 바꾸려면 설정 파일을 고치고 서버를 재시작해야 한다(사용자 결정 2026-11-08(Q170)). 화면에서 버튼을 숨기는 것으로 서버의 인증·CSRF·편집 허용 검사를 대신하지 않는다.

편집 대상은 재로드 대상 43개에서 인증서·개인키 경로 4개와 접속 ticket 공개 키 파일 경로 2개를 뺀 37개 키다. 출발지 IP 허용 목록·역할별 Origin 허용 목록·신뢰 프록시 목록·Mode I 대상 허용 목록·연결 상한·시간 제한·연결 유지를 편집한다(사용자 결정 2026-11-08(Q168·Q171·Q172), 사용자 결정 2026-11-08(Q184), 사용자 결정 2026-11-08(Q188)). 접속 ticket의 역할별 `enabled`·`issuer`·`relay_host`·`max_lifetime_secs` 8개도 편집한다(사용자 결정 2026-11-11(Q200·Q213)). TCP의 `allow`는 해당 진입점이, WS·WSS의 `allow`·`allowed_origins`는 해당 역할이 켜져 있을 때만 편집할 수 있다. `trusted_proxies`는 해당 리스너 역할 중 하나 이상이 켜져 있을 때만 편집할 수 있다. 접속 ticket의 키는 그 역할이 WS 또는 WSS 리스너에서 하나라도 켜져 있을 때만 편집할 수 있다. Mode I 대상 허용 목록은 Mode I이 켜져 있을 때만 편집할 수 있다. 인증서·개인키·접속 ticket 공개 키 파일 경로는 보기에만 나온다. 키 파일 교체는 같은 경로의 파일 내용을 바꾸는 방식을 따른다. 정확한 키와 적용 시점은 [설정 계약 1.8절](../contracts/config-v4.md#18-재로드-구분)이 기준이다.

설정 보기는 접속 ticket 키 10개를 포함한다. 모두 재로드 대상이며 공개 키 파일 경로 2개는 편집 불가다. `enabled = true`로 바꾸는 후보에 `issuer`·`relay_host`·`public_keys_file`이 빠져 있으면 `400 config_invalid`와 `config_missing_key` 진단을 반환한다. 파일과 실행 중 값은 바꾸지 않는다. 성공한 ticket 설정 변경은 새 업그레이드 요청부터 적용한다. 이미 101을 보낸 연결의 중계 ID 대조와 `sx` 타이머, 사용 기록은 유지한다([WebSocket 계약 1.9.6절](../contracts/websocket-relay-v2.md#196-설정과-적용-시점), 사용자 결정 2026-11-11(Q200·Q213)).

서버는 편집과 파일 변경 재로드를 직렬화한다. 편집 때 읽은 파일의 리비전이 요청의 리비전과 다르면 충돌로 거절한다. 지금 파일이 잘못되었거나 읽히지 않으면 편집을 거절한다. 재시작 필요 키의 차이가 남아 있어도 거절한다. 다른 관리자가 바꾸었거나 외부에서 파일을 바꾼 경우 모두 이 규칙을 따른다.

공유 잠금 안에서 임시 파일을 쓰고 flush한 뒤 원자 교체 직전에 현재 파일을 다시 읽어 리비전이 다르면 이번 요청의 파일·실행 중 값 변경 없이 충돌로 거절하되, 마지막 재확인과 교체 사이의 아주 짧은 틈은 보장하지 않는다(사용자 결정 2026-11-08(Q178)).

서버는 바뀐 값만 `serve`가 읽는 TOML 파일에 기록한다. 나머지 주석·공백·키 순서·다른 값은 보존한다(사용자 결정 2026-11-08(Q167)). 후보 전체 검증을 통과한 뒤 같은 디렉터리의 임시 파일을 원자적으로 교체한다. 쓰기·교체에 실패하면 파일과 실행 중 값은 이전 그대로다. 성공하면 같은 후보의 재로드 대상 값을 한 번에 교체한다. 부분 적용하지 않는다. 뒤따르는 파일 변경 감지가 같은 내용을 읽으면 다시 교체하지 않는다. 값이 실제로 바뀌지 않았으면 파일을 쓰거나 편집 성공 사건을 기록하지 않고 성공한 빈 적용 결과를 반환한다. 처리 순서는 [관리 API 계약 1.14절](../contracts/management-api-v1.md#114-동적-설정-편집-patch-apiv1config)이 정한다.

이미 맺은 연결·시작한 타이머·설정한 소켓 옵션은 이전 값을 유지한다. E 변경 뒤 세션 정보는 응답 때의 E + 5초를 종료 응답 대기 한도로 전달한다. 이미 시작한 종료 교환의 기한은 바꾸지 않는다. P와 `query_timeout_secs`는 재시작 필요로 남는다. 정상 종료 유예 중에도 설정 보기·편집을 처리한다.

편집 성공은 `reload_applied`(`trigger = config_edit`) 다음 `config_edited` 순서로 기록한다. 인증·CSRF를 통과한 편집 거절은 `invalid_request`를 제외하고 `config_edit_rejected`로 기록한다. 계정명과 키를 기록하되 설정값은 기록하지 않는다(계정명·바뀐 키 기록은 사용자 결정 2026-11-08(Q169)). 사건·필드와 계정명 기록 규칙은 [운영 정보 계약 1.5절](../contracts/ops-info-v2.md#15-사건-목록)·[1.8절](../contracts/ops-info-v2.md#18-관리자-계정명-기록-규칙)을 따른다.

요청마다 같은 중계 ID를 다시 찾아 종료하는 동작은 금지한다. 실제 오류 코드와 로그인·세션 교환 형식은 [관리 API 계약](../contracts/management-api-v1.md)이 정한다.

## 5. 항상 지켜야 할 규칙과 비보장 범위

- 조회가 중계 스트림을 멈추거나 데이터를 소비해서는 안 된다.
- 중계 ID는 운영 정보로 다룬다. 로그에서의 노출 수준은 운영 정책이 정한다.
- 생존·준비 상태 엔드포인트는 관리 리스너와 분리한 별도 상태 리스너에서 제공한다. 기본 바인딩은 루프백이며, 인증 없이 생존·준비 결과만 응답한다. 세션 목록·중계 ID·상대 주소·인증 비밀을 포함하지 않는다([운영 스펙](operations.md)).
- 대시보드의 '로그인 화면만 인증 예외' 규칙은 그대로다. 상태 리스너는 관리 리스너가 아니므로 이 규칙의 대상이 아니다.
- 종료된 세션의 상세 이력 조회와 재시작 전 카운터의 복구를 보장하지 않는다. 최근 종료 목록은 2.3절의 목록 정보만 제공하며 재시작 전 항목을 복구하지 않는다.
- 관리 로그인·로그아웃은 중계 접근용 IP 정책이나 활성 중계 수명을 바꾸지 않는다.

## 6. 화면 동작의 소유

[대시보드 화면 스펙](dashboard.md)의 7절이 정상·빈 결과·오류·상세 이동·종료 확인·폴링·로그인·로그아웃·최근 종료 목록·최근 로그·연결 수·사용량 표시·설정 보기·동적 설정 편집·화면 폭과 브라우저 호환·화면 언어를 소유한다. 이 문서의 수용 테스트는 API·서비스 경계의 결과를 검증하며 UI 테스트를 중복 정의하지 않는다.

## 7. 수용 테스트
