## 1. 범위와 적용 상태

- TCP·WS·WSS와 Mode I·II는 사용자 확정 범위다. Viewer는 Mode I·II, Server는 Mode II를 지원한다. WS·WSS Server 추가는 사용자 결정 2026-11-08(Q181), 사용자 결정 2026-11-08(Q188)에 따른다.
- 아래 종료 세부 정책도 채택했다(사용자 결정 2026-11-07(Q150)). 중복 ID 정책은 사용자 결정 2026-11-01(Q74)로 정했다(3.3절 4항). 모드 지원 확정과 통신 바이트 형식의 검증 여부는 구분한다.
- 외부 주체는 TCP·WS·WSS의 Viewer·Server, Mode I 대상과 운영자다. WS·WSS에서 들어온 논리적 역할에도 같은 중계 규칙을 적용한다. Server의 Mode I 거절과 전송 경로를 가리지 않는 같은 역할 중복 ID 거절도 같다.
- TLS·WebSocket 프레임 처리는 WS·WSS 스펙이 소유한다. 관리 API와 프로세스 종료는 관련 스펙이 소유한다.
- RFB 화면·인증·입력 내용을 해석하거나 변환하지 않는다. 원격 화면·입력 검증은 실제 끝점의 호환성 테스트에서 수행한다.
- 후속: 2026-11-08 추가한 WS·WSS Server는 기준 문서만 반영했다. 새 조합의 구현·검증은 아직 없다. 이전 지원 판정은 그 당시 조합의 증거로 유지한다. 후속: 구현은 커밋 `3df0693`이며, 시험은 커밋 `51bd747`의 두 OS 게이트에서 통과했다([WSS Server·프록시·최근 로그 판정표](../how-to/set-up-and-verify.md#43-wss-server프록시-tls-종료최근-로그-판정표)).

## 3. 정상 흐름

### 3.1 초기 교환

1. TCP Viewer 진입점과 TCP Server 진입점은 각각 자기 진입점의 출발지 IP 허용 목록으로 실제 연결 상대의 출발지 IP를 검사한다. 검사는 접속 수락 직후, 데이터를 읽기 전에 한다. 목록에 없는 출발지의 연결은 초기 교환에 진입하지 않는다. 명시적으로 빈 목록이면 그 진입점의 모든 출발지를 거절한다. 명시적 전체 허용 항목의 처리는 [운영 스펙](operations.md#4-보안과-신뢰-경계)을 따른다. 기본 허용이나 전달 헤더에 의한 우회는 허용하지 않는다. WS·WSS 진입점의 검사 시점은 [WebSocket 스펙](websocket.md)이 정한다.
2. [호환 계약 1절](../contracts/repeater-handshake-v1.md#1-형식과-의미)에 따라 요청을 해석한다. Viewer 쪽에는 초기 교환에 들어가자마자 시작 바이트를 보낸다. Server에는 보내지 않는다. 초기 요청은 250바이트 고정이고, 모드는 값의 `ID:` 접두어로 정한다. 역할은 TCP에서는 리스너가, WS·WSS에서는 `/relay`·`/relay/server` 경로가 정한다. Server는 Mode II만 받는다. 설정으로 비활성화한 모드의 요청은 대기 등록·대상 연결 전에 거절한다(RLY-R17).
3. 대상 주소나 중계 ID는 호환 계약이 정한 초기 교환 절차 안에서 얻는다. 별도의 대상 선택 메시지나 URL API를 추가하지 않는다.
4. 초기 요청 뒤에 이미 수신한 데이터는 스트림의 첫 바이트로 전달한다. 이 데이터도 중계 버퍼 상한에 포함한다.

IP 목록 재로드는 [운영 스펙](operations.md#33-파일-변경-자동-감지와-부분-재로드)에 따른다. 허용 검사를 통과한 TCP 연결과 업그레이드를 완료한 WS·WSS 연결은 이후 목록에서 제거돼도 초기 교환·대기·활성 수명을 유지한다. 기존 대기 연결은 원래의 허용 판정으로 매칭될 수 있다. 새 TCP 연결의 허용 검사와 WS·WSS 업그레이드 검사에는 당시 유효한 목록을 적용한다.

### 3.2 Mode I

1. 호환 요청에서 대상 주소와 포트를 얻는다.
2. 이름을 사용하는 경우 주소를 해석한다. 실제 연결에 사용할 IP·포트에 허용 정책을 적용한다.
3. 검사한 IP가 아닌 다른 주소로 연결해서는 안 된다. 주소를 다시 해석해 연결하는 경우 새 결과에도 정책을 적용한다.
4. 대상 연결 성공 후 활성 세션을 만들고 양방향 중계를 시작한다.
5. 정책 거절 시 대상 연결을 만들지 않는다. 연결 실패는 RLY-R06의 원인으로 운영자에게 표시한다.

이 절의 요청은 Viewer 역할만 보낼 수 있다. WS·WSS Server가 Mode I 대상 문법을 보내면 TCP Server와 같이 `handshake_invalid`로 거절한다. 대상 연결과 대기 등록을 만들지 않는다.

### 3.3 Mode II

1. 역할은 TCP 리스너 또는 WS·WSS 요청 경로로, 중계 ID는 [호환 계약 1.2절](../contracts/repeater-handshake-v1.md#12-초기-요청-250바이트)대로 정한다. 중계 ID는 숫자로만 되어 있고, 바이트열이 정확히 같을 때만 같은 ID다(사용자 결정 2026-11-01(Q68)). 앞자리 0 제거·대소문자 변환·공백 제거·숫자 변환으로 서로 다른 ID를 합치지 않는다. 대상 버전 Repeater와 결과가 다른 입력은 [계약 3.1절](../contracts/repeater-handshake-v1.md#31-대상-버전-repeater와-다르게-처리하는-입력)에 있다.
2. 유효한 상대가 없으면 연결을 대기에 등록한다. 양쪽 접속 순서를 모두 허용한다.
3. 같은 ID의 반대 역할이 도착하면 두 연결을 한 번만 활성 세션으로 전환한다. 대기 시간 초과·단절과 경합하더라도 종료된 연결을 매칭하지 않는다.
4. **중복 정책:** 대기 중이거나 활성 세션이 점유한 ID에 같은 역할의 연결이 추가되면 후발 연결을 바로 닫아 거절한다. TCP는 FIN으로 닫고, WS·WSS는 close 4004(`duplicate_id`)를 보낸다. 거절한 연결은 대기 등록을 만들지 않으며, 기존 연결과 활성 세션은 유지한다. 활성 세션 종료 정리가 끝난 뒤 ID를 다시 사용할 수 있다. 사용자 결정 2026-11-01(Q74). 대상 버전 Repeater는 후발 연결을 닫지 않고 둔다. 활성 세션이 쓰는 ID의 중복은 대상 버전에서 관찰하지 않았다(Q75). 차이는 [Repeater 초기 교환 계약 3.1절](../contracts/repeater-handshake-v1.md#31-대상-버전-repeater와-다르게-처리하는-입력)에 있다.
   - 후속: 사용자 결정 2026-11-08(Q181·Q188)에 따라 TCP·WS·WSS Server에도 같은 정책을 적용한다. 대기·활성 ID 점유는 전송 경로별로 나누지 않는다(RLY-R20).
5. 매칭 시 대기 시간이 끝난다. 세션 식별자는 중계 ID와 별도로 부여한다.

### 3.4 중계와 EOF

- 중계는 Repeater 초기 교환 뒤의 RFB 스트림을 해석하지 않는다. VNC 인증과 화면 처리는 끝점의 책임이다.
- 읽기 속도를 수신자에 맞춰 제한한다. 전송 전에 받은 후속 데이터도 무제한으로 쌓지 않는다.
- **TCP 종료:** 한쪽 TCP 연결에서 정상 EOF를 받으면, 이미 받은 데이터를 상대에게 모두 전달한 뒤 상대 연결의 쓰기 방향만 닫는다. 반대 방향은 [정리 제한 시간 E](operations.md#2-상태와-검증-매개변수)까지 계속 전달한다.
- 반대 방향도 종료되거나 E에 도달하면 최종 정리한다. E의 기본값과 유효 범위는 [설정 계약](../contracts/config-v4.md)이 정한다.
- 연결 오류·관리자 종료·종료 유예 만료 시 미전달 데이터의 완전한 도착을 보장하지 않는다. 정상 중계의 무손실 보장과 강제 중단을 구분한다.
- **끊긴 연결 감지:** 중계 측 TCP 소켓 전체(Viewer·Server·Mode I 대상, WS·WSS의 하부 TCP 포함)에 TCP keepalive를 적용한다. 응답하지 않는 상대의 대기·활성 연결은 K 안에 끊긴 연결로 판정하고 정리한다(RLY-R18). K는 [운영 스펙의 검증 매개변수](operations.md#2-상태와-검증-매개변수)에서 정한다. keepalive에 응답하는 연결은 데이터가 없어도 종료하지 않는다(RLY-R19). WS·WSS의 ping은 [WebSocket 스펙](websocket.md#4-오류와-종료)이 정한다.
- WS·WSS가 섞인 세션의 종료는 [WebSocket 종료 규칙](websocket.md#4-오류와-종료)이 정한다.

## 4. 오류와 복구

| 조건 | 외부 결과 | 상태와 자원 | 재시도 |
| --- | --- | --- | --- |
| 형식 오류 | 요청 거절(연결 종료) | 활성·대기 등록 없음 | 올바른 요청으로 새 접속 |
| 초기 교환 미완료·시간 초과 | 연결 종료, 원인 구분 | 예약한 연결 자원 회수 | 새 접속 |
| 금지 대상·최종 IP 정책 위반 | Mode I 연결 거절 | 대상 연결 없음 | 허용 대상·설정으로 새 접속 |
| 주소 해석 실패·연결 거절·시간 초과 | 원인별 실패 | 시도 중 자원 회수 | 자동 재시도는 보장하지 않음 |
| Mode II 같은 역할 중복 | 후발 연결을 바로 닫음(TCP FIN, WS·WSS close 4004 `duplicate_id`) | 선행 연결·활성 세션 유지, 후발 연결은 대기 등록 없음 | 기존 점유 해제 후 새 접속 |
| 대기 단절·만료 | 해당 대기 제거 | 후속 상대가 이전 연결과 매칭되지 않음 | 양 끝점이 새로 접속 |
| 중계 I/O 오류 | 해당 세션 종료 | 자원 회수, 종료 원인 기록 | 새 세션으로 접속 |
| 끊긴 연결 감지 | 해당 연결 종료. 활성 세션이면 반대쪽 연결도 종료, 종료 원인은 끊긴 연결 감지 | 대기 등록 해제 또는 세션 정리, 자원 회수, 다른 세션 영향 없음 | 같은 ID로 새 Server·Viewer 접속 |

[Repeater 초기 교환 계약 2절](../contracts/repeater-handshake-v1.md#2-오류)에 따라 오류 응답 바이트를 보내지 않는다. TCP는 연결을 닫아(FIN) 알리고, WS·WSS는 close 코드로 알린다. 대상 버전 Repeater도 오류 바이트를 보내지 않았다.

## 5. 항상 지켜야 할 규칙과 비보장 범위

- 서로 다른 세션 사이에 바이트나 상태를 섞어서는 안 된다.
- 중계 ID를 접속 권한의 증거로 사용해서는 안 된다. 접근 경계는 [운영·보안 규칙](operations.md#4-보안과-신뢰-경계)을 따른다.
- 최초 세션의 지연된 종료가 같은 ID의 새 세션을 제거해서는 안 된다.
- 프로세스 재시작 후 TCP 연결 복구와 자동 재매칭을 보장하지 않는다.
- 관찰·실행 증거가 없는 버전이나 확장 기능을 호환 지원으로 표기하지 않는다.

## 6. 검증 전제

- Mode I과 TCP·WS·WSS Viewer, Mode II의 TCP·WS·WSS Viewer × TCP·WS·WSS Server를 검증한다. Mode II는 양 접속 순서를 포함한다. TCP의 실제 UltraVNC 화면·입력 테스트와 WS·WSS의 스트림 테스트를 구분한다.
- 유효·무효 초기 메시지 데이터는 선정한 버전의 공개 통신 규칙과 허가된 관찰에서 확보한다. 원본 구현 소스를 복사·번역해 테스트 데이터를 만들지 않는다.
- 크기·시간의 경계 테스트는 [운영 스펙의 검증 매개변수](operations.md#2-상태와-검증-매개변수)를 사용한다.

## 8. 미결정 사항

확정 책임은 프로젝트 요구사항·운영 결정 담당자에게 있다. 통신 사실은 허가된 관찰과 실행 증거로 확정한다.

현재 남은 미결정 사항은 없다.

후속: RLY-028과 변경된 RLY-023·024의 2026-11-08 추가 범위는 미실행 (구현 전)이다. 계약 테스트 계획은 [WebSocket 계약 5절](../contracts/websocket-relay-v1.md#5-예제와-계약-테스트)을 따른다. 이 스펙에서 새로 채택을 기다리는 이름은 없다. 신뢰 프록시 경고 이름과 필드는 사용자 결정 2026-11-08(Q191)으로 채택했으며 [WebSocket 스펙 8절](websocket.md#8-미결정-사항)에서 기록한다. 후속: 구현은 커밋 `3df0693`이며, 시험은 커밋 `51bd747`의 두 OS 게이트에서 통과했다([WSS Server·프록시·최근 로그 판정표](../how-to/set-up-and-verify.md#43-wss-server프록시-tls-종료최근-로그-판정표)).
