## 1. 범위와 적용 상태

- TCP·WS·WSS, Mode I·II, Windows 11 x64·Ubuntu 24.04 LTS x64 지원 목표(Windows Server 제외), 서버 내장 TLS(TLS 1.2 이상), 공개 관리 HTTPS·내장 로그인·관리자 종료, 진입점별 출발지 IP 허용 목록, 활성 100세션 목표, 최신 안정판 고정 검증과 MIT는 사용자 확정 사항이다.
- 로컬 CLI 관리자 계정 준비(단일 관리자 역할·여러 계정 가능, 준비된 계정이 없으면 시작 실패), Windows 11 x64·Ubuntu 24.04 LTS x64 실행파일·설정 예시 배포, 인증서·출발지 IP 허용 목록 자동 감지 재로드, IP 정책의 새 접속 적용은 사용자 확정 사항이다. 재로드 대상을 27개로 넓혔다(사용자 결정 2026-11-08(Q168·Q171)). 관리 API·대시보드 편집은 같은 설정 파일에 저장하며 기본은 꺼짐이다(사용자 결정 2026-11-08(Q167·Q170)).
- 서버 실행과 관리자 계정 준비는 실행파일 하나의 서로 다른 하위 명령이다. 설정 파일은 TOML이다. 출발지 IP 허용 목록 항목은 단일 IP, CIDR, 범위(`a-b`)이며 IPv4·IPv6 모두 받는다. 관리자 비밀번호 해시는 Argon2id다. 운영 로그는 JSON Lines다. 파일 변경은 OS 파일 알림으로 감지하고 주기 확인으로 보조한다. 구현의 비동기 런타임은 tokio, TLS는 rustls다. 이 항목들은 사용자 확정 사항이다.
- 평문 WS는 기본 비활성이며 명시적으로 켠 경우에만 연다. 관리 평문 HTTP는 루프백 바인딩에서만 허용한다. 상태 엔드포인트는 기본 루프백의 별도 리스너에서 제공한다. 재로드 대상이 아닌 값이 다르면 후보 전체를 거절한다. 이 항목들은 사용자 확정 사항이다.
- 단일 인스턴스 운영과 끊긴 연결 감지(TCP keepalive·WebSocket ping)는 사용자 확정 사항이다. 프로세스 사이에 대기·세션·카운터 상태를 공유하지 않는다. 이미 사용 중인 리스너 주소로 두 번째 프로세스를 시작하면 시작 실패다. 상대가 살아 있는 유휴 연결은 끊지 않는다.
- 검증 대상 OS는 Windows 11 x64와 Ubuntu 24.04 LTS x64다. Windows Server는 검증 대상이 아니다. 실제 실행 증거가 없으면 지원 완료로 표시하지 않는다. 이 항목은 사용자 확정 사항이다.
- VNC Relay는 로그를 표준 출력 또는 지정한 파일로 출력만 한다. 로그 파일 교체·보관 기간·접근 권한은 운영자 책임이며, 수동 운영 안내에 권장 사항을 적는다. 이 항목은 사용자 확정 사항이다.
- 수명 세부 정책도 채택했다(사용자 결정 2026-11-07(Q150)).
- 이 문서는 하위 명령 이름·파일 확장자·환경 변수 이름·설정 키 이름을 임의로 정하지 않는다. 이 이름은 [설정 계약](../contracts/config-v3.md)과 [CLI 계약](../contracts/cli-v1.md)이 정한다(둘 다 Active, 2026-10-16 채택). 기본 포트도 이 문서가 정하지 않으며 설정 계약이 기준이다. tokio·rustls 외 Rust 라이브러리는 [PRD 1절 "구현 기술" 행](../requirements/PRD.md#확정-기준)이 단일 기준이다. 그 라이브러리는 2026-10-20 의존성 라이선스 검토 뒤 확정했다. 이 문서는 라이브러리 이름을 정하지 않는다.
- 변경 범위는 시작 검증, 제한, 종료, 운영 정보, 접근 경계, 성능·호환성·출처의 수용 판정이다. 설치·빌드 절차는 [개발 환경·검증 how-to](../how-to/set-up-and-verify.md)에서 관리한다.
- 신규 중계 프로토콜·세션 영속화·자동 재접속·전체 설정 재로드·OS 서비스 등록·컨테이너 배포는 추가하지 않는다. 설정 보기와 23개 대상 키의 웹 편집은 제공한다(사용자 지시 2026-11-08, 사용자 결정 2026-11-08(Q167~Q172)). 수동 재로드 API·CLI는 추가하지 않는다.

L·Lm·Lw·B·M·H·U·W·C·E·G·K·Kw는 재로드 대상이다(사용자 결정 2026-11-08(Q171)). 새 값의 적용 시점은 3.3절과 [설정 계약 1.8절](../contracts/config-v3.md#18-재로드-구분)을 따른다. F·Si·Sa·P·R과 `dashboard.query_timeout_secs`는 재시작이 필요하다. 세션 정보 응답의 `dashboard.terminate_timeout_secs`는 응답 때의 E + 5초다.

Mode I의 Viewer 연결과 생성한 대상 연결은 L에서 각각 한 개다. Mode II의 Viewer·Server 연결도 각각 한 개다. 관리·상태 연결은 L이 아니라 Lm에서 센다. 수신·송신 소켓을 구분해 상한을 우회해서는 안 되며, 대상 연결 생성 전에도 예산을 확보한다. 리스닝 소켓 자체는 연결 수에 세지 않지만 기본 자원 측정에 포함한다.

활성 100세션에는 중계 연결 소켓만 최소 200개가 필요하다. 초기 교환·대기·연결 중 작업에 필요한 여유는 L에, 관리 HTTPS·상태 리스너에 필요한 여유는 Lm에 반영한다. 100은 검증 규모 목표이지 모든 연결의 상한 값이나 지원 완료 증거가 아니다.

## 3. 정상 흐름과 수명 규칙

### 3.1 설정 검증과 시작

1. TOML 설정 파일과 로컬 CLI로 준비한 관리자 정보를 읽어 유효 설정을 만든다. 키 이름·구조·입력 방식은 [설정 계약](../contracts/config-v3.md)이 정한다.
2. 리스닝 주소·포트, 활성 모드, 진입점별 출발지 IP 허용 목록, Mode I 대상 허용 정책, 한도·시간, 관리자 자격 증명과 내장 TLS 인증서 설정을 검증한다.
3. 잘못된 값·누락된 필수 보안 경계는 시작 실패로 보고한다. 보안 검사를 묵시적으로 끄거나 임의의 공개 주소로 대체하지 않는다.
4. 켠 진입점마다 출발지 IP 허용 목록을 확인한다. 목록이 없으면 시작 실패다. 명시적으로 빈 목록이면 그 진입점의 모든 출발지를 거절한다. 목록 항목은 단일 IP, CIDR, 범위(`a-b`)만 받으며 IPv4·IPv6 모두 해당한다. 범위의 시작이 끝보다 크거나, 두 주소의 체계(IPv4·IPv6)가 다르거나, 표기가 잘못된 항목은 설정 오류이며 시작 실패다. `0.0.0.0/0`, `::/0` 같은 전체 허용 항목은 허용하고 시작 경고를 기록한다.
5. 준비된 관리자 계정이 하나도 없으면 시작 실패다. 종료 코드는 [CLI 계약 2.1절](../contracts/cli-v1.md#21-종료-코드)의 계정 파일 오류다.
6. 평문 WS 리스너는 설정에서 명시적으로 켠 경우에만 연다. 켜면 시작 경고를 기록한다. 보호된 네트워크인지 판단하는 것은 운영자 책임이다. 인터넷에 공개하는 WebSocket 진입점을 WSS로만 두는 것도 운영자가 정한다. 수동 운영 안내에 이 권장 사항을 적는다(사용자 결정 2026-11-04(Q96)).
7. WSS·관리 HTTPS는 TLS 1.2 미만 협상을 거절한다. 허용 암호 스위트는 선택한 rustls 암호 모듈(crypto provider)이 제공하는 rustls 기본 목록이다. 설정 키가 없으므로 운영자가 바꿀 수 없다. 스위트 이름은 모듈에 따라 다르므로 이 문서에 나열하지 않는다. 암호 모듈은 aws-lc-rs다(사용자 결정 2026-10-20).
8. 채택한 필수 리스너를 준비한다. 상태 리스너는 기본 루프백의 별도 리스너로 준비한다. 일부 필수 리스너 준비에 실패하면 시작 중 확보한 자원을 회수한다. 부분 준비 상태를 정상 준비 완료로 표시하지 않는다.
9. 관리 바인딩은 기본 루프백으로 둘 수 있으며 설정한 주소로 외부 HTTPS 접근을 지원한다. 내장 TLS와 관리자 로그인 준비 없이 공개 관리 요청을 수락하지 않는다. 기본 관리자 비밀번호를 묵시적으로 제공하지 않는다.
10. 관리 평문 HTTP는 루프백 바인딩에서만 허용한다. 비루프백 주소에 평문 HTTP를 설정하면 시작 실패다. 평문 루프백에서도 관리자 로그인을 생략하지 않는다. 쿠키 보안 속성은 [관리 기능](management.md)의 3.0절이 정한다.
11. 설정 파일과 참조한 인증서·개인키 파일의 변경 감지(OS 파일 알림과 주기 확인)를 준비한 뒤 접속을 받는다. 변경 감지 준비가 불가능하면 이를 묵시적으로 끄고 시작하지 않는다.
    로그 디렉터리 알림 등록만 실패한 경우는 시작 실패에 해당하지 않는다. `reload_watch_failed`(`notify_error`)를 쓰고 시작을 계속하며 Dp마다 로그 파일 다시 열기와 알림 등록을 시도한다(사용자 결정 2026-11-04(Q111)).

단일 인스턴스로 운영한다. 프로세스 사이에 대기·세션·카운터 상태를 공유하지 않는다. 이미 사용 중인 리스너 주소로 두 번째 프로세스를 시작하면 시작 실패다. 두 번째 프로세스의 시작 실패는 첫 번째 프로세스의 대기·활성 세션에 영향을 주어서는 안 된다.

### 3.2 로컬 CLI 계정 준비

1. 운영자는 서버 시작 전에, 서버를 실행하는 같은 실행파일(Windows 11 x64·Ubuntu 24.04 LTS x64 배포)의 계정 준비 하위 명령을 실행한다. 서버 실행과 계정 준비는 서로 다른 하위 명령이다. 공개 웹 계정 생성·기본 비밀번호는 제공하지 않는다.
2. 여러 관리자 계정을 준비할 수 있다. 모든 계정은 같은 단일 관리자 역할을 가진다. 조회·세션 종료·동적 설정 변경 권한을 계정별로 나누지 않는다(사용자 결정 2026-11-08(Q169)).
3. 계정명과 비밀번호를 입력한다. 비밀번호는 터미널에 표시하지 않으며 명령행 인수·URL로 받지 않는다.
4. 솔트를 포함한 Argon2id 비밀번호 해시만 저장한다. 평문 비밀번호·해시를 일반 출력이나 로그에 기록하지 않는다. 저장 파일은 허용되지 않은 일반 OS 계정이 읽거나 수정할 수 없도록 보호한다.
5. 입력 취소·검증·저장 실패 시 이전의 유효한 자격 증명을 손상하지 않는다. 준비 완료는 필요한 저장이 성공한 뒤에만 알린다.
6. 실행 중인 서버의 계정 변경·세션 변경을 위한 네트워크 API는 추가하지 않는다. 기존 계정 정보를 바꿀 때는 서버를 정상 종료하고 로컬 CLI로 준비한 뒤 다시 시작한다.

하위 명령 이름·옵션·파일 위치는 [CLI 계약](../contracts/cli-v1.md)이, Argon2id 매개변수는 [설정 계약](../contracts/config-v3.md)이 정한다. 두 계약은 Active(2026-10-16 채택)다. `vnc-relay admin add|passwd|remove|list`로 관리자 계정을 준비한다.

### 3.3 파일 변경 자동 감지와 부분 재로드

재로드 대상은 27개다. 이 중 인증서·개인키 경로 4개를 뺀 23개가 관리 API 편집 대상이다. 정확한 키 목록·편집 조건은 [설정 계약 1.8절](../contracts/config-v3.md#18-재로드-구분)을 따른다. 아래 표의 "교체 뒤"는 후보 검증과 유효 설정 교체가 끝난 뒤다. 이미 맺은 연결·이미 시작한 타이머·이미 설정한 소켓 옵션은 이전 값을 유지한다.

| 설정 | 적용 방식 | 기존 연결·상태 |

| TLS 인증서·개인키 | 파일 변경을 자동 감지·검증한 뒤 새 TLS 핸드셰이크부터 적용 | 기존 TLS 연결 유지, 운영자 제공 인증서 교체이며 자동 발급 기능은 아님 |
| TCP Viewer 출발지 IP 허용 목록 | 유효한 설정 변경 뒤 새 TCP 접속부터, 수락 직후 판정 시점에 적용 | 이미 허용된 초기 교환·대기·활성 연결 유지, 대기 연결의 매칭 자격도 유지 |

TCP 접속은 수락 직후, 데이터 읽기·TLS 협상 전에 출발지 IP 허용 목록을 검사한다. WS·WSS 접속은 수락 직후 한 번 검사하고, 업그레이드 직전에 당시 유효한 목록으로 한 번 더 검사한다. 이 판정과 재로드 적용은 이전 또는 새 정책 중 하나로 일관되게 처리한다. 업그레이드 전의 HTTP·TLS 연결은 아직 중계 접속이 아니다. 재검사에서 거절된 연결은 업그레이드하지 않는다. 관리 HTTPS·로그인 권한은 중계 IP 정책과 별개다.

1. 설정 파일과 켜진 진입점·관리 리스너가 쓰는 인증서·개인키 파일의 변경·교체 저장을 OS 파일 알림으로 감지한다(사용자 결정 2026-10-22(Q50)). 꺼진 진입점의 파일은 감시하지 않는다. 알림을 놓친 변경도 주기 확인(간격 Dp)으로 감지한다. 변경이 안정되면 설정·파일을 한 재로드 후보로 읽는다.
2. 시작과 같은 전체 설정 검증을 한다. 구문·모든 정책·한도·시간·값 관계·인증서/개인키 쌍·필수 보안 설정을 포함한다. 임시 저장·한쪽 인증서 파일만 교체·파일 일시 소멸은 유효한 새 구성으로 취급하지 않는다.
3. 재로드 후보는 실행 중 유효 설정과 비교한다. 재로드 대상이 아닌 값이 실행 중 값과 다르면 후보 전체를 재시작 필요로 거절한다. 그 차이가 설정 파일에 남아 있는 동안에는 이후 재로드 대상 변경(IP·인증서·관리 API 편집 포함)도 모두 거절한다. 급한 인증서 교체도 같다. 운영자는 그 값을 되돌리거나 재시작해야 한다. 일부 값만 조용히 적용하지 않으며, 거절된 후보를 적용된 설정으로 보고하지 않는다.
4. 유효한 후보의 재로드 대상 값을 원자적으로 한 번에 교체한다. 후보 검증 중에는 이전 유효 설정과 기존 중계를 유지한다. 실패하면 어느 값도 일부만 반영하지 않는다. 전체 출발지 허용 항목은 `allow_all_source`, 전체 대상 허용 항목은 `allow_all_target` 경고를 `phase = reload`로 기록한다.
5. 검증 중 후속 파일 변경을 관찰하면 이전 후보를 적용하지 않는다. 늦게 끝난 이전 검증이 새 후보나 이전 유효 설정을 덮어써서는 안 된다. 마지막 변경을 감지한 뒤 D 안에, 안정된 최신 파일 상태에 대해 적용 또는 실패 결과를 확인할 수 있어야 한다.
6. 성공·실패·재시작 필요·변경 감지 장애를 비밀 없는 운영 사건으로 구분한다. `reload_applied.trigger`는 파일 감지이면 `file_watch`, 관리 API 편집이면 `config_edit`다. 실행 중 감지 장애는 이전 유효 설정을 유지하며 원인을 알린다. 적용하지 않았는데 성공으로 표시하지 않는다.
7. 정상 종료가 시작되면 파일 감지에 따른 새 후보 적용을 중지한다. 관리 API 편집은 다른 관리 요청처럼 종료 유예 중에도 처리한다. 어느 경로의 재로드도 종료를 취소하거나 새 중계 수락을 다시 시작해서는 안 된다.

관리 API 편집 경로는 `PATCH /api/v1/config`다. `management.config_edit = true`일 때 로그인한 모든 관리자가 같은 단일 역할로 편집할 수 있다. 처리 순서·오류는 [관리 API 계약](../contracts/management-api-v1.md), 파일 쓰기는 [설정 계약 1.10절](../contracts/config-v3.md#110-관리-api-편집의-파일-쓰기)을 따른다. 편집과 파일 감지 재로드는 직렬로 처리한다. 고칠 내용을 같은 로더로 검증하고, 주석·공백·순서를 보존한 파일을 원자적으로 쓴 뒤 같은 후보를 즉시 한 번 교체한다. 그 뒤의 파일 감지는 차이가 없으므로 다시 교체하거나 `reload_applied`를 기록하지 않는다. `reload_change_detected`는 기록될 수 있다. 실제 값 차이가 없는 편집은 파일 쓰기·교체·`config_edited` 사건을 만들지 않는다. 쓰기 실패이면 파일과 실행 값은 이전 그대로다.

시간 기준: 파일 알림을 놓친 변경은 Dp 안에 감지하고, 마지막 변경을 감지한 뒤 D 안에 적용 또는 실패 결과를 확인한다. 최대 지연은 Dp + D다(사용자 결정 2026-10-22(Q50)). D·Dp는 [설정 계약](../contracts/config-v3.md)을 따른다. 파일 감지의 구체 방식은 [파일 변경 감지 모듈 설계](../architectures/file-watch.md)에 있다. Windows 디렉터리·편집기 핸들 한계는 사용자 결정 2026-10-23(Q57)와 그 설계 §9 항목 14를 따른다. 설정 보기·편집 API는 제공하되, 별도의 수동 재로드 API·CLI는 추가하지 않는다.

### 3.4 정상 종료와 재시작

1. 정상 종료 사건을 받으면 신규 중계 접속을 중지한다. 종료 중 도착한 접속을 새 세션으로 만들지 않는다.
2. 초기 교환·대기·대상 연결 중인 미완성 작업을 종료하고 등록을 해제한다.
3. 활성 세션에는 G의 유예를 부여한다. 그 전에 자발적으로 끝나면 즉시 정리한다. G가 0이면 유예 없이 바로 정리한다.
4. G 만료 시 남은 활성 세션을 강제 정리한다. 아직 정리를 시작하지 않은 세션에 프로세스 종료에 따른 원인 `server_shutdown`을 남긴다. 이미 정리를 시작한 세션은 최초 정리 시작 원인을 유지한다(사용자 결정 2026-11-01(Q82)).
5. 자원 정리 후 프로세스를 종료한다. 재시작은 새 프로세스 수명이며 이전 소켓·중계 ID 매칭·카운터를 복원하지 않는다.

종료 유예 중에도 관리 조회·관리자 로그인·관리자 종료를 모두 처리한다. 서버 상태는 관리 요약에 `shutdown_grace`로 표시한다([관리 API 계약 1.6절](../contracts/management-api-v1.md#16-서버-요약-get-apiv1summary)). 상태 리스너의 준비 확인은 이 상태에서 준비 아님이다([운영 정보 계약 1.12절](../contracts/ops-info-v1.md#112-상태-리스너와-엔드포인트)).

필수 리스너(상태·관리·설정으로 켠 TCP·WS·WSS)의 복구 불가능 수락 오류는 같은 종료 절차를 시작한다. 일시 오류·자원 부족은 기존 100밀리초 뒤 재시도한다. 횟수 임계값·새 설정은 없다. 정확한 OS 분류는 [운영 정보 계약 1.12절](../contracts/ops-info-v1.md#112-상태-리스너와-엔드포인트)을 따른다. 장애 종료는 `shutdown_started(trigger=fatal_error)`를 `error`로 기록하고 정리 후 종료 코드 1로 끝난다. 살아 있는 상태 HTTP는 유예·정리 동안 `/readyz` 503 `listener_failed`와 `/livez` 200을 유지한다. 상태 소켓 자체 장애의 응답은 보장하지 않는다. 관찰을 위한 별도 대기는 없다. 정상 종료가 먼저 시작되면 뒤늦은 장애는 최초 원인·유예를 바꾸지 않는다. 사용자 결정 2026-11-05(Q114).

유예 중 두 번째 종료 요청(Ctrl+C·SIGTERM 등)을 받으면 남은 유예를 건너뛰고 남은 세션과 등록을 즉시 강제 정리한다. 세션의 종료 원인은 아직 정리를 시작하지 않은 세션에만 `server_shutdown`을 기록하고, 이미 정리를 시작한 세션은 최초 정리 시작 원인을 유지한다(사용자 결정 2026-11-01(Q82)). 정상 종료 요청에 따른 종료로 본다. 종료 코드는 [CLI 계약 1.8절](../contracts/cli-v1.md#18-수동-시작과-종료)이 정한다.

Windows에서 `serve`를 실행한 콘솔 창을 닫으면 종료 요청과 두 번째 종료 요청을 함께 받은 것으로 처리한다. 신규 중계 접속을 중지하고, G를 기다리지 않고 남은 세션과 등록을 즉시 강제 정리한다. 종료 원인 규칙은 두 번째 종료 요청과 같다. OS는 창을 닫은 뒤 기본 5초 안에 프로세스를 끝낸다([Microsoft HandlerRoutine 문서](https://learn.microsoft.com/en-us/windows/console/handlerroutine)의 Timeouts). 그러므로 정리와 종료 사건 기록은 그 안에 끝나야 한다. 정상 종료 요청에 따른 종료로 본다. 사용자 결정 2026-11-04(Q102).

Windows 로그오프·시스템 종료의 신호는 서비스만 받는다. 대화형 콘솔 프로그램은 그 전에 OS가 끝낸다(같은 문서). 그러므로 로그오프·시스템 종료는 강제 종료로 보고 정상 유예와 종료 기록을 보장하지 않는다.

Windows 11 x64·Ubuntu 24.04 LTS x64의 수동 실행·정상 종료 방식을 검증한다. Windows Server는 검증하지 않는다. OS 서비스 등록·서비스 제어 산출물과 컨테이너는 배포 범위에서 제외한다. 충돌·전원 장애에도 정상 유예를 보장하지 않는다.

### 3.5 운영 정보

- 접속 수락·거절, 대기 등록, 매칭, 대상 연결 실패, 종료와 자동 재로드 성공·실패·재시작 필요·감지 장애를 구분해 기록한다.
- 관리자 종료와 동적 설정 편집·거절 사건에는 수행한 관리자 계정명을 기록한다. 편집 사건에는 바뀐 키를 기록하고 설정 값은 기록하지 않는다(사용자 결정 2026-11-08(Q169)). 사건·필드·순서는 [운영 정보 계약 1.5절](../contracts/ops-info-v1.md#15-사건-목록)을 따른다.
- 사건은 적용 가능한 세션 식별자·역할·모드·시각·원인으로 추적한다. 세션 생성 전 사건에는 존재하지 않는 세션 식별자를 만들어 연결된 것처럼 기록하지 않는다.
- 비밀값·VNC 인증 데이터·원시 페이로드·사용자 입력 내용을 기록하지 않는다. 중계 ID와 상대 주소의 노출 수준을 정한다.
- 운영 로그는 JSON Lines다. 한 줄에 사건 하나를 쓰고, 줄마다 JSON 객체 하나를 쓴다. VNC Relay는 로그를 표준 출력 또는 지정한 파일로 출력한다. 로그 필드 이름은 [운영 정보 계약](../contracts/ops-info-v1.md)이 정한다.
- 로그 파일로 출력하는 중에 운영자가 그 파일의 이름을 바꾸거나 지우면(로그 회전), VNC Relay는 같은 경로를 다시 열어 그 경로의 파일에 이어 쓴다. 파일이 없으면 만든다(사용자 결정 2026-11-04(Q104)). 경로의 이름 변경·삭제·생성 알림을 받으면 곧바로 다시 열고, 알림을 놓친 경우를 위해 주기 확인 간격 Dp마다 항상 다시 연다. 경로의 파일이 그대로이면 같은 파일을 다시 여는 것이므로 결과가 같다(사용자 결정 2026-11-04(Q109)). 다시 열기에 실패하면 이전 파일에 계속 쓰고, 실패가 시작될 때 한 번 원인을 알리고, 다음 알림·주기에 다시 시도한다(사용자 결정 2026-11-04(Q110)).
- 로그 회전 시점·보관 기간·접근 권한은 운영자 책임이다. 수동 운영 안내에 로그 회전 방법과 로그 보관·접근 권장 사항을 적는다.
- 생존 확인은 프로세스가 응답할 수 있는 상태인지, 준비 확인은 필수 애플리케이션 리스너가 요청을 받을 수 있는 상태인지를 구분한다.
- 생존·준비 확인은 상태 리스너에서 제공한다. 상태 리스너는 관리 리스너가 아니다. 대시보드의 "로그인 화면만 인증 예외" 규칙은 관리 리스너에만 적용하며, 상태 리스너는 인증 없이 생존·준비 결과만 응답한다.
- 준비 전·애플리케이션이 맡은 필수 경계 실패·종료 유예 중에는 준비 완료를 반환하지 않는다. 상태 응답에 세션 목록·중계 ID·상대 주소·인증 비밀을 포함하지 않는다.
- WSS·관리 HTTPS의 인증서와 로그인 경계는 VNC Relay가 직접 준비한다. 평문 WS는 설정에서 명시적으로 켠 경우에만 열고 시작 경고를 기록한다. 관리 평문 HTTP는 루프백에서만 허용한다. 평문 HTTP·WS를 통한 공개 관리·중계 우회를 허용하지 않는다.

## 4. 보안과 신뢰 경계

| 경계 | 지켜야 할 동작 | 적용 조건 |
| --- | --- | --- |
| TCP Viewer·Server | 진입점마다 실제 출발지 IP 허용 목록 적용, 호환 초기 교환에 임의 인증 필드 추가 금지 | 양쪽 TCP 진입점, [중계와 매칭](relay.md)의 RLY-024 |
| Mode I 대상 | 최종 연결 IP·포트에 명시적 대상 허용 정책 적용 | 출발지 정책과 독립, RLY-007·RLY-008 |
| Mode II 매칭 | 중계 ID를 권한 증거로 취급하지 않음 | 모든 ID 매칭 |
| 대시보드·관리 API | 외부 접근은 내장 HTTPS·관리자 로그인 필수, 조회·종료는 유효한 관리 세션을 서버에서 검증 | 로컬에서도 로그인 생략 금지 |
| 관리 리스너 평문 HTTP | 루프백 바인딩에서만 허용, 비루프백 주소의 평문 설정은 시작 실패 | 루프백에서도 관리자 로그인 생략 금지 |
| 상태 리스너 | 기본 루프백인 별도 리스너, 인증 없이 생존·준비 결과만 응답, 세션·중계 ID·상대 주소·인증 비밀 미포함 | 관리 리스너가 아님, 로그인 예외 규칙 미적용 |
| WS·WSS | 진입점별 실제 출발지 IP 제한, 공개 접속에는 내장 WSS 권장(평문 WS 공개 여부는 운영자 책임, 사용자 결정 2026-11-04(Q96)) | 관리 세션으로 IP 제한 우회 금지 |
| 출발지 IP 허용 목록 표기 | 항목은 단일 IP·CIDR·범위(`a-b`)만 허용(IPv4·IPv6), 잘못된 표기·역순 범위·체계 혼합 범위는 설정 오류 | 시작이면 시작 실패, 재로드이면 후보 전체 거절, OPS-R24 |
| 평문 WS | 기본 비활성, 설정에서 명시적으로 켠 경우에만 열림, 시작 시 경고 기록 | 보호된 네트워크 여부 판단은 운영자 책임 |
| TLS 협상 | WSS·관리 HTTPS는 TLS 1.2 미만 협상 거절. 허용 암호 스위트는 선택한 rustls 암호 모듈의 rustls 기본 목록이며 운영자가 바꿀 수 없음 | 클라이언트는 TLS 1.2 이상 필요 |
| 클라이언트 주소 | 실제 소켓 상대 주소 사용, 전달 헤더 신뢰 금지 | 직접 접속 기준 |
| 관리 세션 쿠키·브라우저 Origin | 관리 상태 변경 CSRF 방어, 중계 Origin은 별도 WebSocket 정책 | 관리 세션과 중계 접근 분리 |
| 인증 비밀·로그 | 조회·오류·로그에 비밀과 원시 중계 데이터 노출 금지 | 모든 배치 |

출발지 허용 정책 누락을 공개 허용으로 대체하지 않는다. 켠 진입점의 목록이 없으면 시작 실패다. 명시적으로 빈 목록을 설정하면 그 진입점의 모든 출발지를 거절한다. `0.0.0.0/0`, `::/0` 같은 전체 허용 항목을 명시적으로 쓰면 허용하고 시작·재로드 시 경고를 기록한다. 기본 허용은 금지한다. 목록 항목 표기는 단일 IP, CIDR, 범위(`a-b`)이며 IPv4·IPv6 모두 받는다. 범위의 시작이 끝보다 크거나, 두 주소의 체계가 다르거나, 표기가 잘못되면 설정 오류다. IP는 개별 사용자 인증이 아니며 같은 공인 IP를 공유하는 사용자를 구분하지 못한다.

성능 합격 기준은 사용자 결정 2026-11-04(Q98)로 정했다.

- 측정 환경: 개발 PC 한 대의 Windows 11 x64와 같은 PC의 WSL2 Ubuntu 24.04 LTS x64. 클라이언트와 서버는 같은 PC 안에서 루프백으로 접속한다. 하드웨어 사양은 측정 기록에 적는다.
- 부하: 전송 조합(TCP·WS·WSS)마다 활성 100세션. 세션마다 양방향으로 각 1 Mbit/s를 10분 동안 보낸다.
- 합격 수치: 데이터 유실·혼입 0건, VNC Relay를 거쳐 늘어난 지연의 p99 10 ms 이하, 서버 프로세스 CPU 평균 1코어 이하, RSS 256 MiB 이하, 측정 구간 시작 뒤 RSS 증가 10% 이하.

측정 방법은 작업 5.4의 측정 기록에 적는다. 측정 환경은 위 Q98의 환경과 같다. 전송 조합(TCP·WS·WSS)마다 따로 판정한다. 허용 오버헤드·잔여 자원 판정 구간(OPS-017)과 느린 수신자 부하(AC-08)는 다음과 같이 정했다.

- 허용 오버헤드: 부하 중 서버 RSS에서 유휴 기준 RSS를 뺀 값이 `열린 중계 연결 수 × (B + 64 KiB)` 이하여야 한다. 64 KiB는 소켓·TLS·작업 상태의 연결당 여유다(사용자 결정 2026-11-06(Q118)).
- 잔여 자원: Mode II 접속·종료 수명 1,000회를 한 라운드로 하여 15라운드를 반복한다. 각 라운드 뒤 대기 연결과 활성 세션이 0이 된 것을 확인하고 5초 기다린다(사용자 결정 2026-11-06(Q119), 라운드 수는 사용자 결정 2026-11-06(Q123)).
  - 소켓·핸들 수: 2~15라운드 뒤 값이 1라운드 뒤 값과 같아야 한다. 1라운드는 OS의 재사용 자원 예열로 본다. Windows에서 핸들 수가 첫 라운드 뒤 32개 늘고 그 뒤 평평한 것을 관찰했다(사용자 결정 2026-11-06(Q122)). Windows에서는 Event 핸들을 따로 센다. Event가 아닌 핸들 수는 1라운드 값과 같아야 한다. Event 핸들 수는 1라운드 값에 작업자 스레드 수(제품 런타임 기본값인 논리 코어 수)의 2배를 더한 값 이하여야 한다. Linux의 fd 수는 1라운드 값과 같아야 한다(사용자 결정 2026-11-07(Q148)). 근거: Winsock은 스레드가 특정 소켓 호출을 처음 할 때 그 스레드의 Event를 만들어 유지한다(`mswsock!MSAFD_SockThreadInitialize`, `ws2_32!closesocket`의 `DoWaitForReaders`). 예열 뒤에도 일부 작업자 스레드는 이 호출을 하지 않았다. 그래서 Windows TCP에서 나중 라운드에 Event가 1개 늘고 그 뒤 6만 수명 동안 늘지 않았다(2026-11-07 진단, 사용자 결정 2026-11-07(Q147)). 2배는 관찰한 호출 경로 두 가지에서 정했다. 두 경로가 스레드마다 Event를 하나씩만 유지한다는 것은 추정이다.
  - RSS: 11~15라운드 RSS의 최댓값이 1~10라운드 RSS의 최댓값보다 2 MiB 넘게 커서는 안 된다(사용자 결정 2026-11-06(Q127)). 라운드 수와 10라운드 경계는 Q123을 따른다. 처음에는 `15라운드 − 10라운드 ≤ 2 MiB`였다(사용자 결정 2026-11-06(Q123)). Windows에서는 1 MiB 이상인 개인 커밋 영역 7~10 MB가 몇 초 간격으로 생겼다 사라졌고, 라운드 RSS가 약 8 MB 차이의 두 수준을 오갔다. 이 영역을 힙이 소유한다는 것은 추정이다. 그래서 두 라운드 값의 차이는 −8.6~+8.3 MB 사이로 흔들렸다. 최고점 비교는 같은 데이터의 Windows 15건에서 +0.0~+0.4 MB였다. 위 수준이 11라운드 이후에 처음 나타나면 누수가 없어도 실패할 수 있다. 관찰한 가장 늦은 첫 출현은 10라운드였다.
  - 수명 반복은 느린 수신자 부하(AC-08)를 실행한 서버가 아니라 새로 시작한 서버에서 실행한다. 느린 부하에서 해제된 큰 버퍼 영역이 RSS를 흔들기 때문이다. 느린 부하의 메모리는 허용 오버헤드 기준이 판정한다(사용자 결정 2026-11-06(Q124)).
  - 새 서버에서는 1라운드 전에 예열한다. 느린 부하와 같은 100세션을 열고 양방향 각 1 Mbit/s로 10초 동안 보낸 뒤 닫는다. Windows에서 늘어난 핸들은 Thread 핸들과 Event 핸들뿐이었다. 관찰 PC에서는 최대 16쌍(논리 코어 수)이었고, 그동안 프로세스의 스레드 수는 늘지 않았다. 작업자 스레드마다 처음 소켓 작업을 할 때 생기는 자원이라는 것은 추정이다. 동시 50수명 라운드는 이 상한에 몇 라운드에 걸쳐 도달하므로, 예열 없이는 1라운드 기준이 낮게 잡힌다(사용자 결정 2026-11-06(Q125)). 수명 100개를 한 번에 실행하는 예열로는 WS·WSS가 5~7라운드에야 상한에 도달했다. 그래서 트래픽 10초를 더했다(이 문서의 판단, 사용자 결정 없음).
  - Linux에서는 수명 반복 서버만 `MALLOC_ARENA_MAX=1`로 실행해 할당기 영향을 뺀다. 이 설정은 측정 전용이며 제품 배포 설정이 아니다. 근거: 기본 glibc 할당기에서는 수명 반복 RSS가 15라운드 동안 계속 늘었다(WSS 41.3→67.8 MB). 같은 측정을 `MALLOC_ARENA_MAX=1`로 실행하면 라운드 10→15 증가가 0~1.4 MB였다. 다중 arena 단편화로 판단한다(사용자 결정 2026-11-06(Q126), 작업 5.4 진단). Q126에서 함께 정한 Windows 표본 10개 최솟값 규칙은 개인 커밋 메모리의 두 수준을 없애지 못해 Q127로 대체했다.
- 느린 수신자(AC-08): 100세션 가운데 50세션은 수신을 멈춰 중계 버퍼를 B까지 채운 상태로 60초 둔다. 나머지 50세션은 양방향 각 1 Mbit/s를 계속 보낸다. 메모리는 위 허용 오버헤드 안이어야 한다. 정상 50세션은 데이터 유실·혼입이 0건이고 전송을 계속해야 한다(사용자 결정 2026-11-06(Q120)).
  - 중계 소켓의 커널 송수신 버퍼는 OS 자동 조정을 그대로 쓴다. 허용 오버헤드는 프로세스 RSS만 재며 커널 소켓 메모리를 포함하지 않는다. 루프백 측정에서는 시험 클라이언트 소켓이 같은 커널 메모리를 쓰므로, 시험 클라이언트의 송수신 버퍼를 64 KiB로 둔다. 실제 배치에서 클라이언트는 다른 호스트에 있다(사용자 결정 2026-11-06(Q121)).
  - 운영 위험: 막힌 중계 연결 하나가 커널 메모리를 최대 `tcp_rmem`·`tcp_wmem` 최댓값만큼 붙잡을 수 있다. WSL2 Ubuntu(`tcp_mem` 압박 시작 253,863페이지)에서 느린 흐름 100개의 중계 소켓만으로 최대 233,317페이지(약 911 MB)를 관찰했다. 시험 클라이언트 버퍼를 줄이지 않으면 상한을 넘어 패킷 폐기와 재전송 백오프로 흐름이 60초 넘게 멈췄다(작업 5.4 진단, 2026-11-06).

법률 검토가 필요한 행위의 허용 여부나 엄격한 클린룸 인증 완료를 이 스펙으로 보증하지 않는다.

## 7. 수용 테스트
