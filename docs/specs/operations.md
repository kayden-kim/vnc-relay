## 1. 범위와 적용 상태

- 지원 범위는 TCP·WS·WSS, Mode I·II, Windows 11 x64·Ubuntu 24.04 LTS x64 지원 목표(Windows Server 제외), VNC Relay 내장 TLS(TLS 1.2 이상), 공개 관리 HTTPS·내장 로그인·관리자 종료, 진입점별 출발지 IP 허용 목록, 중계 진입점 공통의 출발지 IP 차단 목록, 활성 100세션 목표, 최신 안정판 고정 검증과 MIT다.
- 로컬 CLI로 관리자 계정을 준비한다. 모든 계정은 단일 관리자 역할이며 여러 계정을 둘 수 있다. 준비된 계정이 없으면 시작에 실패한다. Windows 11 x64·Ubuntu 24.04 LTS x64 실행파일과 설정 예시를 배포한다. 인증서·출발지 IP 허용 목록을 자동 감지해 재로드하며 IP 허용 정책은 새 접속에 적용한다. 차단 목록은 새 접속에 더해 열린 활성 세션·대기 연결에도 적용한다(3.10절). 재로드 대상은 접속 ticket 키 10개와 차단 목록 키 1개를 포함한 44개다. 관리 API·대시보드 편집은 같은 설정 파일에 저장하며 기본은 꺼짐이다.
- VNC Relay 실행과 관리자 계정 준비는 실행파일 하나의 서로 다른 하위 명령이다. 설정 파일은 TOML이다. 출발지 IP 허용·차단 목록 항목은 단일 IP, CIDR, 범위(`a-b`)이며 IPv4·IPv6 모두 받는다. 관리자 비밀번호 해시는 Argon2id다. 운영 로그는 JSON Lines다. 파일 변경은 OS 파일 알림으로 감지하고 주기 확인으로 보조한다. 구현의 비동기 런타임은 tokio, TLS는 rustls다. Windows 11에서는 같은 실행파일의 `service` 하위 명령으로 Windows 서비스를 설치·해제하고 서비스로 실행한다. 서비스 상태 확인과 시작·중지는 별도 실행파일인 트레이 앱도 맡는다.
- 평문 WS는 기본 비활성이다. `[relay.ws.viewer]` 또는 `[relay.ws.server]` 역할을 명시적으로 켜면 공유 `ws` 리스너를 연다. WS·WSS는 경로로 역할을 고른다. 중계 WS·WSS 리스너는 내장 WSS 또는 역방향 프록시 TLS 종료를 지원한다. 관리 리스너는 이 프록시 지원의 대상이 아니다. 관리 평문 HTTP는 루프백 바인딩에서만 허용한다. 상태 엔드포인트는 기본 루프백의 별도 리스너에서 제공한다. 재로드 대상이 아닌 값이 다르면 후보 전체를 거절한다.
- 단일 인스턴스로 운영하고 TCP keepalive·WebSocket ping으로 끊긴 연결을 감지한다. 프로세스 사이에 대기·세션·카운터 상태를 공유하지 않는다. 이미 사용 중인 리스너 주소로 두 번째 프로세스를 시작하면 시작 실패다. 상대가 살아 있는 유휴 연결은 끊지 않는다.
- 검증 대상 OS는 Windows 11 x64와 Ubuntu 24.04 LTS x64다. Windows Server는 검증 대상이 아니다. 실제 실행 증거가 없으면 지원 완료로 표시하지 않는다.
- VNC Relay는 로그를 표준 출력 또는 지정한 파일로 출력한다. 별도로 최근 운영 사건 N개를 메모리에 보관해 대시보드 로그 화면에서 조회한다. 로그 파일 교체·보관 기간·접근 권한은 운영자 책임이며, 수동 운영 안내에 권장 사항을 적는다.
- 메트릭은 OpenTelemetry 의미 규칙의 이름을 쓰며, 상태 리스너의 `/metrics`에서 Prometheus 텍스트로 낸다. 기본은 꺼짐이다. 관리 API와 대시보드는 설정과 관계없이 같은 값과 최근 1시간·최근 24시간 추이를 로그인한 관리자에게 보여 준다(3.8절). OTLP 내보내기와 장기 보관은 제공하지 않는다.
- 접속 출처 통계는 중계 리스너의 연결 사건을 클라이언트 주소마다 세어 최근 사건 100,000개를 메모리에 보관한다. 국가·ASN은 운영자가 내려받아 둔 IP 정보 DB 파일에서 찾는다(3.9절). VNC Relay는 IP 정보를 찾으려고 외부에 요청하지 않으며, DB 파일을 배포 묶음에 넣거나 내려받지 않는다.
- 하위 명령 이름·파일 확장자·환경 변수 이름·설정 키 이름과 기본 포트는 [설정 계약](../contracts/config-v4.md)과 [CLI 계약](../contracts/cli-v1.md)이 정한다. Rust 라이브러리는 [PRD 1절 "구현 기술" 행](../requirements/PRD.md#확정-기준)이 단일 기준이다.
- 이 문서의 범위는 시작 검증, 제한, 종료, 운영 정보, 접근 경계, 성능·호환성·출처의 수용 판정이다. 설치·빌드 절차는 [개발 환경·검증 how-to](../how-to/set-up-and-verify.md)에서 관리한다.
- 신규 중계 프로토콜·세션 영속화·자동 재접속·전체 설정 재로드·Ubuntu의 OS 서비스 등록·컨테이너 배포는 제공하지 않는다. Windows 11의 서비스 실행은 3.7절을 따른다. 설정 보기와 38개 대상 키의 관리 API·대시보드 편집을 제공한다. 수동 재로드 API·CLI는 제공하지 않는다.

| U | 내장 TLS 협상·HTTP 업그레이드 제한 시간 | VNC Relay가 적용, 준비 전 접속도 제한. WS·WSS는 수락부터 TLS 핸드셰이크(WSS)와 업그레이드 요청까지, 관리 리스너는 수락부터 TLS 핸드셰이크와 첫 요청 머리 읽기까지 잰다. 관리 리스너는 첫 요청 머리 뒤 U를 읽기·쓰기 사이의 유휴 제한으로만 쓴다. 요청 전체·본문 전체의 절대 제한 시간은 두지 않는다 |

| G | 정상 종료 시 활성 세션 유예 시간 | 만료 후 남은 세션 강제 정리. 유예 중 두 번째 종료 요청이면 만료 전에도 정리. OPS-R26, OPS-042 |
| D | 마지막 변경을 감지한 뒤 재로드 결과 확인 제한 시간 | 자동 감지·연속 변경의 수용 판정에 사용. 감지 뒤 안정화 대기·검증·교체를 포함한다. 수치는 설정 계약에서 정함 |
| Dp | 파일 변경 주기 확인 간격 | OS 파일 알림을 놓친 변경도 Dp 안에 감지. 수치는 설정 계약에서 정함. OPS-R25, OPS-041 |
| R | 최근 종료 목록 최대 항목 수 | 메모리에만 보관, 초과 시 가장 오래된 항목부터 제거, 재시작 후 비어 있음. [관리 기능](management.md)의 MGT-024 |
| F | 관리자 로그인 실패 기준 | 계정별·출발지 IP별 실패 횟수와 제한 시간. 넘으면 로그인을 지연·거절하며 계정 존재 여부를 드러내지 않음. [관리 기능](management.md)의 MGT-022 |
| Si | 관리 세션 유휴 만료 시간 | 사용자 행동 요청만 연장하며 대시보드 자동 폴링은 연장하지 않음. [관리 기능](management.md)의 MGT-025 |
| Sa | 관리 세션 절대 최대 수명 | 활동과 관계없이 지나면 무효화. [관리 기능](management.md)의 MGT-025 |
| K | TCP keepalive 감지 시간 | 유휴 시작·탐색 간격·횟수로 정함. 중계 측 TCP 소켓 전체(뷰어·서버·Mode I 대상, WS·WSS 하부 TCP 포함)에 적용. 응답 없는 상대의 대기·활성 연결을 K 안에 끊긴 연결로 판정하고, 응답하는 유휴 연결은 끊지 않음. [중계와 매칭](relay.md)의 RLY-025~027 |
| Kw | WebSocket ping 주기와 pong 응답 제한 시간 | WS·WSS 연결에 적용. 제한 안에 pong이 없으면 끊긴 연결로 처리, pong에 응답하는 유휴 연결은 유지. [WS·WSS](websocket.md)의 WS-026 |
| P | 대시보드 폴링 주기 | 설정 가능, 기본값 2초. 유효 범위는 설정 계약에서 정함. [화면](dashboard.md)의 DASH-022 |

L·Lm·Lw·B·M·H·U·W·C·E·G·K·Kw는 재로드 대상이다. 새 값의 적용 시점은 3.3절과 [설정 계약 1.8절](../contracts/config-v4.md#18-재로드-구분)을 따른다. F·Si·Sa·P·R, `recent_logs.max_entries`, `metrics.enabled`, `ip_info.country_db`·`ip_info.asn_db`와 `dashboard.query_timeout_secs`는 재시작이 필요하다. 세션 정보 응답의 `dashboard.terminate_timeout_secs`는 응답 때의 E + 5초다.

Mode I의 뷰어 연결과 생성한 대상 연결은 L에서 각각 한 개다. Mode II의 뷰어·서버 연결도 각각 한 개다. 관리·상태 연결은 L이 아니라 Lm에서 센다. 수신·송신 소켓을 구분해 상한을 우회해서는 안 되며, 대상 연결 생성 전에도 예산을 확보한다. 리스닝 소켓 자체는 연결 수에 세지 않지만 기본 자원 측정에 포함한다.

활성 100세션에는 중계 연결 소켓만 최소 200개가 필요하다. 초기 교환·대기·연결 중 작업에 필요한 여유는 L에, 관리 HTTPS·상태 리스너에 필요한 여유는 Lm에 반영한다. 100은 검증 규모 목표이지 모든 연결의 상한 값이나 지원 완료 증거가 아니다.

## 3. 정상 흐름과 수명 규칙

### 3.1 설정 검증과 시작

1. TOML 설정 파일과 로컬 CLI로 준비한 관리자 정보를 읽어 유효 설정을 만든다. 키 이름·구조·입력 방식은 [설정 계약](../contracts/config-v4.md)이 정한다.
2. 리스닝 주소·포트, 활성 모드, 진입점별 출발지 IP 허용 목록, 출발지 IP 차단 목록, Mode I 대상 허용 정책, 한도·시간, 관리자 자격 증명과 내장 TLS 인증서 설정을 검증한다. 차단 목록은 허용 목록과 같은 항목 문법을 검사하고 신뢰 프록시 항목과의 겹침도 검사한다(3.10절). 접속 ticket 표의 형식·범위도 검사한다. `enabled = true`인 표는 필수 키와 공개 키 파일을 검사한다. 두 역할을 모두 켜면 같은 공개 키가 있는지도 검사한다([설정 계약 1.11절](../contracts/config-v4.md#111-접속-ticket-공개-키-파일-형식)).
3. 잘못된 값·누락된 필수 보안 경계는 시작 실패로 보고한다. 보안 검사를 묵시적으로 끄거나 임의의 공개 주소로 대체하지 않는다. ticket 설정·공개 키 파일 오류도 리스너 바인드 전에 종료 코드 3으로 끝낸다. 공개 키 파일 오류 코드는 `ticket_keys_invalid`다.
4. 켠 진입점마다 출발지 IP 허용 목록을 확인한다. 목록이 없으면 시작 실패다. 명시적으로 빈 목록이면 그 진입점의 모든 클라이언트 주소를 거절한다. 목록 항목은 단일 IP, CIDR, 범위(`a-b`)만 받으며 IPv4·IPv6 모두 해당한다. 범위의 시작이 끝보다 크거나, 두 주소의 체계(IPv4·IPv6)가 다르거나, 표기가 잘못된 항목은 설정 오류이며 시작 실패다. `0.0.0.0/0`, `::/0` 같은 전체 허용 항목은 허용하고 시작 경고를 기록한다. 꺼진 역할·리스너도 형식·범위 검사는 하며 필수 키 검사만 생략한다. WSS 역할을 하나라도 켜면 해당 리스너의 `listen`·인증서·개인키가 필요하다.
5. 준비된 관리자 계정이 하나도 없으면 시작 실패다. 종료 코드는 [CLI 계약 2.1절](../contracts/cli-v1.md#21-종료-코드)의 계정 파일 오류다.
6. `[relay.ws.*]` 역할 중 하나라도 켜면 평문 WS 리스너를 연다. 둘 다 끄면 열지 않는다. 켜면 `plaintext_ws_enabled(listener=ws)` 시작 경고를 기록한다. 보호된 네트워크인지 판단하는 것은 운영자 책임이다. 공개 접속에는 내장 WSS 또는 역방향 프록시 TLS 종료를 권장한다. 프록시에서 VNC Relay까지의 구간은 운영자가 보호해야 한다.
7. WSS·관리 HTTPS는 TLS 1.2 미만 협상을 거절한다. 허용 암호 스위트는 선택한 rustls 암호 모듈(crypto provider)이 제공하는 rustls 기본 목록이다. 설정 키가 없으므로 운영자가 바꿀 수 없다. 스위트 이름은 모듈에 따라 다르므로 이 문서에 나열하지 않는다. 암호 모듈은 aws-lc-rs다.
8. 채택한 필수 리스너를 준비한다. 상태 리스너는 기본 루프백의 별도 리스너로 준비한다. 일부 필수 리스너 준비에 실패하면 시작 중 확보한 자원을 회수한다. 부분 준비 상태를 정상 준비 완료로 표시하지 않는다.
9. 관리 바인딩은 기본 루프백으로 둘 수 있으며 설정한 주소로 외부 HTTPS 접근을 지원한다. 내장 TLS와 관리자 로그인 준비 없이 공개 관리 요청을 수락하지 않는다. 기본 관리자 비밀번호를 묵시적으로 제공하지 않는다.
10. 관리 평문 HTTP는 루프백 바인딩에서만 허용한다. 비루프백 주소에 평문 HTTP를 설정하면 시작 실패다. 평문 루프백에서도 관리자 로그인을 생략하지 않는다. 쿠키 보안 속성은 [관리 기능](management.md)의 3.0절이 정한다.
11. 설정 파일과 참조한 인증서·개인키 파일, `enabled = true`인 ticket 표의 `public_keys_file`, `[ip_info]`가 가리키는 IP 정보 DB 파일의 변경 감지(OS 파일 알림과 주기 확인)를 준비한 뒤 접속을 받는다. 변경 감지 준비가 불가능하면 이를 묵시적으로 끄고 시작하지 않는다.
    로그 디렉터리 알림 등록만 실패한 경우는 시작 실패에 해당하지 않는다. `reload_watch_failed`(`notify_error`)를 쓰고 시작을 계속하며 Dp마다 로그 파일 다시 열기와 알림 등록을 시도한다.
    IP 정보 DB 파일 디렉터리의 알림 등록 실패도 시작 실패가 아니다. DB 파일은 없어도 되므로 경고 없이 주기 확인으로 감지하고 Dp마다 등록을 다시 시도한다([설정 계약 1.12절](../contracts/config-v4.md#112-ip-정보-db-파일-형식)).
12. `[ip_info]`에 경로가 있으면 변경 감지를 준비한 뒤, 준비됨 전에 IP 정보 DB 파일을 읽는다(3.9절). 읽지 못해도 시작 실패가 아니다. 키마다 경고 `ip_db_unavailable`을 기록하고 그 정보 없이 시작한다. 감시를 먼저 준비하므로 읽는 사이에 바뀐 파일도 변경 감지로 다시 읽는다.

단일 인스턴스로 운영한다. 프로세스 사이에 대기·세션·카운터 상태를 공유하지 않는다. 이미 사용 중인 리스너 주소로 두 번째 프로세스를 시작하면 시작 실패다. 두 번째 프로세스의 시작 실패는 첫 번째 프로세스의 대기·활성 세션에 영향을 주어서는 안 된다.

### 3.2 로컬 CLI 계정 준비

1. 운영자는 VNC Relay 시작 전에, VNC Relay를 실행하는 같은 실행파일(Windows 11 x64·Ubuntu 24.04 LTS x64 배포)의 계정 준비 하위 명령을 실행한다. VNC Relay 실행과 계정 준비는 서로 다른 하위 명령이다. 공개 웹 계정 생성·기본 비밀번호는 제공하지 않는다.
2. 여러 관리자 계정을 준비할 수 있다. 모든 계정은 같은 단일 관리자 역할을 가진다. 조회·세션 종료·동적 설정 변경 권한을 계정별로 나누지 않는다.
3. 계정명과 비밀번호를 입력한다. 비밀번호는 터미널에 표시하지 않으며 명령행 인수·URL로 받지 않는다.
4. 솔트를 포함한 Argon2id 비밀번호 해시만 저장한다. 평문 비밀번호·해시를 일반 출력이나 로그에 기록하지 않는다. 저장 파일은 허용되지 않은 일반 OS 계정이 읽거나 수정할 수 없도록 보호한다.
5. 입력 취소·검증·저장 실패 시 이전의 유효한 자격 증명을 손상하지 않는다. 준비 완료는 필요한 저장이 성공한 뒤에만 알린다.
6. 실행 중인 VNC Relay의 계정 변경·세션 변경을 위한 네트워크 API는 추가하지 않는다. 기존 계정 정보를 바꿀 때는 VNC Relay를 정상 종료하고 로컬 CLI로 준비한 뒤 다시 시작한다.

하위 명령 이름·옵션·파일 위치는 [CLI 계약](../contracts/cli-v1.md)이, Argon2id 매개변수는 [설정 계약](../contracts/config-v4.md)이 정한다. `vnc-relay admin add|passwd|remove|list`로 관리자 계정을 준비한다.

### 3.3 파일 변경 자동 감지와 부분 재로드

재로드 대상은 ticket 키 10개와 차단 목록 키 1개를 포함한 44개다. 이 중 인증서·개인키 경로 4개와 ticket 공개 키 파일 경로 2개를 뺀 38개가 관리 API 편집 대상이다. 정확한 키 목록·편집 조건은 [설정 계약 1.8절](../contracts/config-v4.md#18-재로드-구분)을 따른다. 아래 표의 "교체 뒤"는 후보 검증과 유효 설정 교체가 끝난 뒤다. 이미 맺은 연결·이미 시작한 타이머·이미 설정한 소켓 옵션은 이전 값을 유지한다. 차단 목록만 예외이며, 열린 대기·활성 연결을 끊는다(3.10절).

| 설정 | 적용 방식 | 기존 연결·상태 |
| --- | --- | --- |
| TLS 인증서·개인키 | 파일 변경을 자동 감지·검증한 뒤 새 TLS 핸드셰이크부터 적용 | 기존 TLS 연결 유지, 운영자 제공 인증서 교체이며 자동 발급 기능은 아님 |
| TCP 뷰어 출발지 IP 허용 목록 | 유효한 설정 변경 뒤 새 TCP 접속부터, 수락 직후 판정 시점에 적용 | 이미 허용된 초기 교환·대기·활성 연결 유지, 대기 연결의 매칭 자격도 유지 |
| TCP 서버 출발지 IP 허용 목록 | 유효한 설정 변경 뒤 새 TCP 접속부터, 수락 직후 판정 시점에 적용 | 이미 허용된 초기 교환·대기·활성 연결 유지, 대기 연결의 매칭 자격도 유지 |
| WS·WSS 역할별 출발지 IP 허용 목록 | 교체 뒤 새 수락의 활성 역할 목록 합집합 검사와 새 업그레이드의 역할별 클라이언트 주소 검사부터 | 이미 통과한 검사의 결과·기존 연결·대기 매칭 자격 유지 |
| WS·WSS `trusted_proxies` | 교체 뒤 다음 수락 시점 또는 업그레이드 시점의 검사부터 | 이미 통과한 검사의 결과 유지. 기존 연결을 끊거나 주소를 소급 변경하지 않음 |
| 출발지 IP 차단 목록(`relay.deny.sources`) | 교체 뒤 새 수락·새 업그레이드·새 등록의 차단 검사부터. 값이 이전과 다르면 교체 직후 열린 활성 세션·대기 연결도 검사(3.10절) | 차단된 주소의 열린 활성 세션·대기 연결은 끊음. 초기 교환 중인 연결은 등록 단계 검사에서 거절. 목록이 그대로이거나 줄기만 하면 끊을 대상 없음 |
| WS·WSS 역할별 `allowed_origins` | 교체 뒤 Origin 검사를 받는 새 업그레이드 요청부터 | 기존 연결 유지 |
| `relay.ticket.{viewer,server}.enabled` | 교체 뒤 새 업그레이드 요청부터 | 이미 101을 보낸 연결의 중계 ID 대조·`sx` 타이머와 사용 기록 유지 |

TCP 접속은 수락 직후, 데이터 읽기 전에 출발지 IP 허용 목록을 검사한다. WS·WSS는 수락 직후(TLS·HTTP 전)에 소켓 상대가 신뢰 프록시인지 또는 켜진 역할 허용 목록의 합집합에 있는지 검사한다. 업그레이드 때는 경로로 역할을 고른 뒤 클라이언트 주소를 해당 역할 목록으로 다시 검사한다. 신뢰 프록시의 전달 주소 판정과 순서는 [WebSocket 계약 1.8절](../contracts/websocket-relay-v2.md#18-신뢰-프록시와-x-forwarded-for)을 따른다. 각 판정과 재로드 적용은 이전 또는 새 정책 중 하나로 일관되게 처리한다. 업그레이드 전의 HTTP·TLS 연결은 아직 중계 접속이 아니다. 재검사에서 거절된 연결은 업그레이드하지 않는다. 관리 HTTPS·로그인 권한은 중계 IP 정책과 별개다.

차단 목록 검사는 모든 허용 검사보다 앞선다. 검사 위치와 순서는 3.10절을 따른다.

`trusted_proxies`에는 프록시 주소만 넣어야 한다. 클라이언트 범위를 넣어서는 안 된다. 신뢰 프록시의 `X-Forwarded-For`는 오른쪽부터 검사해 처음 만나는 비신뢰 주소를 클라이언트 주소로 쓴다. 그 왼쪽 요소는 검사하지 않는다. 헤더 누락·빈 값·검사 중 잘못된 요소·모든 요소가 신뢰 프록시인 체인은 `HTTP 400 forwarded_for_invalid`로 거절한다. 이때 등록과 `forwarded_ip`는 없다. 프록시 주소가 역할 허용 목록에 있어도 모두 신뢰하는 체인은 거절해야 한다([WS-032~036](websocket.md#7-수용-테스트)). 신뢰 프록시 호스트나 그 신뢰 범위 안에서 시작한 요청은 프록시를 거치면 거절된다. 같은 출발지에서 그 리스너에 직접 접속해도 신뢰 프록시 연결로 취급한다. 그래서 유효한 전달 헤더가 없으면 거절되고, 있으면 같은 전달 주소 판정과 역할 허용 목록 검사를 받는다. 전달 헤더 없이 직접 접속하려면 출발지가 그 리스너의 `trusted_proxies` 밖에 있고 해당 역할의 허용 목록에 들어야 한다.

1. 설정 파일과 켜진 중계 리스너·관리 리스너가 쓰는 인증서·개인키 파일의 변경·교체 저장을 OS 파일 알림으로 감지한다. 역할을 모두 끈 리스너의 TLS 파일은 감시하지 않는다. `enabled = true`인 ticket 표의 `public_keys_file`도 감시한다. 알림을 놓친 변경도 주기 확인(간격 Dp)으로 감지한다. 변경이 안정되면 설정·파일을 한 재로드 후보로 읽는다. `[ip_info]`가 가리키는 IP 정보 DB 파일도 같은 방법으로 감시하지만 재로드 후보에는 넣지 않는다. 그 파일은 3.9절에 따라 따로 다시 읽는다.
2. 시작과 같은 전체 설정 검증을 한다. 구문·모든 정책·한도·시간·값 관계·인증서/개인키 쌍·필수 보안 설정을 포함한다. ticket의 필수 키·범위·공개 키 파일과 역할 간 공개 키 분리도 검사한다. 공개 키 파일 형식은 [설정 계약 1.11절](../contracts/config-v4.md#111-접속-ticket-공개-키-파일-형식)을 따른다. 임시 저장·한쪽 인증서 파일만 교체·파일 일시 소멸은 유효한 새 구성으로 취급하지 않는다.
3. 재로드 후보는 실행 중 유효 설정과 비교한다. 재로드 대상이 아닌 값이 실행 중 값과 다르면 후보 전체를 재시작 필요로 거절한다. 그 차이가 설정 파일에 남아 있는 동안에는 이후 재로드 대상 변경(IP·인증서·관리 API 편집 포함)도 모두 거절한다. 급한 인증서 교체도 같다. 운영자는 그 값을 되돌리거나 재시작해야 한다. 일부 값만 조용히 적용하지 않으며, 거절된 후보를 적용된 설정으로 보고하지 않는다.
4. 유효한 후보의 재로드 대상 값을 원자적으로 한 번에 교체한다. 후보 검증 중에는 이전 유효 설정과 기존 중계를 유지한다. 실패하면 어느 값도 일부만 반영하지 않는다. 전체 출발지 허용 항목은 `allow_all_source`, 전체 대상 허용 항목은 `allow_all_target` 경고를 `phase = reload`로 기록한다. WS·WSS 역할 목록의 경고에는 `role`도 기록한다. 전체 주소 체계를 신뢰하는 `trusted_proxies` 항목은 `trust_all_proxies` 경고에 `listener`·`item`·`phase`를 기록한다.
   ticket을 켠 역할에 같은 역할의 TCP 진입점이 있으면 `ticket_tcp_bypass`를 기록한다. 그 역할이 평문 WS에서도 켜져 있으면 `ticket_plaintext_ws`를 기록한다. 두 경고의 조건·신뢰 경계는 4절을 따른다. 경고만으로 후보를 거절하지 않는다.
5. 검증 중 후속 파일 변경을 관찰하면 이전 후보를 적용하지 않는다. 늦게 끝난 이전 검증이 새 후보나 이전 유효 설정을 덮어써서는 안 된다. 마지막 변경을 감지한 뒤 D 안에, 안정된 최신 파일 상태에 대해 적용 또는 실패 결과를 확인할 수 있어야 한다.
6. 성공·실패·재시작 필요·변경 감지 장애를 비밀 없는 운영 사건으로 구분한다. `reload_applied.trigger`는 파일 감지이면 `file_watch`, 관리 API 편집이면 `config_edit`다. 실행 중 감지 장애는 이전 유효 설정을 유지하며 원인을 알린다. 적용하지 않았는데 성공으로 표시하지 않는다.
7. 정상 종료가 시작되면 파일 감지에 따른 새 후보 적용을 중지한다. 관리 API 편집은 다른 관리 요청처럼 종료 유예 중에도 처리한다. 어느 경로의 재로드도 종료를 취소하거나 새 중계 수락을 다시 시작해서는 안 된다.

관리 API 편집 경로는 `PATCH /api/v1/config`다. `management.config_edit = true`일 때 로그인한 모든 관리자가 같은 단일 역할로 편집할 수 있다. 처리 순서·오류는 [관리 API 계약](../contracts/management-api-v1.md), 파일 쓰기는 [설정 계약 1.10절](../contracts/config-v4.md#110-관리-api-편집의-파일-쓰기)을 따른다. 편집과 파일 감지 재로드는 직렬로 처리한다. 고칠 내용을 같은 로더로 검증하고, 주석·공백·순서를 보존한 파일을 원자적으로 쓴 뒤 같은 후보를 즉시 한 번 교체한다. 그 뒤의 파일 감지는 차이가 없으므로 다시 교체하거나 `reload_applied`를 기록하지 않는다. `reload_change_detected`는 기록될 수 있다. 쓰기 실패이면 파일과 실행 값은 이전 그대로다.

변경 없음은 편집 전후 파일 바이트로 판정한다. 바이트가 같으면 파일 쓰기·교체·실행 값 적용 없이 `applied = []`로 응답하며 두 성공 사건을 기록하지 않는다. 반영 전 파일 변경이 남아 있어도 이 요청은 적용하지 않고 파일 감지가 적용한다. 바이트가 달라 교체하면 반영 전 파일 변경을 포함한 후보 전체를 적용한다. 응답과 `reload_applied.applied`는 실제 실행 값이 바뀐 모든 키를 담는다. `config_edited.config_keys`는 요청 `changes` 가운데 파일 값이 바뀐 키만 담는다.

파일 교체는 공유 잠금 안에서 임시 파일 쓰기·flush를 마친 뒤 현재 파일을 다시 읽어 `revision`을 비교한다. 다르면 임시 파일을 지우고 `409 config_conflict`로 거절하며 이번 요청은 파일·실행 값을 바꾸지 않는다. 같으면 원자 교체 뒤 같은 후보를 적용한다. 마지막 재확인과 교체 사이의 아주 짧은 틈은 보장 범위가 아니다. 재확인 읽기 실패도 같은 충돌로 처리한다. 임시 파일을 지우고 교체·적용 없이 `config_edit_rejected.reason = config_conflict`를 기록한다.

시간 기준: 파일 알림을 놓친 변경은 Dp 안에 감지하고, 마지막 변경을 감지한 뒤 D 안에 적용 또는 실패 결과를 확인한다. 최대 지연은 Dp + D다. D·Dp는 [설정 계약](../contracts/config-v4.md)을 따른다. 파일 감지의 구체 방식과 Windows 디렉터리·편집기 핸들 한계는 [파일 변경 감지 모듈 설계](../architectures/file-watch.md)에 있다. 설정 보기·편집 API는 제공하되, 별도의 수동 재로드 API·CLI는 제공하지 않는다.

### 3.4 정상 종료와 재시작

1. 정상 종료 사건을 받으면 신규 중계 접속을 중지한다. 종료 중 도착한 접속을 새 세션으로 만들지 않는다.
2. 초기 교환·대기·대상 연결 중인 미완성 작업을 종료하고 등록을 해제한다.
3. 활성 세션에는 G의 유예를 부여한다. 그 전에 자발적으로 끝나면 즉시 정리한다. G가 0이면 유예 없이 바로 정리한다.
4. G 만료 시 남은 활성 세션을 강제 정리한다. 아직 정리를 시작하지 않은 세션에 프로세스 종료에 따른 원인 `server_shutdown`을 남긴다. 이미 정리를 시작한 세션은 최초 정리 시작 원인을 유지한다.
5. 자원 정리 후 프로세스를 종료한다. 재시작은 새 프로세스 수명이며 이전 소켓·중계 ID 매칭·카운터를 복원하지 않는다.

종료 유예 중에도 관리 조회·관리자 로그인·관리자 종료를 모두 처리한다. VNC Relay 상태는 관리 요약에 `shutdown_grace`로 표시한다([관리 API 계약 1.6절](../contracts/management-api-v1.md#16-vnc-relay-요약-get-apiv1summary)). 상태 리스너의 준비 확인은 이 상태에서 준비 아님이다([운영 정보 계약 1.12절](../contracts/ops-info-v2.md#112-상태-리스너와-엔드포인트)).

필수 리스너(상태·관리·설정으로 켠 TCP·WS·WSS)의 복구 불가능 수락 오류는 같은 종료 절차를 시작한다. WS·WSS는 역할을 하나 이상 켠 리스너가 해당한다. 일시 오류·자원 부족은 기존 100밀리초 뒤 재시도한다. 횟수 임계값·새 설정은 없다. 정확한 OS 분류는 [운영 정보 계약 1.12절](../contracts/ops-info-v2.md#112-상태-리스너와-엔드포인트)을 따른다. 장애 종료는 `shutdown_started(trigger=fatal_error)`를 `error`로 기록하고 정리 후 종료 코드 1로 끝난다. 살아 있는 상태 HTTP는 유예·정리 동안 `/readyz` 503 `listener_failed`와 `/livez` 200을 유지한다. 상태 소켓 자체 장애의 응답은 보장하지 않는다. 관찰을 위한 별도 대기는 없다. 정상 종료가 먼저 시작되면 뒤늦은 장애는 최초 원인·유예를 바꾸지 않는다.

유예 중 두 번째 종료 요청(Ctrl+C·SIGTERM 등)을 받으면 남은 유예를 건너뛰고 남은 세션과 등록을 즉시 강제 정리한다. 세션의 종료 원인은 아직 정리를 시작하지 않은 세션에만 `server_shutdown`을 기록하고, 이미 정리를 시작한 세션은 최초 정리 시작 원인을 유지한다. 정상 종료 요청에 따른 종료로 본다. 종료 코드는 [CLI 계약 1.8절](../contracts/cli-v1.md#18-수동-시작과-종료)이 정한다.

Windows에서 `serve`를 실행한 콘솔 창을 닫으면 종료 요청과 두 번째 종료 요청을 함께 받은 것으로 처리한다. 신규 중계 접속을 중지하고, G를 기다리지 않고 남은 세션과 등록을 즉시 강제 정리한다. 종료 원인 규칙은 두 번째 종료 요청과 같다. OS는 창을 닫은 뒤 기본 5초 안에 프로세스를 끝낸다([Microsoft HandlerRoutine 문서](https://learn.microsoft.com/en-us/windows/console/handlerroutine)의 Timeouts). 그러므로 정리와 종료 사건 기록은 그 안에 끝나야 한다. 정상 종료 요청에 따른 종료로 본다.

Windows 로그오프·시스템 종료의 신호는 서비스만 받는다. 대화형 콘솔 프로그램은 그 전에 OS가 끝낸다(같은 문서). 그러므로 터미널에서 실행한 `serve`에서는 로그오프·시스템 종료를 강제 종료로 보고 정상 유예와 종료 기록을 보장하지 않는다. Windows 서비스로 실행하면 시스템 종료 알림을 받으며 3.7절을 따른다.

Windows 11 x64·Ubuntu 24.04 LTS x64의 수동 실행·정상 종료 방식과 Windows 11의 서비스 실행(3.7절)을 검증한다. Windows Server는 검증하지 않는다. Ubuntu의 OS 서비스 등록 산출물과 컨테이너는 배포 범위에서 제외한다. 충돌·전원 장애에도 정상 유예를 보장하지 않는다.

### 3.5 운영 정보

- 접속 수락·거절, 대기 등록, 매칭, 대상 연결 실패, 종료와 자동 재로드 성공·실패·재시작 필요·감지 장애를 구분해 기록한다.
- 관리자 종료와 동적 설정 편집·거절 사건에는 수행한 관리자 계정명을 기록한다. 편집 사건에는 바뀐 키를 기록하고 설정 값은 기록하지 않는다. 사건·필드·순서는 [운영 정보 계약 1.5절](../contracts/ops-info-v2.md#15-사건-목록)을 따른다.
- 사건은 적용 가능한 세션 식별자·역할·모드·시각·원인으로 추적한다. 세션 생성 전 사건에는 존재하지 않는 세션 식별자를 만들어 연결된 것처럼 기록하지 않는다.
- 비밀값·VNC 인증 데이터·원시 페이로드·사용자 입력 내용을 기록하지 않는다. 중계 ID와 상대 주소의 노출 수준을 정한다.
- 운영 로그는 JSON Lines다. 한 줄에 사건 하나를 쓰고, 줄마다 JSON 객체 하나를 쓴다. VNC Relay는 로그를 표준 출력 또는 지정한 파일로 출력한다. 로그 필드 이름은 [운영 정보 계약](../contracts/ops-info-v2.md)이 정한다.
- 로그 파일로 출력하는 중에 운영자가 그 파일의 이름을 바꾸거나 지우면(로그 회전), VNC Relay는 같은 경로를 다시 열어 그 경로의 파일에 이어 쓴다. 파일이 없으면 만든다. 경로의 이름 변경·삭제·생성 알림을 받으면 곧바로 다시 열고, 알림을 놓친 경우를 위해 주기 확인 간격 Dp마다 항상 다시 연다. 경로의 파일이 그대로이면 같은 파일을 다시 여는 것이므로 결과가 같다. 다시 열기에 실패하면 이전 파일에 계속 쓰고, 실패가 시작될 때 한 번 원인을 알리고, 다음 알림·주기에 다시 시도한다.
- 로그 회전 시점·보관 기간·접근 권한은 운영자 책임이다. 수동 운영 안내에 로그 회전 방법과 로그 보관·접근 권장 사항을 적는다.
- 생존 확인은 프로세스가 응답할 수 있는 상태인지, 준비 확인은 필수 애플리케이션 리스너가 요청을 받을 수 있는 상태인지를 구분한다.
- 생존·준비 확인은 상태 리스너에서 제공한다. 상태 리스너는 관리 리스너가 아니다. 대시보드의 "로그인 화면만 인증 예외" 규칙은 관리 리스너에만 적용하며, 상태 리스너는 인증 없이 생존·준비 결과만 응답한다.
- 준비 전·애플리케이션이 맡은 필수 경계 실패·종료 유예 중에는 준비 완료를 반환하지 않는다. 상태 응답에 세션 목록·중계 ID·상대 주소·인증 비밀을 포함하지 않는다.
- 내장 WSS·관리 HTTPS의 인증서와 관리 로그인 경계는 VNC Relay가 직접 준비한다. 역방향 프록시 TLS 종료는 중계 WS·WSS에만 적용한다. 관리 리스너는 전달 헤더를 무시하며 쿠키·로그인 제한 규칙도 바꾸지 않는다. 평문 WS는 해당 리스너의 역할을 명시적으로 켤 때만 열고 시작 경고를 기록한다. 관리 평문 HTTP는 루프백에서만 허용한다.

### 3.6 최근 로그

VNC Relay는 최근 `recent_logs.max_entries`개의 운영 사건을 메모리에 기록 순서대로 보관한다. 각 항목에는 `seq`가 있고 내용은 운영 로그 한 줄의 JSON 객체와 같다. `log.output`이 표준 출력인지 파일인지, 출력 쓰기에 성공했는지와 관계없이 보관한다. 가득 차면 가장 오래된 항목부터 버린다.

기본값은 1000, 범위는 0~10000이다. `0`이면 보관하지 않는다. 재시작하면 목록은 비며, 보관 수 변경도 재시작이 필요하다. 메모리 상한은 보관 수 N × 최대 로그 줄 크기다. `detail` 512 B·`origin` 256 B 등 운영 정보 계약의 필드 절단 규칙으로 줄 크기를 제한해야 한다.

로그인한 관리자는 [최근 로그 API](../contracts/management-api-v1.md#115-최근-로그-get-apiv1logs)와 [로그 화면](dashboard.md#scr-006-로그)에서 조회한다. 화면은 수준·사건명 필터, 값 검색, P 주기의 일시정지 가능한 자동 갱신, 세션 상세에서 해당 세션으로 좁혀 열기, 현재 필터 결과의 JSON Lines 내려받기를 제공한다. 영속 보관이나 로그 회전을 대신하지 않는다.

### 3.7 Windows 서비스 실행

Windows 11에서는 VNC Relay를 Windows 서비스로 실행할 수 있다. 서비스 제어 관리자(SCM, Windows가 서비스를 등록·시작·중지하는 구성 요소)가 프로세스를 시작하고 멈춘다. Ubuntu에는 이 절을 적용하지 않는다. 서비스 이름은 `vnc-relay` 하나로 고정하고 한 PC에 서비스 하나만 둔다. 명령 형식·서비스 속성·오류 코드는 [CLI 계약 1.9절](../contracts/cli-v1.md#19-windows-서비스-실행)이 정한다. 상태 확인과 시작·중지는 [Windows 트레이 앱](windows-tray.md)으로도 할 수 있다.

1. 운영자는 관리자 권한 터미널에서 `vnc-relay service install --config <path>`를 실행한다. 관리자 권한 없이 서비스를 시작·중지할 사용자나 그룹은 `--operator`로 지정한다. 이 옵션은 여러 번 쓸 수 있다.
2. 설치는 서비스를 등록하기 전에 설정을 검사한다. 검사 범위는 `serve` 시작 순서 중 리스너 바인드 전까지의 파일 검사(설정·계정 파일·인증서·개인키·접속 ticket 공개 키 파일)이며 오류 코드도 같다. 로그 파일 열기·변경 감지 준비·리스너 바인드는 하지 않는다. `log.output`이 `stdout`이면 설정 오류다. 검사에 실패하면 아무것도 등록하지 않는다.
3. 검사를 통과하면 서비스를 등록한다. 실행 계정은 가상 계정 `NT SERVICE\vnc-relay`다. 시작 유형은 자동(지연 시작)이다. 실패 뒤 다시 시작하는 복구 동작은 설정하지 않는다. 서비스 운영자에게 시작·중지 권한을 준다. 등록 뒤 단계가 실패하면 만든 등록을 지운다. 설치는 서비스를 시작하지 않는다.
4. SCM이 서비스를 시작하면 `serve`와 같은 시작 순서([CLI 계약 1.8절](../contracts/cli-v1.md#18-수동-시작과-종료))를 따른다. 준비됨에 들어간 뒤에만 실행 중으로 보고한다. 시작에 실패하면 실행 중으로 보고하지 않고, CLI 종료 코드를 서비스 종료 코드로 남긴다.
5. 중지 요청(트레이 앱·`sc.exe stop`·Windows 서비스 관리 도구)은 정상 종료 요청이다. 3.4절처럼 G를 적용한다. 중지 중에는 시스템 종료 제어만 받는다. 두 번째 중지 요청은 SCM이 오류 1061(`ERROR_SERVICE_CANNOT_ACCEPT_CTRL`)로 거절하므로 서비스에 전달되지 않는다. 따라서 서비스 중지에는 3.4절의 "두 번째 종료 요청"이 없다. 시스템 종료 알림이 없으면 유예는 활성 세션 종료나 G 경과로 끝난다. 관리자 종료나 리스너 장애로 VNC Relay가 스스로 종료를 시작해도 3.4절의 절차를 따르고, 프로세스가 끝나면 서비스는 중지됨이 된다.
6. Windows 시스템 종료·재시작 알림은 콘솔 창 닫기와 같이 처리한다. G 없이 남은 세션을 즉시 강제 정리하고, OS가 프로세스를 끝내기 전에 종료 기록을 마친다. 사건 순서는 [운영 정보 계약 1.5절](../contracts/ops-info-v2.md#15-사건-목록)의 순서 규칙을 따른다. 사용자 로그오프는 서비스를 멈추지 않는다. 서비스 실행은 콘솔 종료 신호를 종료 요청으로 쓰지 않고, SCM의 중지·시스템 종료 제어로만 종료 요청을 받는다.
7. 해제는 관리자 권한 터미널의 `vnc-relay service uninstall`이다. 중지된 서비스만 지운다. 설정·계정·인증서·로그 파일은 지우지 않는다.

Windows 11의 기본 서비스 보안 설명자(SDDL, 서비스 객체의 접근 권한을 적는 문자열)는 다음과 같다. 설치는 이 기본 권한을 유지하고 지정한 서비스 운영자의 권한만 더한다. 대화형 사용자(`IU`)는 상태·구성을 조회할 수 있지만 시작·중지는 할 수 없다. 서비스 운영자에게는 시작·중지·상태 조회·구성 조회 권한을 더한다.

```text
D:(A;;CCLCSWRPWPDTLOCRRC;;;SY)(A;;CCDCLCSWRPWPDTLOCRSDRCWDWO;;;BA)(A;;CCLCSWLOCRRC;;;IU)(A;;CCLCSWLOCRRC;;;SU)S:(AU;FA;CCDCLCSWRPWPDTLOCRSDRCWDWO;;;WD)
```

서비스 계정의 파일 권한은 운영자가 정한다. `NT SERVICE\vnc-relay`는 설정 파일·계정 파일·인증서·개인키·`enabled = true`인 접속 ticket 공개 키 파일을 읽을 수 있어야 한다. 로그 파일의 디렉터리에는 쓸 수 있어야 한다. 관리 API 편집을 켜면 설정 파일 디렉터리에도 쓸 수 있어야 한다(3.3절, [PRD 7절](../requirements/PRD.md#7-보안-및-신뢰-경계)). 이 파일들은 `%ProgramData%\vnc-relay\` 아래에 두기를 권장한다. 설치는 운영자의 관리자 권한으로 파일을 검사한다. 그러므로 검사를 통과해도 서비스 계정이 파일을 읽을 수 있다는 뜻은 아니다. 설치는 파일 권한을 바꾸거나 검사하지 않는다.

트레이 앱의 대시보드 열기·로그 파일 위치 열기를 쓰려면 트레이 사용자도 설정 파일을 읽을 수 있어야 한다([Windows 트레이 앱 스펙](windows-tray.md) 3절). 이 권한도 운영자가 정한다. 관리자 권한으로 `%ProgramData%` 아래에 만들고 기본 ACL을 물려받은 디렉터리는 별도 권한 부여 없이 서비스 계정의 설정·계정 파일 읽기와 로그 파일 생성·쓰기를 허용한다. 비승격 사용자도 설정 파일을 읽을 수 있다. 따라서 기본 ACL에서는 모든 로컬 사용자가 계정 파일도 읽을 수 있다. 운영자는 [Windows 서비스 운영 안내](../how-to/operate-relay.md)에 따라 파일 ACL을 제한해야 한다.

서비스에는 콘솔이 없다. 로그 파일을 열기 전의 시작 실패(설정 오류 등)는 운영 로그에 남지 않고 서비스 종료 코드로만 보인다. 서비스 종료 코드는 `sc.exe query vnc-relay`의 `SERVICE_EXIT_CODE`와 트레이 앱의 상태 줄에서 볼 수 있다. 진단 문장이 필요하면 서비스가 중지된 상태에서 같은 설정으로 터미널에서 `vnc-relay serve --config <path>`를 실행해 stderr를 확인한다.

서비스 등록은 설치할 때의 실행파일 절대 경로를 쓴다. 실행파일을 새 버전으로 바꿀 때는 서비스를 중지하고 같은 경로의 파일을 바꾼 뒤 다시 시작한다. 실행파일 위치를 바꾸려면 해제한 뒤 다시 설치한다. 서비스가 실행 중일 때 같은 리스너 주소의 설정으로 터미널에서 `serve`를 시작하면 리스너 바인드 실패로 끝난다(OPS-R23).

### 3.8 메트릭

메트릭(metric)은 VNC Relay의 연결·세션·관리 활동과 프로세스 자원을 시간에 따라 바뀌는 수로 나타낸 값이다. 이름·종류·단위·속성과 두 표현 형식은 [메트릭 계약](../contracts/metrics-v1.md)이 정한다. 이 절은 언제 무엇을 응답하는지 정한다.

1. `[metrics] enabled = true`이면 상태 리스너가 `GET /metrics`에 메트릭 계약 1.6절의 Prometheus 텍스트로 응답한다. 인증은 없다. 운영자의 Prometheus나 OpenTelemetry Collector(Prometheus 수신기)가 이 주소를 주기적으로 읽는다.
2. `[metrics] enabled = false`(기본)이면 `/metrics`는 정의하지 않은 경로와 같은 404 `not_found`다. 그래도 값은 센다. 관리 API와 대시보드가 같은 값을 쓰기 때문이다.
3. `/metrics`도 상태 리스너의 다른 규칙을 따른다. 연결은 Lm에서 세고, U와 Lm 거절 규칙도 같다. 상태 리스너가 응답하는 동안에는 준비 전과 종료 유예 중에도 응답한다. 준비 여부는 `/readyz`로 판단한다.
4. 운영 로그 사건에서 세는 값은 사건을 운영 로그 기록부에 넘길 때 함께 센다. 로그 출력의 성공 여부와 관계없다. 그래서 같은 프로세스의 로그 사건 수와 같다. 관리·상태 리스너는 `connection_accepted`를 기록하지 않으므로 수락 수에는 중계 리스너만 있다.
5. 사건이 없는 값은 동작이 끝날 때 직접 기록한다. 초기 교환 시간, Mode I 대상 연결 시간, WebSocket ping 시간 초과가 여기에 속한다. 방향별 전송량은 상대 전송 계층에 쓰기에 성공할 때마다 더한다. 그래서 세션이 끝나기 전에도 늘어난다. 방향과 뜻은 관리 API의 방향별 바이트와 같다([관리 기능 2.1절](management.md#21-전송량의-의미)).
6. 현재 값은 응답을 만들 때 읽는다. 대기·활성 세션·진행 중 연결 수, L·Lm의 사용량과 상한, 유효한 관리 세션 수가 여기에 속한다. L·Lm을 재로드하면 다음 응답부터 새 상한이 나온다.
7. 프로세스 값도 응답을 만들 때 OS에서 읽는다. 가동 시간, CPU 시간, 메모리, 스레드 수, Linux의 파일 기술자 수, Windows의 핸들 수가 여기에 속한다. 읽지 못한 값은 0으로 대신하지 않고 그 계열의 표본을 뺀다. 다른 값은 그대로 응답한다.
8. 속성은 메트릭 계약 1.4절의 고정 값만 쓴다. 중계 ID·세션 식별자·주소·계정명·Origin·ticket 값·설정 값·파일 경로는 넣지 않는다.
9. 값은 메모리에만 둔다. 재시작하면 0부터 다시 센다. 재로드는 값을 지우지 않는다.
10. VNC Relay는 준비됨이 된 때부터 10초마다 일부 값을 추이로 기록하고 최근 360개(1시간)를 보관한다. 그 점 6개마다 하나, 곧 1분마다 같은 점을 최근 24시간 추이에도 기록하고 최근 1440개를 보관한다. 정상 종료 유예 중에도 기록한다. 추이는 관리 API와 대시보드만 쓰며 `/metrics`에는 나오지 않는다([메트릭 계약 1.8절](../contracts/metrics-v1.md#18-추이)).
11. `metrics.enabled`는 재시작이 필요하며 편집 대상이 아니다. 설정 보기에서는 값만 보여 준다.
12. 메트릭 기록 때문에 중계 경로가 6절의 성능 합격 수치를 어겨서는 안 된다. 데이터 전송마다 하는 기록은 잠금 없이 더한다.

### 3.9 접속 출처 통계

접속 출처 통계는 중계 리스너에 들어온 연결을 클라이언트 주소마다 센 값이다. 운영자는 접속이 어느 주소·국가·ASN(인터넷 경로를 운영하는 조직의 번호)에서 오는지, 어느 주소가 자주 거절되는지 본다. 조회 형식은 [관리 API 계약 1.17절](../contracts/management-api-v1.md#117-접속-출처-get-apiv1sources), 화면은 [SCR-008](dashboard.md#scr-008-접속-출처)을 따른다.

1. 운영 로그 사건을 기록부에 넘길 때 함께 센다. 로그 출력의 성공 여부와 관계없다. 중계 리스너(`tcp_viewer`·`tcp_server`·`ws`·`wss`)의 사건만 센다. 관리·상태 리스너의 사건은 세지 않는다.
2. 다음 사건을 센다. `target_connect_failed`, 대기 사건, `session_closed`는 세지 않는다.

   | 종류 | 세는 사건 |
   | --- | --- |
   | 연결 시도 | `connection_accepted`와 수락 단계(`stage = accept`)의 `connection_rejected` |
   | 거절 | 중계 리스너의 모든 `connection_rejected`(수락·TLS·업그레이드·초기 교환·등록·대상 단계) |
   | 중단 | `connection_aborted` |
   | 세션 참여 | `session_started`의 뷰어 쪽과 Mode II 서버 쪽 각각. Mode I 대상은 세지 않는다 |

3. 클라이언트 주소는 그 사건의 전달 주소(`forwarded_ip`·`viewer_forwarded_ip`·`server_forwarded_ip`)가 있으면 그 값, 없으면 소켓 상대 IP다. 업그레이드 검사에 쓴 주소와 같다([운영 정보 계약 1.10절](../contracts/ops-info-v2.md#110-상대-주소-표기)).
4. WS·WSS의 `connection_accepted`에는 전달 주소가 없다. 그래서 같은 `conn_id`의 다음 사건이 올 때 그 사건의 주소로 연결 시도를 센다. WSS의 TLS 단계 거절에도 `conn_id`가 있다. 사건 시각은 수락 시각이다. 다음 사건이 오기 전에는 그 연결 시도가 조회에 나오지 않는다. 다음 사건을 기다리는 연결이 65,536개를 넘으면 가장 오래된 것부터 소켓 상대 IP로 센다.
5. 사건마다 그때 쓰는 IP 정보 DB에서 국가와 ASN을 찾아 함께 보관한다. 찾기는 메모리의 DB에서 하며 외부에 요청하지 않는다. 루프백·사설·링크 로컬·공유·지정되지 않은 주소는 찾지 않는다.
6. 사건은 최대 100,000개를 메모리에 보관한다. 넘으면 가장 오래된 사건부터 버리고, 버린 사건 가운데 가장 늦은 시각을 기억한다. 이 상한은 설정할 수 없다. 재시작하면 비어 있다. 재로드는 지우지 않는다.
7. 조회 때 기간(최근 1시간 또는 최근 24시간) 안 사건을 주소·국가·ASN별로 센다.
8. IP 정보 DB는 시작 때 읽는다(3.1절 12단계). 실행 중에는 파일 내용 변경을 감지해 다시 읽는다. 성공하면 그 뒤 사건부터 새 DB를 쓰고 `ip_db_loaded`를 기록한다. 실패하면 이전 DB를 계속 쓰고 `ip_db_unavailable`을 기록한다. 설정 재로드 결과(`reload_applied`·`reload_rejected`·`reload_restart_required`)와 관계없이 다시 읽는다. 경로를 바꾸려면 재시작해야 한다. 형식과 원인 코드는 [설정 계약 1.12절](../contracts/config-v4.md#112-ip-정보-db-파일-형식)을 따른다.
9. 통계는 `/metrics`·상태 응답·운영 로그에 넣지 않는다. 관리 API로만 제공한다.
10. 통계 기록 때문에 중계 경로가 6절의 성능 합격 수치를 어겨서는 안 된다. 기록은 연결 사건마다 하며 데이터 전송마다 하지 않는다.

### 3.10 출발지 IP 차단 목록

출발지 IP 차단 목록은 중계 진입점 6개(TCP 뷰어·TCP 서버·WS 뷰어·WS 서버·WSS 뷰어·WSS 서버)가 함께 쓰는 목록 하나다. 설정 키는 `relay.deny.sources`다. 운영자는 문제가 있는 주소를 한 번에 막고, 그 주소의 열린 연결도 바로 끊는다. 결정 근거는 [ADR-0013](../decisions/ADR-0013-relay-source-deny-list.md)이다. 키와 항목 문법은 [설정 계약 1.2절](../contracts/config-v4.md#12-키-표)과 [1.3절](../contracts/config-v4.md#13-ip-항목-문법)이 정한다.

1. 차단 목록에는 만료가 없다. 운영자가 목록에서 항목을 지울 때까지 차단한다.
2. 판정 주소는 클라이언트 주소다. 신뢰 프록시를 거친 WS·WSS는 전달 주소이고, 그 밖의 접속은 소켓 상대 주소다.
3. 차단은 허용보다 우선한다. 허용 목록에 있는 주소도 차단 목록에 있으면 거절한다.
4. 차단 목록의 `[]`는 아무것도 차단하지 않는다. 허용 목록의 `[]`가 모든 주소를 거절하는 것과 뜻이 반대다. 키를 생략해도 같다.
5. 항목 문법은 허용 목록과 같다. 문법 오류는 허용 목록과 같은 오류 코드로 거절하며 진단 키는 `relay.deny.sources[i]`다. `0.0.0.0/0`·`::/0` 같은 전체 체계 항목에는 특별한 경고나 오류가 없다.
6. 차단 항목이 역할이 하나라도 켜진 WS·WSS 리스너의 `trusted_proxies` 항목과 한 주소라도 겹치면 설정 오류 `config_deny_overlaps_proxy`다. 진단 키는 `relay.deny.sources[i]`다. 시작이면 시작 실패(종료 코드 3), 재로드이면 후보 전체 거절, 관리 API 편집이면 `400 config_invalid`다. 역할이 모두 꺼진 리스너의 `trusted_proxies`와는 비교하지 않는다. 판정은 [설정 계약 1.6절](../contracts/config-v4.md#16-값-관계-검사)을 따른다.
7. `relay.deny.sources`는 중계 진입점이 모두 꺼져 있어도 편집할 수 있다. 편집은 `management.config_edit = true`일 때만 할 수 있다.
8. TCP 수락에서는 소켓 상대 주소를 차단 검사, 허용 검사, 연결 예산 검사 순서로 판정한다. 차단이면 `connection_rejected`(stage `accept`, reason `ip_denied`)를 기록하고 소켓을 바로 닫는다.
9. WS·WSS 수락에서는 소켓 상대가 신뢰 프록시이면 차단 검사를 건너뛴다. 소켓 상대가 신뢰 프록시가 아니면 차단 검사를 먼저 하고, 그다음 켜진 역할 허용 목록의 합집합을 검사한다. 차단이면 stage `accept`, reason `ip_denied`로 기록하고 TLS·HTTP 처리 전에 닫는다.
10. WS·WSS 업그레이드에서는 역할별 허용 검사 바로 앞에서 클라이언트 주소를 차단 검사한다. 차단이면 HTTP 403으로 거절하고 stage `upgrade`, reason `ip_denied`로 기록한다. 거절 우선순위는 Origin 403, 서브프로토콜 400, ticket 401, IP 재검사 403 순서다. IP 재검사는 차단 검사 다음에 역할별 허용 검사를 한다. ticket은 소비하지 않는다.
11. 초기 교환을 마친 연결은 대기 등록·매칭·Mode I 대상 연결 전에 현재 차단 목록으로 클라이언트 주소를 다시 검사한다. 차단이면 stage `register`, reason `ip_denied`로 기록한다. TCP는 연결을 닫고 WS·WSS는 close 4014로 닫는다. 목록 교체 전에 수락돼 초기 교환 중이던 연결을 막는 검사다.
12. 차단 목록 값이 이전과 다르게 교체되면, 교체 직후 열린 연결을 검사한다. 파일 감지 재로드와 관리 API 편집은 같은 결과다. 교체 직후 끊기 점검과 등록 검사는 서로 경합하더라도 차단된 연결이 대기나 세션에 남지 않게 처리한다.
13. 활성 세션은 뷰어 또는 Mode II 서버의 클라이언트 주소가 차단되면 세션 전체를 끊는다. Mode I 대상 주소는 클라이언트 주소가 아니므로 검사하지 않는다. `session_closed.close_cause`는 `ip_denied`이고 관리자 계정명은 기록하지 않는다. WS·WSS 쪽 연결은 close 4014 `ip_denied`로 닫는다. TCP 쪽 연결은 관리자 종료와 같은 방식으로 닫는다. 이미 정리 중인 세션은 기존 종료 원인을 유지한다.
14. 대기 연결은 클라이언트 주소가 차단되면 대기에서 빼고 닫는다. `waiting_removed.reason`은 `ip_denied`이고 WS·WSS 쪽 연결은 close 4014로 닫는다.
15. 값이 그대로이거나 항목이 줄기만 하면 끊을 연결이 없다. 끊은 연결은 되살아나지 않는다.
16. 끊은 연결을 요약하는 사건은 따로 두지 않는다. `reload_applied.applied`에 `relay.deny.sources`가 나오고, 끊은 연결마다 `session_closed` 또는 `waiting_removed`를 기록한다. 거절·종료·대기 해제 원인 속성에는 값 `ip_denied`를 쓴다([메트릭 계약 1.4절](../contracts/metrics-v1.md#14-속성-값)).
17. 관리 리스너와 상태 리스너에는 차단 목록을 적용하지 않는다. 사건 이름·필드·수준은 [운영 정보 계약](../contracts/ops-info-v2.md)이 정한다.
18. 이 기능은 설정 계약 4.4.0, 운영 정보 계약 2.3.0, 메트릭 계약 1.2.0, WebSocket 중계 계약 2.2.0, 관리 API 계약 1.5.0을 쓴다.

출발지 허용 정책 누락을 공개 허용으로 대체하지 않는다. 켠 진입점의 목록이 없으면 시작 실패다. 명시적으로 빈 목록을 설정하면 그 진입점의 모든 출발지를 거절한다. `0.0.0.0/0`, `::/0` 같은 전체 허용 항목을 명시적으로 쓰면 허용하고 시작·재로드 시 경고를 기록한다. 기본 허용은 금지한다. 목록 항목 표기는 단일 IP, CIDR, 범위(`a-b`)이며 IPv4·IPv6 모두 받는다. 범위의 시작이 끝보다 크거나, 두 주소의 체계가 다르거나, 표기가 잘못되면 설정 오류다. IP는 개별 사용자 인증이 아니며 같은 공인 IP를 공유하는 사용자를 구분하지 못한다.

TCP 진입점은 접속 ticket을 실을 수 없어 ticket 확인을 적용하지 않는다. ticket을 켠 역할의 TCP 진입점도 켜져 있으면 시작·재로드 때 `ticket_tcp_bypass`를 기록한다. 뷰어는 `relay.tcp_viewer.enabled`, 서버는 `relay.tcp_server.enabled`로 판정한다. 경고에는 `role`, `listener`(`tcp_viewer` 또는 `tcp_server`), `phase`(`startup` 또는 `reload`)를 넣는다. 이 조건만으로 시작·재로드를 거절하지 않는다.

평문 WS에서도 접속 ticket을 켤 수 있다. 이때 ticket이 암호화되지 않으므로 그 구간은 믿을 수 있는 망 안에 있어야 한다. 운영자가 이 조건을 지켜야 한다. ticket을 켠 역할이 `[relay.ws]`에서도 켜져 있으면 시작·재로드 때 `ticket_plaintext_ws`를 기록한다. 경고는 믿을 수 있는 망 조건을 알리고 `role`, `listener = ws`, `phase`(`startup` 또는 `reload`)를 담는다. 이 조건만으로 시작·재로드를 거절하지 않는다.

성능 합격 기준은 다음과 같다.

- 측정 환경: 개발 PC 한 대의 Windows 11 x64와 같은 PC의 WSL2 Ubuntu 24.04 LTS x64. 클라이언트와 VNC Relay는 같은 PC 안에서 루프백으로 접속한다. 하드웨어 사양은 측정 기록에 적는다.
- 부하: 전송 조합(TCP·WS·WSS)마다 활성 100세션. 세션마다 양방향으로 각 1 Mbit/s를 10분 동안 보낸다.
- 합격 수치: 데이터 유실·혼입 0건, VNC Relay를 거쳐 늘어난 지연의 p99 10 ms 이하, VNC Relay 프로세스 CPU 평균 1코어 이하, RSS 256 MiB 이하, 측정 구간 시작 뒤 RSS 증가 10% 이하.

측정 방법과 실제 결과는 [성능 측정 안내와 기록](../how-to/measure-performance.md)을 따른다. 전송 조합(TCP·WS·WSS)마다 따로 판정한다. 허용 오버헤드·잔여 자원 판정 구간(OPS-017)과 느린 수신자 부하(AC-08)는 다음과 같다.

- 허용 오버헤드: 부하 중 VNC Relay RSS에서 유휴 기준 RSS를 뺀 값이 `열린 중계 연결 수 × (B + 64 KiB)` 이하여야 한다. 64 KiB는 소켓·TLS·작업 상태의 연결당 여유다.
- 잔여 자원: Mode II 접속·종료 수명 1,000회를 한 라운드로 하여 15라운드를 반복한다. 각 라운드 뒤 대기 연결과 활성 세션이 0이 된 것을 확인하고 5초 기다린다.
  - 소켓·핸들 수: Windows에서는 Event 핸들과 나머지 핸들을 나누어 센다. 2~15라운드의 Event가 아닌 핸들 수는 1라운드 값과 같아야 한다. Event 핸들 수는 1라운드 값에 작업자 스레드 수(제품 런타임 기본값인 논리 코어 수)의 2배를 더한 값 이하여야 한다. Winsock은 스레드가 특정 소켓 호출을 처음 할 때 그 스레드의 Event를 만들어 유지한다(`mswsock!MSAFD_SockThreadInitialize`, `ws2_32!closesocket`의 `DoWaitForReaders`). 두 호출 경로가 스레드마다 Event를 하나씩만 유지한다는 것은 추정이다. Linux의 fd 수는 2~15라운드 값이 1라운드 값과 같아야 한다.
  - RSS: 11~15라운드 RSS의 최댓값이 1~10라운드 RSS의 최댓값보다 2 MiB 넘게 커서는 안 된다. Windows 개인 커밋 메모리의 일시적 변동을 고려해 두 라운드 값의 차이가 아니라 구간별 최댓값을 비교한다.
  - 수명 반복은 느린 수신자 부하(AC-08)를 실행한 VNC Relay가 아니라 새로 시작한 VNC Relay에서 실행한다. 느린 부하에서 해제된 큰 버퍼 영역이 RSS를 흔들기 때문이다. 느린 부하의 메모리는 허용 오버헤드 기준이 판정한다.
  - 새 VNC Relay에서는 1라운드 전에 예열한다. 느린 부하와 같은 100세션을 열고 양방향 각 1 Mbit/s로 10초 동안 보낸 뒤 닫는다. 작업자 스레드가 소켓 작업에 사용하는 자원을 예열하는 절차다.
  - Linux에서는 수명 반복용 VNC Relay만 `MALLOC_ARENA_MAX=1`로 실행해 할당기 영향을 뺀다. 이 설정은 측정 전용이며 제품 배포 설정이 아니다.
- 느린 수신자(AC-08): 100세션 가운데 50세션은 수신을 멈춰 중계 버퍼를 B까지 채운 상태로 60초 둔다. 나머지 50세션은 양방향 각 1 Mbit/s를 계속 보낸다. 메모리는 위 허용 오버헤드 안이어야 한다. 정상 50세션은 데이터 유실·혼입이 0건이고 전송을 계속해야 한다.
  - 중계 소켓의 커널 송수신 버퍼는 OS 자동 조정을 그대로 쓴다. 허용 오버헤드는 프로세스 RSS만 재며 커널 소켓 메모리를 포함하지 않는다. 루프백 측정에서는 시험 클라이언트 소켓이 같은 커널 메모리를 쓰므로, 시험 클라이언트의 송수신 버퍼를 64 KiB로 둔다. 실제 배치에서 클라이언트는 다른 호스트에 있다.
  - 운영 위험: 막힌 중계 연결 하나가 커널 메모리를 최대 `tcp_rmem`·`tcp_wmem` 최댓값만큼 붙잡을 수 있다. 커널 메모리 압박으로 패킷 폐기와 재전송 백오프가 생길 수 있다.

법률 검토가 필요한 행위의 허용 여부나 엄격한 클린룸 인증 완료를 이 스펙으로 보증하지 않는다.
